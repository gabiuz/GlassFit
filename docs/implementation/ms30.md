## 1. Decisions and Scope

### 1.1 Canonical Person-Name Contract

GlassFit stores person names as a required `first_name`, an optional `last_name`, and a generated `full_name`. This storage contract supports mononyms while preserving the existing relational schema and user interface vocabulary.

| Field | Required | Normalized Length | Persistence | Rule |
|---|---:|---:|---|---|
| `first_name` | Yes | 1 to 50 Unicode code points | `profiles.first_name` | Must contain at least one Unicode letter |
| `last_name` | No | 0 to 50 Unicode code points | `profiles.last_name` | Empty string represents an intentionally absent family name |
| `full_name` | Generated | Maximum 101 database characters | `profiles.full_name` | Database-generated from `trim(first_name || ' ' || last_name)` |

All identity surfaces use the same rules:

- Customer email registration.
- Google OAuth profile creation.
- Customer profile editing.
- Administrator staff activation.
- Administrator profile editing.
- Booking and quotation flows consume the generated name but do not independently validate or split it.

### 1.2 Name Normalization Rules

The canonical name module must perform these operations in order:

1. Normalize each input with Unicode NFC normalization.
2. Trim leading and trailing whitespace.
3. Collapse consecutive whitespace characters to one ordinary space.
4. Count Unicode code points, not JavaScript UTF-16 code units.
5. Reject an empty `first_name`.
6. Reject values exceeding the database limits.
7. Require at least one Unicode letter in each non-empty name field.
8. Accept Unicode letters, combining marks, spaces, periods, apostrophe variants, and Unicode dash punctuation.
9. Reject control characters and unsupported punctuation with a field-specific validation error.

React JSX escaping remains responsible for output encoding. Name validation is a data-quality rule and must not be presented as an HTML sanitization mechanism.

### 1.3 Role-Aware Email Change Policy

All email changes are self-service and apply only to the authenticated administrator's own account. The server derives the caller's role and selects exactly one path:

| Authenticated Role | Change Mechanism | Required Approval | Email Delivery |
|---|---|---|---|
| Staff | Durable pending request followed by server-only `auth.admin.updateUserById` | Any one active Owner or Manager must approve | Approval request is sent to every active Owner and Manager |
| Manager | Server-only `auth.admin.updateUserById` | None; change is immediate | None |
| Owner | Server-only `auth.admin.updateUserById` | None; change is immediate | None |

Within this specification, **privileged administrator** means an active Owner or Manager. Staff members are administrators by account type but do not receive the privileged immediate-change path.

`auth.users.email` remains the source of truth. A database trigger copies every completed Auth email change to `public.profiles.email`. A Staff request does not change Auth or profile data until an authenticated active Owner or Manager approves it. Approval uses a protected POST mutation; merely opening the email link never changes the address. Owner and Manager changes remain immediate and send no Supabase or Resend email.

Neither path verifies ownership of the proposed address by emailing that address. This is an explicit product decision. Staff changes rely on supervisor approval, while Owner and Manager changes rely on verified active-role authorization. Both paths require server-only credentials, target derivation from the session or pending request, and immutable audit persistence.

### 1.4 Out of Scope

- Changing authentication providers.
- Owner-initiated email changes for other administrators.
- Adding arbitrary display-name or preferred-name columns.
- Changing customer email addresses from the customer profile screen.
- Webhooks or new email-delivery infrastructure. Staff approval requests reuse the existing Resend adapter.
- Modifying booking records or historical quotation snapshots after a profile name changes.

## 2. Current Defects

### 2.1 Inconsistent and Restrictive Name Handling

The current implementation has multiple inconsistent validation paths:

- `RegisterForm` requires both name fields and rejects one-character values.
- `PersonalInfoCard` requires both fields and has no shared server validation.
- `StaffActivationForm` accepts optional values but does not use a canonical name contract.
- `AdminProfileCard` accepts one full-name string that must be ambiguously split before persistence.
- The database rejects an empty `last_name`, preventing mononymous profiles.
- Frontend inputs allow up to 60 characters while the database columns allow 50.

### 2.2 Unsafe Administrator Profile Mutation

`updateAdminProfile` currently accepts a caller-provided `profileId` and uses the service-role client. The service role bypasses RLS, so the current interface does not prove that the caller owns the target profile. It also attempts to write the generated `full_name` column directly.

### 2.3 Invalid Generated-Column Insert in the Auth Trigger

`supabase/migrations/002_auth_user_trigger.sql` inserts a value into `profiles.full_name`. PostgreSQL generated columns must not be assigned by application or trigger input. The replacement trigger must omit this column.

### 2.4 Administrator Email Cannot Be Changed

The settings interface permanently disables the email field. No self-service path exists for the role-specific Staff and privileged-administrator workflows, no durable event records the change lifecycle, no completion notice reaches active Owner and Manager accounts after a Staff change, and no trigger synchronizes Auth email changes to `public.profiles`.

## 3. Deep Name Module

### 3.1 Target File

Create `src/lib/identity/personName.ts`.

### 3.2 Interface

The module owns normalization, validation, field limits, and full-name derivation. Callers must not reproduce its regular expression or length logic.

```typescript
export interface PersonNameInput {
    firstName: string;
    lastName?: string;
}

export interface NormalizedPersonName {
    firstName: string;
    lastName: string;
    fullName: string;
}

export type PersonNameResult =
    | { ok: true; value: NormalizedPersonName }
    | {
          ok: false;
          field: "firstName" | "lastName";
          error: string;
      };

export function normalizePersonName(input: PersonNameInput): PersonNameResult;
```

### 3.3 Module Invariants

- The module has no React, Supabase, or browser dependency.
- It produces deterministic output for identical input.
- It does not mutate the input object.
- `fullName` is returned for Auth metadata and immediate UI updates only. Database writes use `firstName` and `lastName` exclusively.
- The database-generated `profiles.full_name` remains authoritative after persistence.

## 5. Administrator Server Actions

### 5.1 updateAdminProfile

**Target:** `src/features/admin/settings/settingsActions.ts`

Replace the caller-controlled interface with:

```typescript
export async function updateAdminProfile(
    input: PersonNameInput,
): Promise<SettingsActionResult<NormalizedPersonName>>;
```

Required execution order:

1. Call the existing non-redirecting administrator authorization check.
2. Reject unauthenticated users, customers, suspended administrators, and administrators with inactive roles.
3. Derive the target profile ID from the verified administrator context.
4. Normalize and validate through `normalizePersonName`.
5. Use `createSupabaseServerClient()` so the mutation executes under the authenticated user's RLS context.
6. Update only `first_name` and `last_name` for the verified profile ID.
7. Do not use `createSupabaseServiceClient()`.
8. Do not accept `profileId` from the client.
9. Return the normalized name on success.

### 5.2 changeAdminEmail

**Target:** `src/features/admin/settings/settingsActions.ts`

Create one role-aware interface. The caller cannot select the change mode:

```typescript
export interface AdminEmailChangeData {
    mode: "staff_approval_required" | "privileged_immediate";
    email: string;
}

export async function changeAdminEmail(
    newEmail: string,
): Promise<SettingsActionResult<AdminEmailChangeData>>;
```

Shared execution order:

1. Verify the caller through the existing administrator authorization check.
2. Reject unauthenticated users, customers, suspended administrators, and administrators with inactive roles.
3. Normalize the input with `trim().toLowerCase()`.
4. Reject empty values and values longer than 254 characters.
5. Validate with the existing project email validator or an existing approved schema. Do not introduce a dependency.
6. Compare normalized addresses case-insensitively. Return a successful informational result when the address is already current.
7. Derive the target Auth user and profile identifiers from the verified context.
8. Select the Staff or privileged path from the verified role. Never accept a role or mode from the client.
9. Insert an `admin_email_change_events` row before any privileged Auth mutation.

#### Staff Path

1. Do not call any Supabase Auth email-change method.
2. Revoke any older `PendingApproval` request for the same Staff profile.
3. Generate 32 cryptographically secure random bytes and encode the raw approval token as lowercase hexadecimal.
4. Store only the SHA-256 token hash. Never persist or log the raw token.
5. Set the approval expiry to 24 hours after `requested_at`.
6. Insert the event with `change_mode = 'StaffApproval'`, `status = 'PendingApproval'`, and `delivery_status = 'Pending'`.
7. Query and deduplicate every active Owner and Manager email address.
8. Build a protected review URL from the configured application origin: `/admin/settings/email-change-requests/{rawToken}`.
9. Send a branded approval-request email to every eligible recipient through the existing Resend adapter.
10. Include the Staff member's name, current email, proposed email, request time, expiry time, and review link. Do not include session data.
11. Record per-recipient delivery results in the event audit. At least one eligible recipient must receive the message before the request is considered actionable.
12. If no eligible recipient exists or every delivery fails, mark the event `Failed` and return an error. The email remains unchanged.
13. If some deliveries fail, retain `PendingApproval`, mark `delivery_status = 'Partial'`, and expose retry for the failed recipients.
14. Return `mode: "staff_approval_required"` and state that the current email remains active until an Owner or Manager approves the request.

#### Owner and Manager Path

1. Create the service client only after the verified role is exactly Owner or Manager.
2. Call the server-only administrative Auth method for the verified caller:

```typescript
await serviceSupabase.auth.admin.updateUserById(
    adminContext.userId,
    {
        email: normalizedEmail,
        email_confirm: true,
    },
);
```

3. Do not call the authenticated `updateUser({ email })` method.
4. Do not dispatch any Resend message or supervisory notification.
5. Refresh the authenticated caller's Supabase session so cookie-backed user state receives the new email. If refresh fails after Auth succeeds, do not repeat the email mutation; return a success-with-relogin message.
6. Mark the event `Completed` with `delivery_status = 'NotRequired'` after Auth succeeds.
7. Return `mode: "privileged_immediate"` and state that the email changed immediately.
8. If Auth rejects the change, mark the event `Failed` with a sanitized reason.

Both paths map duplicate-email, expired-session, provider, and unexpected failures to stable messages. Staff additionally maps approval-email delivery failures. No path logs raw tokens or provider payloads.

### 5.3 Staff Approval Actions

**Targets:** `src/features/admin/settings/settingsActions.ts`, `src/lib/email/resendClient.ts`, and a new `src/lib/email/templates/staffEmailChangeApproval.ts`

Create these server actions:

```typescript
export async function approveStaffEmailChange(
    rawToken: string,
): Promise<SettingsActionResult>;

export async function rejectStaffEmailChange(
    rawToken: string,
): Promise<SettingsActionResult>;

export async function cancelOwnStaffEmailChange(
    eventId: string,
): Promise<SettingsActionResult>;

export async function retryStaffEmailChangeApprovalDelivery(
    eventId: string,
): Promise<SettingsActionResult>;
```

Approval requirements:

1. Require an authenticated active Owner or Manager. A token alone grants no authority.
2. Hash the supplied raw token and load exactly one `PendingApproval` event by hash.
3. Reject missing, expired, cancelled, rejected, processing, completed, or failed requests.
4. Revalidate the proposed email format and uniqueness immediately before mutation.
5. Load the target Staff profile from the event, verify it is still active, and verify its current email still equals `previous_email`.
6. Use the service client to call `auth.admin.updateUserById` for the event's Staff user ID with the proposed email and `email_confirm: true`.
7. Never accept a target user ID, proposed email, or role from the approval form.
8. Atomically claim the request by conditionally changing `PendingApproval` to `Processing` before calling Auth. A concurrent approver cannot claim the same request.
9. After Auth succeeds, verify profile synchronization and mark the event `Completed` with `decided_by`, `decided_at`, and `completed_at`.
10. On a retryable provider failure, return the event to `PendingApproval`, clear processing ownership, and store a sanitized error without changing the email.
11. The first successful approval wins. Concurrent or later approvals never repeat the Auth mutation.

Rejection requirements:

- Require an authenticated active Owner or Manager.
- Resolve the event only through the token hash.
- Mark the pending event `Rejected` with `decided_by` and `decided_at`.
- Do not mutate Auth or profile email data.

Cancellation requirements:

- Require the authenticated Staff member who owns the pending event.
- Mark it `Cancelled` before approval.
- Do not permit cancellation after a decision or expiry.

Retry requirements:

- Require an active Owner or Manager.
- Reload recipient eligibility and event data on the server.
- Send only to recipients without a successful delivery record.
- Refuse decided, expired, cancelled, or non-Staff events.

Provide authorized read actions for Staff to view their own current request and for Owner or Manager to list pending Staff requests and partial or failed approval-email deliveries.

### 5.4 Action Result Semantics

`SettingsActionResult` continues to use the existing discriminated union. Authentication and authorization failures return `{ ok: false, error }` rather than redirecting from these settings actions.

## 7. Database Migration 012

### 7.1 Migration File

Create `supabase/migrations/012_identity_name_and_admin_email_workflow.sql`.

All database changes in this milestone belong in this single ordered migration.

### 7.2 Relax the Last-Name Constraint

The migration must:

1. Set `public.profiles.last_name` default to `''`.
2. Retain `NOT NULL`.
3. Drop `profiles_last_name_not_blank` if it exists.
4. Retain `profiles_first_name_not_blank`.
5. Retain the generated `full_name` expression.

### 7.3 Replace handle_new_user

Replace `public.handle_new_user()` and recreate `on_auth_user_created` so that:

- Email registrations read normalized name metadata.
- Google OAuth names split on the first normalized whitespace only when multiple parts exist.
- A single-word Google name becomes `first_name` with `last_name = ''`.
- Missing names fall back deterministically to the email local part.
- `first_name` and `last_name` are limited to 50 database characters.
- The `INSERT` omits `full_name` completely.
- The function uses `SECURITY DEFINER SET search_path = ''` and fully qualified relations.
- Trigger and function creation are idempotent for a clean database reset.

### 7.4 AdminEmailChangeEvents (ERD-E20)

Create `public.admin_email_change_events` as the durable audit and Staff approval state:

| Column | Requirement |
|---|---|
| `event_id` | UUID primary key with `gen_random_uuid()` default |
| `profile_id` | Nullable UUID reference to `profiles.profile_id` with `ON DELETE SET NULL` |
| `target_user_id` | Required UUID snapshot of the Auth user ID; never accepted from the client |
| `actor_full_name` | Required snapshot of the actor's generated name at request time |
| `actor_role` | Required value in `Owner`, `Manager`, or `Staff` |
| `previous_email` | Required normalized email before the change |
| `proposed_email` | Required normalized target email |
| `change_mode` | Required value in `StaffApproval` or `PrivilegedImmediate` |
| `status` | Required value in `Initiated`, `PendingApproval`, `Processing`, `Rejected`, `Cancelled`, `Expired`, `Completed`, or `Failed` |
| `approval_token_hash` | Nullable unique 64-character lowercase SHA-256 hexadecimal digest; required only for Staff approval |
| `approval_expires_at` | Nullable timestamp required only for Staff approval |
| `delivery_status` | Required value in `Pending`, `NotRequired`, `Delivered`, `Partial`, or `Failed` |
| `approval_deliveries` | Required JSONB array containing per-recipient profile ID, normalized email, delivery status, provider message ID, and attempt timestamp |
| `delivery_attempts` | Non-negative integer defaulting to zero |
| `processing_by` | Nullable UUID reference to the administrator currently processing approval with `ON DELETE SET NULL` |
| `processing_started_at` | Nullable timestamp set only while status is `Processing` |
| `decided_by` | Nullable UUID reference to the approving or rejecting administrator profile with `ON DELETE SET NULL` |
| `decided_at` | Nullable timestamp set on approval or rejection |
| `last_error` | Nullable sanitized operational error without secrets or provider payloads |
| `requested_at` | Required timestamp defaulting to `now()` |
| `completed_at` | Nullable timestamp set after the Auth email becomes current |

Enable RLS and expose no direct anonymous or authenticated mutation policy. All event access occurs through authorized server actions using the service client after role or ownership verification. Add indexes for `profile_id`, `target_user_id`, `status`, `delivery_status`, `approval_expires_at`, and descending `requested_at`. Add a partial unique index allowing at most one `PendingApproval` event per Staff profile.

### 7.5 Synchronize Completed Emails

Create a function and trigger with these properties:

- Trigger timing: `AFTER UPDATE OF email ON auth.users`.
- Trigger condition: `OLD.email IS DISTINCT FROM NEW.email`.
- Mutation: update only `public.profiles.email` where `profile_id = NEW.id`.
- Null protection: perform no profile update when `NEW.email` is null.
- Security: `SECURITY DEFINER SET search_path = ''` with fully qualified relations.
- The trigger fires in the same transaction when Supabase assigns a new value to `auth.users.email`.
- Staff pending approval does not trigger synchronization because it does not mutate Auth.
- Approved Staff changes and immediate Owner or Manager changes synchronize when the administrative Auth mutation updates `auth.users.email`.

### 7.6 Deployment and Rollback

Deployment order:

1. Apply migration `012`.
2. Verify registration and email synchronization against the target Supabase environment.
3. Deploy the Next.js application changes.
4. Execute the MS30 smoke tests.

Application rollback retains migration `012`. The relaxed constraint, repaired Auth trigger, event audit, and email synchronization trigger are backward-compatible with the previous application. Do not re-add the last-name non-blank constraint after mononymous profiles may exist. Do not delete email-change audit events during application rollback.

## 11. Security Requirements

| Concern | Required Control |
|---|---|
| Caller changes another profile | No profile identifier crosses the Server Action interface; target comes from verified admin context |
| Service-role RLS bypass | Profile-row mutations use the authenticated client; service credentials are limited to verified immediate changes, atomically claimed Staff targets loaded from hashed-token events, and audit persistence |
| Staff request bypasses approval | Staff submission never calls an Auth email mutation; only an active Owner or Manager approval can invoke the administrative Auth change |
| Approval-link theft or scanner prefetch | Raw token is never stored, token alone grants no authority, GET never mutates, and approval requires an authenticated POST action |
| Replay or concurrent approval | Token hash is unique, status transition is conditional, and the first valid decision wins |
| Privileged immediate change | Only verified active Owner or Manager roles may reach `auth.admin.updateUserById`; the caller's own user ID is derived from the session and every attempt is audited |
| Missing Staff approval request | Durable ERD-E20 delivery data records every active Owner and Manager attempt and retains partial failures for retry |
| Stale profile email | Database trigger synchronizes every completed `auth.users.email` change and ignores pending approval records |
| Search-path injection | Trigger functions use `SECURITY DEFINER SET search_path = ''` and qualified relations |
| Generated-column mutation | Application and Auth trigger never write `profiles.full_name` |
| Script injection through names | React performs output escaping; validation rejects controls and unsupported characters |
| Sensitive logging | Actions do not log raw emails, raw approval tokens, or approval URLs |

## 12. Completion Gate

MS30 is complete only when:

- All name-entry surfaces use the shared module.
- Mononyms can register and edit profiles without a fabricated last name.
- No self-service action accepts a target profile ID.
- Profile-row mutations do not use the service-role client; administrative Auth mutation is restricted to a verified Owner or Manager's own account or a Staff target loaded from an atomically claimed pending event.
- Migration `012` passes from a clean database reset.
- The Auth trigger no longer assigns the generated `full_name` column.
- A Staff request leaves Auth and profile emails unchanged until approval.
- Every active Owner and Manager receives the Staff approval request, with partial delivery failures retained for retry.
- Any one authenticated active Owner or Manager can approve; token possession alone cannot approve.
- Approval, rejection, cancellation, expiry, replay, and concurrent decisions are deterministic and audited.
- Owner and Manager email changes apply immediately without Supabase or Resend email delivery.
- All completed Auth email changes synchronize to `profiles.email`.
- All QAD-TC12, QAD-TC14, and QAD-TC45 cases pass.
- `npm run test:ms30`, `npm test`, lint, typecheck, and production build pass.
- PRD, SDD, DSD, ERD, QAD, BUILD, index, and milestone documents are reconciled in the same implementation change.
