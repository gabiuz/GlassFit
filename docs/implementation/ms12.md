## 1. Problem, Goal, and Fixed Decisions

### 1.1 Problem

Product Details currently lets a user select an aluminum finish, glass type, glass color, glass thickness, dimensions, and quantity. Clicking "Visualize on my own Space" navigates through image upload, but the workspace starts from its own defaults and exposes only the legacy finish and glass controls.

The configuration must survive this route sequence:

1. `/product-details/[id]`
2. `/visualize/[productId]/upload`
3. `/visualize/[productId]/workspace`

### 1.2 Goal

For an R.R.D.-supported product, the first workspace render must use the valid configuration selected on Product Details. The workspace must then expose the same 24 aluminum finishes, 5 R.R.D. glass types, 4 glass colors, and 3 optical glass thicknesses. Existing workspace-only glass modes remain available under an Advanced group.

### 1.3 Fixed Implementation Decisions

The following decisions are final for this implementation:

1. Product Details stores a product-scoped `ProductConfigurationSeed`, not a `Partial<ProductConfigurationSnapshot>`.
2. The pending seed is stored in `VisualizationSessionState`, persisted in `sessionStorage`, and retained by image preparation only when its `productId` matches.
3. `thicknessMm` remains the existing workspace structural or legacy thickness field. Product Details glass thickness is written only to `glassThicknessMm`. IMP-MS12 does not change pricing or structural guardrail semantics.
4. Workspace hydration uses explicit precedence: saved full workspace configuration, matching Product Details seed, then existing workspace defaults.
5. Fixed and parametric renderer paths both receive `glassColor` and `glassThicknessMm`. No renderer may hardcode `"clear"` or `6` once these values are supplied.
6. The comparison snapshot set contains all 24 R.R.D. finishes listed in Section 10.
7. Tests added by IMP-MS12 are included in `npm test` and have a dedicated `test:ms12` script.

## 4. Data Contracts

### 4.1 Product Details Seed

The cross-route payload is intentionally smaller than a workspace snapshot:

```typescript
export type ProductConfigurationSeed = {
  aluminumFinish: RrdAluminumFinishKey;
  glassType: GlassTypeKey;
  glassAppearance: GlassAppearanceMode;
  glassColor: GlassColorKey;
  glassThicknessMm: GlassThicknessMm;
  widthCm?: number;
  heightCm?: number;
  quantity: number;
};

export type PendingProductConfiguration = {
  productId: string;
  configuration: ProductConfigurationSeed;
};
```

`GlassTypeKey` moves to `src/lib/visualization/types.ts` as the canonical type because the seed is part of visualization session state. `materialMapping.ts` re-exports it to preserve all existing IMP-MS09 import paths and avoid a type dependency cycle.

Rules:

- `widthCm` and `heightCm` are either both present and valid or both omitted.
- Empty or invalid Product Details dimensions are never serialized as `0`.
- `quantity` is normalized through `normalizeProductQuantity()` before storage.
- All enum-like values are validated at the storage and restoration boundary.
- A seed never carries transform, occlusion, scene, structural waiver, or placement state.

### 4.2 Full Workspace Snapshot

`ProductConfigurationSnapshot` gains these backward-compatible fields:

```typescript
glassColor?: GlassColorKey;
glassThicknessMm?: GlassThicknessMm;
glassType?: GlassTypeKey;
```

`aluminumFinish` remains `string` in the persisted snapshot because older sessions may contain `"black"`, `"silver"`, or an unknown value. Runtime workspace state uses `RrdAluminumFinishKey` after normalization. The persisted string type is a compatibility boundary, not the internal domain type.

### 4.3 Thickness Field Semantics

| Field | Meaning in IMP-MS12 | Source |
|---|---|---|
| `thicknessMm` | Existing structural or legacy workspace thickness used by current guardrail and pricing code | Existing workspace state only |
| `glassThicknessMm` | R.R.D. optical glass choice: 6, 8, or 12 mm | Product Details seed or workspace glass control |

Product Details must not copy `selectedThickness` into `thicknessMm`. Existing pricing and guardrail code must not be rewritten to consume `glassThicknessMm` in this milestone.

### 4.4 Runtime Validation

`colorVariations.ts` remains the owner of aluminum finish validation and normalization:

```typescript
isRrdAluminumFinish(value: unknown): value is RrdAluminumFinishKey
normalizeAluminumFinish(value: unknown): RrdAluminumFinishKey
```

`configurationPropagation.ts` must export the remaining pure helpers with no React or browser dependency:

```typescript
normalizeProductConfigurationSeed(value: unknown): ProductConfigurationSeed | null
normalizeGlassType(value: unknown): GlassTypeKey | undefined
normalizeGlassColor(value: unknown): GlassColorKey
normalizeGlassThickness(value: unknown): GlassThicknessMm
deriveGlassTypeFromAppearance(value: GlassAppearanceMode): GlassTypeKey | undefined
getMatchingProductConfigurationSeed(
  pending: PendingProductConfiguration | null,
  productId: string,
): ProductConfigurationSeed | null
```

The session reader must call seed normalization instead of trusting parsed JSON through a type assertion. Invalid pending data is discarded without affecting the rest of the session.

## 5. Session Transport and Lifecycle

### 5.1 State and Context API

`VisualizationSessionState` gains:

```typescript
pendingProductConfiguration: PendingProductConfiguration | null;
```

The context gains:

```typescript
setPendingProductConfiguration: (
  productId: string,
  configuration: ProductConfigurationSeed,
) => void;

clearPendingProductConfiguration: () => void;
```

### 5.2 Required State Transitions

| Event | Pending seed behavior |
|---|---|
| Product Details visualize click | Replace pending seed with the current product ID and validated configuration |
| Refresh on Product Details or upload | Restore the normalized pending seed from `sessionStorage` |
| Upload completion for the same product | `setPreparedSpaceImage()` preserves the pending seed while resetting prior workspace artifacts |
| Upload completion for a different product | `setPreparedSpaceImage()` clears the pending seed |
| Workspace first mount with matching product | Pass the seed to `ProductModelWorkspace` |
| Workspace emits its first complete configuration | Persist the full `productConfiguration`, then clear the pending seed |
| Full saved configuration already exists | Ignore the pending seed and clear it after confirming the full configuration is retained |
| Change Product from upload | Clear the pending seed before navigation |
| Workspace product transition in `add`, `change`, or `edit` mode | Clear the Product Details pending seed; use the transition's explicit configuration rules |
| Reset visualization session | Clear the pending seed with all other session state |
| Direct workspace or upload URL with no seed | Use current default behavior |

The pending seed must be included in the primary, lightweight, and minimal configuration-only `sessionStorage` payloads. The field contains only small scalar values and must never be removed as part of quota reduction.

### 5.3 Consumption Ordering

Clearing must not occur during render. `ProductAwareWorkspacePage` clears a matching pending seed in an effect only after `onConfigurationChange` has stored the first complete `ProductConfigurationSnapshot`. This ordering is safe under React Strict Mode because both operations are idempotent.

The pending seed is valid only when `pendingProductConfiguration.productId === productId`. A nonmatching seed is never passed to the workspace.

## 6. Product Details Capture and Navigation

The plain visualization `Link` is replaced with a button-backed programmatic navigation handler. The component uses the existing session provider from the root layout.

The handler must:

1. Normalize quantity.
2. Validate the dimension pair.
3. Include both dimensions only when the pair is valid.
4. Reject navigation only when the user has entered an invalid or incomplete dimension pair.
5. Permit navigation when both dimension fields are empty; workspace scale-aware defaults then apply.
6. Create a `ProductConfigurationSeed` for supported product types.
7. Store the seed under `product.product_id` before calling `router.push()`.
8. For unsupported product types, clear any old seed and navigate without a new one.

The handler stores `glassThicknessMm` but does not set the legacy `thicknessMm` field.

## 7. Workspace Hydration and State Invariants

### 7.1 Hydration Precedence

Each field is initialized once when the keyed workspace mounts:

1. A valid full `initialConfiguration` for an existing or edited workspace session.
2. A valid matching Product Details seed.
3. Existing workspace defaults and scale-aware dimension estimation.

The seed may override only these fields:

- `aluminumFinish`
- `glassType`
- `glassAppearance`
- `glassColor`
- `glassThicknessMm`
- `widthCm` and `heightCm` when both are valid
- `quantity`

All transform, zoom, lighting, occlusion, sill, panel, structural waiver, and placement values continue to use full saved configuration or existing workspace defaults.

### 7.2 Backward Compatibility

| Stored condition | Required result |
|---|---|
| Missing `glassColor` | Use `"clear"` |
| Missing `glassThicknessMm` | Use `6` |
| Missing `glassType`, appearance `"clear"` | Use `"regular"` |
| Missing `glassType`, appearance `"frosted"` | Use `"frosted"` |
| Missing `glassType`, appearance `"reflective"` | Use `"reflective"` |
| Appearance `"opaque"` or `"outdoor"` | Keep appearance; leave `glassType` undefined |
| Finish `"black"` | Normalize to `"al_1009"` |
| Finish `"silver"` | Normalize to `"al_1001"` |
| Unknown finish | Use `"white"` |
| Invalid glass color or thickness from storage | Use the IMP-MS09 default |

### 7.3 Glass Type and Advanced Appearance Invariant

- Selecting an R.R.D. glass type sets both `glassType` and its mapped `glassAppearance` in one handler.
- Selecting Advanced `opaque` or `outdoor` sets `glassType` to `undefined` and sets `glassAppearance` to the chosen mode.
- Selecting an R.R.D. type after an Advanced mode restores both fields.
- Snapshot emission includes `glassType` only when an R.R.D. type is active.
- The UI derives selected state from these two fields and must never show an R.R.D. type and an Advanced mode as selected simultaneously.

### 7.4 Complete Snapshot Emission

Every emitted `ProductConfigurationSnapshot` includes the normalized `aluminumFinish`, `glassAppearance`, `glassColor`, and `glassThicknessMm`, plus `glassType` when applicable. `applyProductConfiguration()` must restore the same fields when editing a placed overlay.

## 8. Renderer and Material Integration

### 8.1 Renderer Options

Replace positional material arguments with an explicit options object to prevent parameter drift:

```typescript
export type ModelPresentationOptions = {
  aluminumFinish: RrdAluminumFinishKey;
  glassAppearance: GlassAppearanceMode;
  glassColor: GlassColorKey;
  glassThicknessMm: GlassThicknessMm;
  includeSill: boolean;
};
```

`MVPModelRenderer.loadModel()`, its fixed-model branch, and its parametric branch receive this object. `ParametricProductBuilderOptions` gains `glassColor` and `glassThicknessMm`. Both branches pass the complete values to `applyPresentationMaterials()`.

No fixed or parametric render path may hardcode glass color or thickness after this change. Default values are applied at the workspace hydration boundary.

### 8.2 Capability Reporting

After a model group is assembled and before or during material application, the renderer calls `detectProductMaterialCapabilities(group)`. `loadModel()` resolves with:

```typescript
export type LoadedModelResult = {
  capabilities: ProductMaterialCapabilities;
};
```

The workspace stores capabilities for the current model-load revision only. Results from superseded asynchronous loads are ignored using the renderer's existing load-version guard.

Glass Type, Glass Color, and Glass Thickness controls are disabled only when capability detection has completed and `hasGlass === false`. While loading or unknown, controls remain enabled so the user is not shown a false negative. Disabled controls use `disabled`, `aria-disabled`, and explanatory text matching the Product Details accessibility pattern.

### 8.3 Finish and Glass Application

- Finish material properties come from `findFinishOption()` after normalization.
- Glass tint and optical thickness flow through `createMaterialPalette()` and `createWindowGlassMaterial()`.
- Unsupported products retain the legacy basic controls and do not receive the R.R.D. catalog UI.
- Existing pricing mapping from finish and glass appearance is unchanged by this milestone.

## 9. Workspace Controls

### 9.1 Supported Product Types

For Window, Door, and Cabinet products:

- Aluminum Finish uses all 24 options from `getAvailableFinishOptions()`.
- Glass Type uses all 5 options from `getAvailableGlassTypeOptions()`.
- Advanced Glass Appearance contains only Opaque and Outdoor.
- Glass Color uses all 4 `GLASS_COLOR_OPTIONS`.
- Glass Thickness uses all 3 `GLASS_THICKNESS_OPTIONS`.

For unsupported product types, the existing basic finish and glass appearance controls remain available. Their visible White, Black, and Silver finish choices use normalized keys `white`, `al_1009`, and `al_1001` so runtime finish state remains `RrdAluminumFinishKey`. No R.R.D. seed is created on Product Details for these products.

### 9.2 Layout and Accessibility

- The finish options use `max-h-72 overflow-y-auto`.
- Existing workspace spacing, radii, colors, labels, focus behavior, and Tailwind tokens are reused.
- Every option is a native button or input with a programmatic label and visible focus state.
- Disabled glass groups provide one shared explanatory message instead of repeated tooltips.
- No external UI library or new design system is introduced.

### 10.2 Snapshot Rules

> Superseded by `docs/implementation/fix10.md` as of September 22, 2026. The 24 finishes remain mandatory metadata and selectable choices, but binary finish layers are generated lazily, stored outside `sessionStorage`, and are not an all-finishes readiness requirement.

- Every placed overlay generates snapshots for all 24 R.R.D. finishes.
- Maximum generated finish snapshots per overlay is 24.
- The active finish snapshot is used for the committed flattened layer.
- `hasCompleteVariationLayers()` requires all 24 finishes.
- Comparison selectors expose the intersection of finish keys available across all compared overlays. Complete overlays expose all 24 options.
- If a stored initial comparison selection is not in the intersection, it falls back to `white`.
- Finish titles and swatches come from shared metadata. Consumers must not recreate labels or colors locally.

This policy exposes the complete R.R.D. catalog while preserving deterministic snapshots and the user's exact active finish in the committed visualization and configuration snapshot.

## 13. Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Stale Product Details configuration applies to another product | High | Store product ID with the seed and require an exact match at upload and workspace boundaries |
| Upload preparation erases the seed | High | Preserve the matching seed explicitly in `setPreparedSpaceImage()` and test the transition |
| Glass options reach only one renderer strategy | High | Use one presentation options object for fixed and parametric branches and test both |
| Optical thickness changes pricing or guardrails unintentionally | High | Keep `glassThicknessMm` separate and leave existing `thicknessMm` consumers unchanged |
| Session JSON contains invalid values | Medium | Normalize at read boundaries and discard only the invalid pending seed |
| Asynchronous capability result belongs to an older model | Medium | Apply capabilities only for the current renderer load version |
| Comparison snapshot rendering becomes expensive | Medium | Generate each of the 24 finishes exactly once per overlay and reuse persisted snapshots across comparison views |
| Expanded controls crowd the sidebar | Medium | Use the established scroll container and existing responsive layout patterns |
| Advanced mode conflicts with R.R.D. glass type | Medium | Enforce the state invariant in one selection handler and snapshot serializer |
