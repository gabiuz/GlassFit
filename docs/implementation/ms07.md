## 1. Problem Context & Motivation

In Milestone MS-02 (`docs/implementation/ms02.md`), GlassFit introduced interactive **4-Point Perspective Plane Fitting** for window products. In real-world customer room photographs, fenestration openings photographed from oblique angles appear as trapezoids or non-axis-aligned quadrilaterals due to projective foreshortening. When an aperture is photographed at an angle, the near vertical jamb appears taller than the far jamb, the horizontal header slopes, and standard axis-aligned rectangular placement creates jarring visual detachment from the wall surface.

MS-02 solved this problem for windows through a 4-point interactive canvas picker (`PerspectivePlanePicker.tsx`), projective homography computation via Direct Linear Transform (DLT in `perspectiveTransform.ts`), edge-to-edge 3D perspective camera projection (`ProductModelRenderer.render(yaw, pitch, isPlanarFit)` in `modelRenderer.ts`), and CSS `matrix3d()` transformation in the live DOM.

### The Architectural Limitation in the Current System

Despite the complete mathematical independence of the underlying homography solver and Three.js edge-to-edge camera projection, **4-point perspective plane fitting is currently hard-gated exclusively to window products**:

1. **Hardcoded Product Type Gating:** In `src/features/visualization/components/ProductModelWorkspace.tsx` (line 373 and line 2451), the "Fit to Opening" button is conditioned strictly on:
   ```typescript
   const isWindowProduct =
     structuralDefinition?.product.productType === "Window" ||
     Boolean(
       structuralDefinition?.components.some(
         (component) => component.componentKey.replace(/_/g, "-") === "window-sill",
       ),
     );
   ```
   When a customer or administrator configures a **Door product** (such as a 2-Panel Sliding Glass Door, French Double Swing Door, Bi-Fold Patio Door, or Commercial Entry Door), `isWindowProduct` evaluates to `false`. As a consequence, the "Fit to Opening" toolbar button is suppressed entirely.

2. **Detached Door Visualizations in Real-World Client Spaces:** Doors are architectural apertures installed into wall cutouts, doorways, portals, and patio openings. When customers photograph room entryways or patio portals obliquely, doors exhibit the exact same trapezoidal perspective foreshortening as windows. Currently, customers placing doors are forced to use 2D free-placement (drag, scale, rotate) or manual yaw/pitch sliders, which can never conform flush to an oblique door portal.

3. **Hardcoded UI Copy:** `PerspectivePlanePicker.tsx` previously displayed window-specific prompt strings, which caused user confusion when configuring doors. The shared picker now uses contextual window, door, or wall copy throughout drag selection and refinement.

4. **Window-Biased Dimension Estimation:** In `ProductModelWorkspace.tsx.onConfirm`, opening dimension estimation assumes typical window dimensions (`currentH = Number(heightCm) || 120`). Doors have distinct architectural heights standardized by the Philippine National Building Code (typically 2100mm / 210cm finished floor-to-header). When a tall door opening (aspect ratio < 1.0) is fitted, the existing window dimension formula divides width by aspect ratio, occasionally exploding door height to unrealistic extremes.

### The MS-07 Solution: Complete Parity of 4-Point Perspective Plane for Doors

MS-07 removes the artificial restriction and brings **exact feature and rendering parity** of the 4-point perspective plane workflow from windows to all door products:
- Extend aperture eligibility from `isWindowProduct` to `supportsPerspectivePlane` (`isWindowProduct || isDoorProduct`).
- Present the teal "Fit to Opening" button in the active toolbar when configuring door products.
- Dynamically tailor `PerspectivePlanePicker.tsx` instruction copy based on whether the active product is a window or a door.
- Provide height-anchored dimensional estimation tailored to door openings (standard 210cm baseline).
- Reuse the existing edge-to-edge 3D camera projection, CSS `matrix3d()` DOM warping, 9-handle perspective manipulation, and triangle-mesh snapshot compositing pipeline with zero regression.

## 4. Architectural Analysis: Window vs Door Opening Dynamics

To ensure a seamless extension from windows to doors, the physical and geometric characteristics of both fenestration types must be aligned:

| Dimension / Behavioral Aspect | Window Fenestrations (MS-02) | Door Fenestrations (MS-07) | Architectural Integration Strategy |
|---|---|---|---|
| Floor / Elevation Reference | Elevated off the floor; sill sits atop apron wall (sill height typically 800mm to 1000mm) | Ground level; bottom threshold or floor track rests directly on the finished floor line | Point 3 (bottom-right) and Point 4 (bottom-left) align with the room's floor/threshold boundary. |
| Architectural Standard Height | 600mm to 1500mm (highly variable by room type and elevation) | 2000mm to 2400mm (standardized at 2100mm in Philippine residential/commercial architecture) | For doors, default height baseline is 210cm (or product template default), anchoring width calculation reliably. |
| Aperture Aspect Ratio Range | 0.8 to 2.5 (predominantly landscape or square apertures) | 0.35 to 0.55 (single swing/sliding doors) or 0.7 to 1.8 (double swing/multi-panel patio sliding doors) | Door dimension estimation calculates `width = height * openingAspect` rather than dividing width by aspect. |
| Foreshortening Characteristics | Vertical jambs foreshorten based on horizontal camera yaw; rails slope with pitch | Tall door jambs exhibit pronounced vertical foreshortening due to height; lintel and threshold converge | `deltaH` and `deltaW` formulas compute initial 3D yaw and pitch identically, rotating door frame reveals into opening. |
| 3D Model Structure | Built via `buildWindowLikeProduct` (parametric extrusion) | Built via `buildAssembledProduct` (multi-part GLB) or `buildWindowLikeProduct` | Both output a centered `THREE.Group` at origin, enabling identical `isPlanarFit` camera framing. |
| Transform Handles | 9 handles (4 corners, 4 midpoints, 1 center) | 9 handles (4 corners, 4 midpoints, 1 center) | User can stretch door width, height, and position directly in perspective space. |
| Occlusion Interaction | YOLO foreground objects (desks, sofas) occlude window | Foreground furniture (chairs, dining tables, rugs) occlude door | Composite pipeline in `captureWorkspaceSnapshot` draws masks over door canvas identically. |

### 5.1 Presentation Layer: `ProductModelWorkspace.tsx`

#### 5.1.1 Product Classification Logic

Currently, line 373 defines only window product detection:
```typescript
const isWindowProduct =
  structuralDefinition?.product.productType === "Window" ||
  Boolean(
    structuralDefinition?.components.some(
      (component) => component.componentKey.replace(/_/g, "-") === "window-sill",
    ),
  );
```

MS-07 introduces `isDoorProduct` and the unified aperture predicate `supportsPerspectivePlane`:
```typescript
const isDoorProduct =
  structuralDefinition?.product.productType === "Door" ||
  (structuralDefinition?.product.productType || "").toLowerCase().includes("door") ||
  Boolean(
    structuralDefinition?.components.some(
      (component) => component.componentKey.replace(/_/g, "-").includes("door"),
    ),
  );

const supportsPerspectivePlane = isWindowProduct || isDoorProduct;
```

#### 5.1.4 Perspective Confirmation & Door Dimension Estimation

In `ProductModelWorkspace.tsx.onConfirm` (lines 3169 to 3215), the system estimates real-world metric dimensions from the quadrilateral's width/height ratio. For doors, the calculation anchors to the standardized architectural door height:

```typescript
onConfirm={(corners) => {
  const currentDisplayWidth = canvasRef.current?.clientWidth || canvasDisplaySize.width;
  const currentDisplayHeight = canvasRef.current?.clientHeight || canvasDisplaySize.height;
  const pxCorners = denormalizeCorners(corners, currentDisplayWidth, currentDisplayHeight);
  const { widthRatio, heightRatio } = estimateDimensionsFromCorners(pxCorners);

  if (heightRatio > 0 && widthRatio > 0) {
    const openingAspect = widthRatio / heightRatio;

    if (isDoorProduct) {
      // Doors are height-standardized architectural fenestrations (default: 210cm)
      const templateDefaultH = Number(
        structuralDefinition?.parameters?.find((p) => p.parameterKey === "height")?.defaultValue
      );
      const currentH = Number(heightCm) || (templateDefaultH > 0 ? templateDefaultH : 210);
      // Width is directly proportional to height: width = height * aspect
      const nextW = Math.round(clampNumber(currentH * openingAspect, 50, 500));
      const nextH = currentH;

      setWidthCm(String(nextW));
      setHeightCm(String(nextH));
      setOverlaySize(getOverlaySizeFromDimensions(String(nextW), String(nextH)));
    } else {
      // Standard window dimension estimation
      const currentH = Number(heightCm) || 120;
      const currentW = Number(widthCm) || 120;
      let nextW = currentW;
      let nextH = currentH;

      if (openingAspect >= 1) {
        nextW = Math.round(clampNumber(currentH * openingAspect, 50, 400));
      } else {
        nextH = Math.round(clampNumber(currentW / openingAspect, 50, 400));
      }

      setWidthCm(String(nextW));
      setHeightCm(String(nextH));
      setOverlaySize(getOverlaySizeFromDimensions(String(nextW), String(nextH)));
    }
  }

  // Calculate trapezoidal foreshortening for initial 3D yaw and pitch
  const [p0, p1, p2, p3] = pxCorners;
  const leftH = Math.hypot(p3.x - p0.x, p3.y - p0.y);
  const rightH = Math.hypot(p2.x - p1.x, p2.y - p1.y);
  const topW = Math.hypot(p1.x - p0.x, p1.y - p0.y);
  const bottomW = Math.hypot(p2.x - p3.x, p2.y - p3.y);

  const maxH = Math.max(leftH, rightH, 1);
  const maxW = Math.max(topW, bottomW, 1);
  const deltaH = (leftH - rightH) / maxH;
  const deltaW = (bottomW - topW) / maxW;

  const estimatedYaw = clampNumber(Math.round(deltaH * 45), -35, 35);
  const estimatedPitch = clampNumber(Math.round(deltaW * 35), -25, 25);

  setYaw(estimatedYaw);
  setPitch(estimatedPitch);
  setPerspectiveCorners(corners);
  setShowPerspectivePicker(false);
}}
```

### 5.3 3D Rendering & Edge-to-Edge Camera Projection Parity

The 3D model rendering pipeline in `src/lib/visualization/modelRenderer.ts` operates via `isPlanarFit`:
1. Model Rotation Reset: `this.modelGroup.rotation.set(0, 0, 0)`.
2. Bounding Box Query: `baseBounds = new THREE.Box3().setFromObject(this.modelGroup)`.
3. Camera Distance: `distance = (baseSize.y / 2) / Math.tan(fovRad / 2)`.
4. Frustum Alignment: `this.camera.projectionMatrix.makePerspective(...)`.
5. Angular Tilt: `this.modelGroup.rotation.set(pitchRad, yawRad, 0)`.

Because this logic computes `baseSize` directly from whatever meshes exist inside `this.modelGroup`, **it functions identically for door assemblies as it does for windows**:
- Door stiles, rails, glass infill, and bottom tracks project directly to the four canvas boundaries.
- When yaw or pitch is adjusted via sidebar sliders or initial foreshortening, frame reveals and glass reflections shift in 3D while remaining perfectly framed within the 4-point quadrilateral.

### 5.4 Snapshot Export and Occlusion Compositing Pipeline

In `ProductModelWorkspace.tsx.captureWorkspaceSnapshot`:
1. The door model is rendered offscreen using `modelRenderer.render(yaw, pitch, isPlanar = Boolean(perspectiveCorners))`.
2. When `perspectiveCorners` is present, `drawSnapshotOverlay` passes the unwarped canvas and corner coordinates to `drawPerspectiveWarpedImage(context, offscreen, pixelCorners)`.
3. The 16x16 triangle mesh subdivision warps the door canvas into the exact quadrilateral in the exported snapshot.
4. Auto-detected YOLO objects (such as a chair, couch, or table sitting in front of the door) and manual point/brush occlusion masks are drawn with `destination-in` compositing, rendering realistically in front of the door.

## 7. Definition of Done (Exit Criteria)

The implementation of MS-07 is complete when all of the following verification criteria are satisfied:

1. **Toolbar Button Availability:** When an active product has `productType === "Door"` (or product name/components indicating a door), the "Fit to Opening" button appears in the floating overlay toolbar.
2. **Contextual Instruction Copy:** Clicking "Fit to Opening" for a door product opens `PerspectivePlanePicker` displaying "door opening" in the header subtitle and step guidance messages.
3. **Four-Point Placement and Convex Validation:** The user can drag over a door portal or wall opening to create four ordered corner points, then refine them independently. Non-convex shapes trigger the warning alert.
4. **Door Metric Dimension Estimation:** Confirming the 4 points calculates appropriate real-world door dimensions anchored to standard door height (210cm baseline), preventing aspect-ratio-induced dimensional explosion.
5. **Live DOM Perspective Warping:** The door 3D canvas is warped via CSS `matrix3d()` to fit the 4 selected points with edge-to-edge alignment and zero detached margins.
6. **9-Handle Manipulation:** Dragging any of the 4 corner handles, 4 edge midpoint handles, or 1 center move handle resizes and repositions the door quadrilateral correctly.
7. **Perspective Toolbar Controls:** "Edit Corners", "Free Place", "Flip", "Reset", and "Remove" all operate predictably on door products.
8. **Snapshot Export Parity:** Exporting a consultation snapshot with a planar door overlay applies triangle-mesh perspective warping and preserves foreground object occlusion.
9. **Zero Window Regressions:** All existing window perspective fitting features continue to function identically.
10. **Build & Quality Assurance:**
    - `npm run lint` passes with zero errors.
    - `npx tsc --noEmit` passes with zero type errors.
    - `npm run build` compiles without errors.
    - Zero em-dashes in any code comment or documentation (BAN-PUNCT-01).
    - Zero `any` types in TypeScript (BAN-TYPE-05).

## 8. Risk Assessment & Mitigations

| Identified Risk | Severity | Probability | Mitigation Strategy |
|---|---|---|---|
| Customer selects floor-to-ceiling opening with high aspect ratio, causing width over-scaling | Medium | Low | `clampNumber(currentH * openingAspect, 50, 500)` limits calculated width between 50cm and 500cm, keeping values within realistic fabricator limits. |
| Non-standard door product types (e.g. `product_type = 'Sliding Door'` vs `'Door'`) missed by classification | High | Medium | Predicate checks `productType === "Door"`, `toLowerCase().includes("door")`, and component keys containing `"door"`, ensuring comprehensive matching across catalog items. |
| User draws door opening down to floor, but floor contains occluding rug or threshold strip | Low | Medium | Point-based manual occlusion (`ManualOcclusionPointPicker`) and auto-detected YOLO masks composite cleanly above the door layer. |
| Door 3D model origin not centered, causing perspective offset | Medium | Low | `ProductModelRenderer` establishes `baseBounds` via `Box3.setFromObject` and positions the edge-to-edge camera relative to `baseCenter`, neutralizing non-zero model group offsets. |
