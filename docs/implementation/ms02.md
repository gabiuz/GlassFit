## 1. Problem Context & Motivation

GlassFit's visualization workspace currently places product overlays as axis-aligned rectangles that the user can drag, scale, rotate, and adjust with yaw/pitch controls. This works well when the room photograph is taken roughly straight-on, but real-world customer photos are frequently captured at oblique angles.

When a wall is photographed at an angle, window openings appear as **trapezoids rather than rectangles** due to perspective foreshortening. The right jamb of a window may appear taller than the left, the top rail may appear shorter than the bottom sill, and the opening edges are no longer horizontal or vertical. Placing a rectangular product overlay into such a trapezoidal opening produces a visible mismatch: the overlay does not fill the opening naturally, and the user must wrestle with yaw/pitch sliders to approximate the perspective, which never fully conforms to the actual opening shape.

**Example scenario:** A customer photographs a room with a sliding window opening. The camera is positioned slightly to the left of center. The resulting photo shows the window opening as a quadrilateral where the right edge is approximately 15% taller than the left edge. The top edge angles downward from left to right. No combination of rectangular scaling, rotation, and yaw/pitch adjustment can make a rectangular overlay perfectly fill this trapezoidal opening.

**Approach selected:** Interactive 4-point perspective plane fitting. The user drags a freeform rectangle over the room photo to create four ordered corners, then adjusts those handles independently to match the opening boundary. The system computes a projective homography matrix mapping the rectangular product overlay onto this quadrilateral, then applies a CSS `matrix3d()` transform to warp the overlay to fill the opening exactly. This approach:
- Gives the user direct spatial control through a quick initial selection and independent corner refinement.
- Produces a visually accurate fit regardless of camera angle or perspective distortion.
- Provides approximate width and height estimation from the quadrilateral edge proportions.
- Coexists with the existing free-placement mode (the user can switch between modes).
- Requires no external dependencies (pure TypeScript linear algebra for homography computation).
- Integrates with the existing snapshot compositing pipeline via canvas 2D perspective drawing.

```typescript
  ambientLight?: boolean;
  // ... remaining fields ...
};
```

The `perspectiveFitCorners` array stores four corner positions as **normalized coordinates** (0.0 to 1.0 range relative to workspace canvas dimensions). Normalized storage ensures corner positions remain valid if the workspace container resizes between sessions. The corner order convention is: `[topLeft, topRight, bottomRight, bottomLeft]`.

### 4.2 Perspective Transform Math Module

**File:** `src/lib/visualization/perspectiveTransform.ts` (NEW)

A pure TypeScript module with zero external dependencies implementing projective geometry operations:

**Exported functions:**

| Function | Purpose |
|---|---|
| `computeHomographyMatrix(src, dst)` | Computes a 3x3 homography matrix H mapping four source points to four destination points using the Direct Linear Transform (DLT) algorithm. Solves an 8x8 linear system via Gaussian elimination with partial pivoting. |
| `homographyToCssMatrix3d(corners, elementWidth, elementHeight)` | Converts four target corner positions (pixel coordinates) into a CSS `matrix3d()` string that warps an element of the given dimensions to fill the target quadrilateral. The source rectangle is the element's bounding box `[(0,0), (w,0), (w,h), (0,h)]`. |
| `estimateDimensionsFromCorners(corners)` | Returns `{ widthRatio, heightRatio }` representing the proportional relationship between horizontal and vertical edges of the quadrilateral. The calling code multiplies these ratios against the user-configured cm dimensions. |
| `denormalizeCorners(normalizedCorners, canvasWidth, canvasHeight)` | Converts normalized (0-1) corner coordinates to pixel coordinates for the current canvas dimensions. |
| `normalizeCorners(pixelCorners, canvasWidth, canvasHeight)` | Converts pixel corner coordinates to normalized (0-1) coordinates for persistence. |

**Homography algorithm overview:**

The DLT algorithm maps four source points `(x_s, y_s)` to four destination points `(x_d, y_d)` by solving for the 8 degrees of freedom in the 3x3 projective matrix:

```
| h0  h1  h2 |   | x_s |   | w * x_d |
| h3  h4  h5 | * | y_s | = | w * y_d |
| h6  h7  1  |   |  1  |   |    w    |
```

Each point correspondence produces two linear equations, giving 8 equations for 8 unknowns (h0 through h7, with h8 normalized to 1). The system is solved via Gaussian elimination with partial pivoting for numerical stability.

**CSS `matrix3d` conversion:**

The homography H maps from the element's local coordinate system to the target quadrilateral in the parent's coordinate system. The CSS `matrix3d()` values are derived by expressing H as a 4x4 matrix with the z-row and z-column set to identity, then transposing to match CSS column-major order:

```
matrix3d(h0, h3, 0, h6, h1, h4, 0, h7, 0, 0, 1, 0, h2, h5, 0, 1)
```

The element must have `transform-origin: 0 0` for this mapping to align correctly.

### 4.3 PerspectivePlanePicker Component

**File:** `src/features/visualization/components/PerspectivePlanePicker.tsx` (NEW)

**Props interface:**

```typescript
interface PerspectivePlanePickerProps {
  canvasWidth: number;
  canvasHeight: number;
  backgroundImageUrl: string;
  initialCorners?: QuadrilateralCorners | null;
  onConfirm: (corners: QuadrilateralCorners) => void;
  onCancel: () => void;
}
```

**Component capabilities:**

| Feature | Implementation Detail |
|---|---|
| Instruction banner | Guidance text prompts the user to drag over the opening, then changes to corner-refinement guidance. Door and window flows use the matching opening noun. |
| Point placement | A primary pointer drag renders a live teal rectangle. A release after at least 8 CSS pixels of movement on both axes creates four markers ordered top-left, top-right, bottom-right, bottom-left. Clicks and undersized drags create no points. |
| Quadrilateral preview | After all 4 points are placed, connecting lines form the quadrilateral outline with a semi-transparent cyan fill (approximately 20% opacity) so the user sees the target area against the room photo. |
| Draggable handles | After all 4 points are placed, each corner marker becomes draggable for fine-tuning. Drag uses `pointerdown`/`pointermove`/`pointerup` events (consistent with existing resize handle patterns in `ProductModelWorkspace`). |
| Confirm action | "Confirm" button (visible after 4 points placed) normalizes corner coordinates (0-1 range) and calls `onConfirm(corners)`. |
| Cancel action | "Cancel" button discards all placed points and calls `onCancel()`. |
| Reset action | "Reset Points" clears committed points, the live selection draft, pointer capture, and handle-drag state, then returns to drag selection. |
| Keyboard shortcut | `Escape` key triggers cancel. |

**Rendering structure:**
1. A fixed/absolute-positioned overlay covering the workspace canvas area (matching `ManualMaskPainter` modal pattern).
2. Background layer: the room photograph rendered at workspace dimensions for spatial reference.
3. Interactive SVG overlay at the same dimensions receiving pointer events, rendering corner markers, connecting lines, and quadrilateral fill.
4. Toolbar: positioned at the bottom of the overlay with confirm, cancel, and reset controls.

**Corner marker rendering:**

Each placed corner is an SVG group containing:
- A filled circle (radius 8px, fill `#07b6d3`, stroke white 2px) at the corner position.
- A centered text label showing the corner number (1 through 4).
- On hover: circle scales to 1.2x with a subtle shadow for grab affordance.
- When draggable: `cursor: grab` / `cursor: grabbing` states.

**4.4.2 Perspective-aware overlay transform** (modifying the `motion.div` at line 1679):

When `perspectiveCorners` is active, the overlay rendering switches from the current position/size/rotation style to a CSS `matrix3d()` transform. The key changes:

```tsx
{selectedProduct && (
  <div className="absolute inset-0 pointer-events-none z-20">
    {perspectiveCorners ? (
      // Perspective-fitted overlay: uses matrix3d to warp into quadrilateral
      <div
        ref={overlayBoxRef}
        className="absolute pointer-events-auto"
        style={{
          width: overlaySize.width,
          height: overlaySize.height,
          transformOrigin: "0 0",
          transform: homographyToCssMatrix3d(
            denormalizeCorners(perspectiveCorners, canvasWidth, canvasHeight),
            overlaySize.width,
            overlaySize.height,
          ),
        }}
      >
        {/* Three.js canvas or fallback image renders inside */}
      </div>
    ) : (
      // Existing free-placement overlay (current motion.div with drag, position, rotation)
      <motion.div ...>{/* existing overlay code */}</motion.div>
    )}
  </div>
)}
```

When perspective fitting is active, the free-placement drag, rotation handles, and resize handles are hidden because the overlay position and shape are fully determined by the 4 corner points. The user adjusts the fit by editing the corner positions via the picker.

**4.4.5 Snapshot export integration** (inside `captureWorkspaceSnapshot` and `drawSnapshotOverlay`):

When `perspectiveCorners` is active, `drawSnapshotOverlay` applies the homography as a canvas 2D transform instead of the standard translate/rotate/drawImage path:

```typescript
if (perspectiveCorners) {
  const pixelCorners = denormalizeCorners(perspectiveCorners, canvasBounds.width, canvasBounds.height);
  const H = computeHomographyMatrix(
    [{ x: 0, y: 0 }, { x: width, y: 0 }, { x: width, y: height }, { x: 0, y: height }],
    pixelCorners,
  );

  context.save();
  // Apply perspective transform using canvas setTransform
  // Canvas 2D does not natively support perspective (only affine),
  // so we render the product onto a temporary canvas, subdivide it
  // into a triangle mesh, and draw each triangle with the appropriate
  // affine approximation to simulate perspective warping.
  drawPerspectiveWarpedImage(context, sourceCanvas, pixelCorners);
  context.restore();
} else {
  // Existing translate/rotate/drawImage path
}
```

**Note on canvas 2D perspective limitation:** The HTML Canvas 2D API only supports affine transforms (translate, rotate, scale, skew) via `setTransform()`. True perspective warping requires either:
- (a) Subdividing the source image into a triangle mesh and applying per-triangle affine transforms (texture-mapped quadrilateral rendering), or
- (b) Using an offscreen WebGL canvas to apply the `matrix3d` equivalent as a shader.

The implementation will use approach (a) with a configurable subdivision level (default: 8x8 grid producing 128 triangles) for adequate visual quality without WebGL dependency. A helper function `drawPerspectiveWarpedImage(context, source, targetCorners, subdivisions)` will be added to `perspectiveTransform.ts`.

## 5. Compositing Pipeline Extension

The existing compositing pipeline in `captureWorkspaceSnapshot` processes layers in this order:

| Layer Order | Source | Compositing Strategy |
|---|---|---|
| 1 | Background room photograph | `drawObjectContainImage` onto output canvas |
| 2 | Placed product overlay layers | `drawImage` per placed overlay |
| 3 | Active product overlay (current) | `drawSnapshotOverlay` with rotation, flip, filter, **or perspective warp** |
| 4 | Auto-detected YOLO occlusion masks | `drawMaskedBackgroundLayer` per active object |
| 5 | Manual brush-painted occlusion mask | `drawMaskedBackgroundLayer` with `manualMaskDataUrl` |

Layer 3 is the only layer modified by this feature. When `perspectiveCorners` is present in the snapshot parameters, `drawSnapshotOverlay` uses the triangle-mesh perspective warp path instead of the standard affine translate/rotate/drawImage path. All other layers (background, placed layers, occlusion masks) remain unchanged.

## 8. Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Reverse-direction selection produces an incorrect corner order | Low | Medium | Rectangle bounds are normalized in a pure helper and always emitted as top-left, top-right, bottom-right, bottom-left. All four drag directions have unit coverage. |
| A click or tiny drag creates a degenerate plane | Low | Medium | Selection requires at least 8 client CSS pixels of movement on both axes before corners are committed. |
| CSS `matrix3d` perspective warp causes visual artifacts on low-end mobile GPUs | Low | Medium | The transform is a standard CSS property with broad browser support. The Three.js canvas content is rasterized before warping, avoiding complex shader interactions. |
| Triangle-mesh subdivision produces visible seams in snapshot export | Low | Medium | Default 8x8 subdivision (128 triangles) provides smooth interpolation for typical perspective angles. Subdivision count can be increased for extreme angles. Anti-aliasing via `imageSmoothingEnabled = true` minimizes seam visibility. |
| Homography computation fails for degenerate quadrilaterals (three collinear points) | Low | Low | Gaussian elimination with partial pivoting detects singular matrices. The confirm button is disabled if the computed homography is degenerate, with helper text: "The selected corners do not form a valid quadrilateral." |
| Perspective-fitted overlay dimensions do not match real-world window dimensions | High | Low | Dimension estimation from perspective is inherently approximate without camera calibration. The sidebar width/height inputs remain editable so the user can manually correct dimensions. The feature is a visualization aid, not a measurement instrument. |
| Performance degradation from triangle-mesh rendering in snapshot export | Low | Low | 128 triangles with affine sub-transforms is computationally inexpensive (under 10ms on typical hardware). Only triggered during snapshot capture, not during live DOM rendering. |
