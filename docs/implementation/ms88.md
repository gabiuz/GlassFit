## 1. Required Outcome and Problem Context

After fitting a product to an opening in the uploaded space photo, the customer must be able to choose whether the product shows its **Front (Exterior)** or **Back (Interior)** face. The product must immediately adjust to show the selected physical side, including the correct view of frames, glass, handles, operators, screens, and security grilles.

The same fixture can be photographed from outside a building or inside a room. A successful perspective fit establishes placement, but does not establish which physical side should face the viewer. Requiring the customer to approximate a reverse view through yaw controls makes this choice unclear and can disturb an otherwise correct fit.

This milestone adds an explicit product-facing selection to the existing fitted-product workflow. It follows `IMP-MS87` sequentially. Application implementation, tests and upstream registry updates are authorized by the subsequent implementation request. No migration is required.

## 3. Technical Contract and Architectural Design

### 3.1 User Interface and Post-Fit Workflow

1. After Fit confirmation, show **Product Facing** in the existing Placement accordion for the active fitted product. Keep the setting available while the customer edits that product.
2. Provide two mutually exclusive options: **Front (Exterior)** and **Back (Interior)**. Show the selected option clearly using existing repository control patterns and design tokens.
3. Supporting text: "Choose the side of the product visible in your photo."
4. A newly placed product defaults to Front (Exterior). Confirming Fit preserves its existing facing selection; customers can change the selection immediately afterward.
5. Selecting a face updates the rendered product and its active configuration without reopening Fit, uploading another photo, or requiring a separate Apply action.
6. Controls must support keyboard operation, accessible group and option names, visible focus, and the repository's existing mobile touch-target sizing. The setting must remain reachable in the mobile editor.
7. Use the existing Placement layout and shared UI patterns. Introduce no new palette, dependency, modal workflow, or standalone settings page.

### 3.2 Typed State and Default Semantics

The proposed configuration field is `productFacing`, with exactly two values: `front` and `back`.

| Stored Value | Customer Label | Meaning |
|---|---|---|
| `front` | Front (Exterior) | The exterior face of the product is presented toward the viewer. |
| `back` | Back (Interior) | The interior face of the same product is presented toward the viewer. |
| Absent in a legacy configuration | Front (Exterior) | Preserve the current baseline presentation without introducing an automatic reverse view. |

1. Keep `productFacing` separate from yaw, pitch, image flip, and `addonMountingSide`.
2. Validate the enum at configuration boundaries. Missing legacy data receives the documented default; an invalid explicit value follows existing validation/error handling rather than being guessed from a photograph or yaw angle.
3. Store facing per product instance. Editing one overlay must not change another overlay's facing.
4. Include facing in configuration snapshots, overlay save/edit restoration, duplication, and existing in-session configuration transfer paths.
5. Refit preserves facing and follows MS40 by resetting manual yaw and pitch to zero. Changing facing alone preserves the current manual yaw and pitch values.
6. A newly added product receives the default; a duplicate inherits its source product's facing. An explicit full product reset restores Front (Exterior), while an action that only resets placement preserves facing.

### 3.3 Rendered Face and Assembly Integrity

1. Resolve the selected face as a proper 3D view of the existing assembly. Back (Interior) must reveal actual interior geometry, including interior operator and handle details where modeled.
2. Do not implement facing solely as a CSS horizontal flip, negative image scale, swapped labels, or a change to the visible yaw control.
3. Establish a deterministic exterior baseline for each supported assembly path. Reverse the face through a 180-degree turn about the product's local vertical installation axis, or an equivalent camera-space view, composed separately from user yaw and pitch.
4. Use a stable installation reference and pivot so asymmetric geometry and depth offsets cannot move the product away from its fitted opening when changing sides.
5. Render the host product and its attached screen, grille, handles, operators, and hatches as one spatially coherent assembly. Preserve material assignments and physically correct depth ordering from the selected viewpoint.
6. Do not silently synthesize missing rear hardware or infer front/back metadata from arbitrary mesh names. Assets with incomplete or ambiguous face geometry require explicit asset review during implementation and must not be described as visually verified until inspected.
7. Ensure immediate canvas redraws and later asynchronous model builds use the latest selected face. A stale load must not revert the setting or produce a preview with the opposite face.

### 3.4 Fit, Measurement, and Orientation Invariants

Changing the visible face must preserve:

1. The fitted opening quadrilateral, its established corner order, and the workspace perspective mapping.
2. Installation width and height, measurement provenance, calibration eligibility, dimension confirmation, and quotation dimensions.
3. Overlay translation, visual scale, in-plane rotation, existing flip state, and other independently controlled placement properties.
4. The MS83 structural installation perimeter used for fitting. Sills, handles, and add-ons must not redefine the opening width when the selected face changes.
5. Manual yaw and pitch as relative adjustments to the selected face. Front and Back at zero manual angles must both use the appropriate neutral fitted rendering and canvas normalization behavior.

Front-to-Back-to-Front switching must return to the same placement and configuration without cumulative rotation, scaling, crop drift, or reordered fit corners. An asymmetric fixture is required to verify that reverse-face rendering remains aligned while showing the correct physical left/right relationship.

### 3.5 Add-on Side and Pricing Independence

Product facing describes the side seen by the viewer. Add-on mounting describes where the attachment physically sits on the product. They are independent settings.

1. An exterior-mounted screen or grille remains physically exterior when the viewer selects Back (Interior). Its scene depth and visibility change naturally with the viewpoint.
2. An interior-mounted attachment remains physically interior when the viewer selects Front (Exterior).
3. Preserve MS87 rules: operator hatches and handle-clearance openings depend on physical interior mounting, regardless of the selected viewing face.
4. Switching facing must not change BOM quantities, selected accessories, hatch counts, finish selections, or quotation totals.

### 3.6 Preview and Final Composite Consistency

All existing render consumers must receive the same effective facing selection: the active workspace canvas, stored overlay previews, restored overlays, and the final flattened composite image. The captured output must show the same face that was visible at capture time.

Do not recalculate the photograph's foreground masks or measurement evidence merely because facing changed. Preserve the existing compositing and occlusion pipeline with the newly rendered product image.

## 4. Database Schema and Persistence Architecture

1. Treat facing primarily as active workspace configuration, consistent with `PRD-F24` excluding persistent editable 3D scene sessions.
2. If existing configuration serialization writes visual settings to `ERD-E11.visual_parameter_values`, carry the enum through that existing JSON contract. Do not introduce a new table or column for this setting.
3. The `ERD-E10` flattened snapshot records the selected appearance through its composed image. Historical snapshots and quotations remain unchanged.
4. Configuration serialization must remain backward compatible with records that omit facing. This milestone does not expand restoration guarantees beyond existing supported flows.
5. No schema migration, RLS change, CV API change, new environment variable, or new third-party dependency is planned.

## 8. Scope Boundary

This milestone specifies a post-fit product-facing choice and consistent rendering through existing configuration and composite paths. It does not redesign Fit, add continuous AR tracking, infer camera location from photos, modify product fabrication rules or pricing, change physical add-on mounting, add persistent editable scene sessions, or introduce new dependencies.

Implementation includes the existing workspace, renderer, configuration/session contract, comparison rendering, focused tests and upstream documentation. No new dependency, schema migration or CV change is introduced.


## 9. Implementation and Verification Evidence (November 3, 2026)

### Delivered behavior

- Placement exposes native, mutually exclusive Front (Exterior) and Back (Interior) radio controls after Fit, with the specified hint, keyboard navigation, visible focus and 44px targets.
- `productFacing` is captured per instance and in existing `visualParameterValues` JSON; restoration validates both representations, defaults missing values to front and rejects explicit invalid values. Existing duplication and measurement-transfer spreads preserve facing. New products reset to front, placement reset and refit preserve facing, and refit continues to zero manual angles.
- Rendering recomputes a rigid transform around the structural installation center on every draw, composing the physical local vertical turn before manual angles. The neutral selected face controls camera reference bounds, padding and alpha normalization. Independent horizontal image flips mirror the normalized installation rectangle as well as the pixels, preserving alignment with asymmetric padding in the live view, capture and comparison renders. Facing is deliberately outside asynchronous build inputs so a completed build redraws using current state.
- Overlay capture freezes the selected canvas pixels synchronously before asynchronous background/mask loading. Comparison recipes use the same facing, physical attachments, accessories and removal state, and include facing in the cache fingerprint.

### Face convention and asset review

The existing parametric builder explicitly defines exterior as -Z and interior as +Z (MS80), while the previous workspace camera viewed +Z. These are inconsistent with treating the previous image as exterior. The implementation follows the physical MS80 mounting convention: explicit front uses a PI exterior baseline and back shows +Z. This corrects the former baseline for parametric workspace images, including legacy configurations restored as front. This is a documented compatibility exception to section 3.2's original baseline-preservation assumption, required to keep physical mounting and the customer labels consistent. Historical flattened images are untouched.

Fixed models retain their authored +Z baseline as front. No mesh-name inference or rear-hardware synthesis is added. No production GLB assets are checked into this repository; their authored side and rear geometry remain subject to asset review. Synthetic fixtures establish transform behavior, not the correctness of every uploaded product's face metadata or geometry.
