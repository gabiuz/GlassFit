## 1. Outcome and Scope

Administrators must be able to identify an exact 3D part, assign and review its allowed raw materials and default material, and save the result while keeping the model in view. The Components step must communicate selection, edit state, upload problems, and readiness accurately. This milestone also resolves the save and removal defects found during the audit because a polished material editor cannot be trusted while failed changes can be left behind or removed components can return.

The primary acceptance fixture is the existing 18-part Jalousie product in the normal seven-step wizard. The same shared Components surface must continue to support accessory products in the five-step wizard and Fixed strategy products under MS78. Existing part geometry, material binding semantics, pricing formulas, and customer visualization behavior remain governed by their upstream specifications.

### 1.1 Administrator goals

1. Assign raw materials to a part with fewer decisions and less scanning. Search, category filtering, allowed-material selection, and default designation must form one clear workflow.
2. Keep the 3D model visible while browsing many materials or editing a long inspector form.
3. Make the selected part unmistakable on opaque and transparent meshes, especially glass, and make model, part list, and inspector agree on the same selection.
4. Reach and edit small, overlapping, or transparent parts predictably without relying solely on 3D picking.
5. Know whether changes are unsaved, saving, saved, or failed before leaving the step.

## 3. Experience Contract

### 3.1 Bounded Components workbench

1. Retain the DSD-UI10 60/40 desktop split. Bound the workbench to the available viewport height so inspector content cannot stretch the canvas to the full length of the form. Fit the model within the viewer and keep it visible while the inspector scrolls.
2. In the model side, provide a searchable and groupable part navigator with exact part names, category, selected state, and issue state. Model clicks select the matching navigator entry; navigator selection focuses the exact part and updates the inspector. Provide a reliable list path for small, glass, and overlapping parts.
3. Keep the selected part name and selection count visible in the viewer and inspector. Add Fit Model, Reset Camera, and Front View controls alongside Assembled and Exploded. Preserve camera orientation when changing inspector fields; reset only on explicit request or product change.
4. Compact the page introduction, completed-state upload controls, and status summary so an already configured product reaches the workbench quickly. Retain the upload mode choices behind a clear Add Parts entry point. Make the wizard show completed, current, and upcoming states and provide a discoverable narrow-width step navigation treatment.
5. At narrow widths, stack the workbench without losing the preview. Use a compact pinned model preview while the material chooser is open, with a clear Expand Model action. Keep the save state and primary action visible without covering form controls.

### 3.2 Precise and visible part selection

1. Render a high-contrast silhouette or edge outline for selected geometry that remains visible on transparent glass and pale aluminum. The outline must not depend on material emissive color. Hover prehighlight must be visibly distinct from committed selection.
2. Resolve overlapping hit targets predictably. If a pointer position maps to multiple eligible parts, present a small named part chooser or a deterministic cycle control. Exploded view and the navigator remain alternate exact-selection paths.
3. A selected part has one source of truth for viewer outline, navigator state, inspector header, and accessible announcement. A multiselection explicitly lists the affected part count and names before any batch change.
4. Geometry overlays must preserve existing glass transparency and finish preview. Use the installed Three.js and React Three Fiber stack; do not add a visual library solely for the outline.

### 3.3 Easier raw material assignment

1. Start the inspector with a compact current-binding summary: default material name, code, unit, effective rate, allowed count, and edit state. Put technical codes after human-readable names.
2. A Change Materials action opens one focused chooser with category filters, search, candidate count, clear selected state, and a readable material row. Avoid a short nested scrolling checklist inside another long form. The inspector or chooser owns one scrolling region while the model stays visible.
3. Keep allowed materials and default material separate concepts. Offer an explicit `Allow material` action and `Set as default` action, plus an optional one-action `Allow and set default` path. Exactly one default is required when bindings exist. Fixed-price components retain MS78's optional raw materials behavior.
4. Suggest candidates from the part category and billing unit without silently changing saved mappings. Show unusual category or unit matches as review warnings, not automatic rejection unless an existing domain rule prohibits them.
5. Batch and group assignment must state the exact scope, such as `Apply to 4 selected framing parts`, before committing. Preview the affected names and report per-part results. Keep center-grille one-click assignment from MS72 and explicit accessory bindings from MS77 intact.
6. Group the rest of the inspector into Materials, Dimensions and Pricing, and Client Options. Show only controls relevant to the selected product strategy and part type. Preserve the existing underlying fields and formulas.

### 3.4 Trustworthy state and recovery

1. Define a component editing state contract: `clean`, `dirty`, `saving`, `saved`, and `error`. Show it beside the selected part and in a persistent workbench action area. A successful preview update may say `Preview updated`, but must not be described as saved until persistence succeeds.
2. Save returns an explicit aggregate result and per-part results. Continue waits for persistence and remains on the Components step if any required component fails. Provide the error summary, affected names, and Retry action without discarding valid local edits.
3. Removing an existing component must persist its deletion through an authorized server mutation. Offer Undo until save, distinguish a newly added local part from a persisted part, and verify related bindings and asset references before cleanup. Do not rely on filtering client state as deletion.
4. Derive Ready from saved and valid required components, valid default bindings or fixed-price rules, preview availability, and absence of blocking errors. Show `Needs review` with actionable counts otherwise. The readiness contract must match the Validation step's actual prerequisites.
5. Reject unsupported files with a visible file-level reason. If a GLB cannot be parsed, do not represent placeholder dimensions as verified geometry. Keep retry or remove available and display the failure beside the affected file.
6. Treat the 18-row table as a secondary review surface. Prioritize part name, material name, and actionable status. Group or filter by category and issue; expand a row for driver, ratio, SKU, and other technical detail. Keep a path to inspect every stored field.

## 4. Accessibility, Responsiveness, and Visual Consistency

1. Use semantic buttons or listbox options for part navigation and row selection. Expose `aria-selected`, visible keyboard focus, named remove/select-all actions, and live announcements for selected part, default material, save state, and errors. Expose active view, driver, filter, and ratio options with appropriate pressed or selected semantics.
2. Provide keyboard paths for choosing a file, picking a part, setting allowed and default materials, batch application, save, and continuing. Shift+Click may remain a shortcut but cannot be the only discoverable multiselect method.
3. Replace 9-11px material detail text with readable type and sufficient contrast. Do not rely on color alone to distinguish selected, pending, ready, and error states.
4. Reuse existing GlassFit components, Tailwind tokens, spacing, typography, and brand colors in `src/app/globals.css` and `src/features/admin/`. Do not introduce a new UI library or unrelated palette.
5. Verify desktop, laptop, tablet, phone, 200% browser zoom, and keyboard-only operation. The model and current part identity must remain visible or one explicit action away while a long catalog is being browsed.
