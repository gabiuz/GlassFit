## 1. Outcome and Scope

In architectural glass and aluminum installations, customers frequently customize physical hardware elements on their doors and windows. For example, a client ordering an aluminum swing door may choose between a standard lever handle, a privacy round doorknob, a long stainless pull bar, or a keyless electronic smart lock. Similarly, sliding doors require choices between recessed flush pulls, keyed hook locks, or heavy-duty bottom rollers.

Previously, the GlassFit catalog schema supported only two product classifications:
1. **Standard Architectural Fixture:** Standalone windows, doors, enclosures, and partitions browsable by retail customers in the public catalog (`is_addon = false`).
2. **Add-on Accessory:** Modular framing attachments (insect screens and security grilles) that span entire apertures or host frames (`is_addon = true`).

This binary taxonomy created two critical architectural limitations:
- **No Dedicated Authoring for Sub-Component Hardware:** Hardware items like door handles, knobs, latches, and electric locks could not be authored or registered as discrete modular entities. If a door came with a handle, that handle was permanently baked into the door's 3D `.glb` model, preventing customers from selecting alternative handles or smart lock upgrades.
- **Mismatched Authoring Workflows:** Standard products require a 7-step wizard (including 2D catalog elevation assets and scalar parametric dimension rules). Add-on products follow a 5-step procedural workflow omitting 3D asset uploads and visualization strategies. Hardware accessories require their own distinct authoring flow: they do need a 3D visualization strategy (to define mounting anchors and pivot origins) and 3D components upload, but do NOT require 2D public catalog assets (since they are not browsable as standalone products) or scalar parametric dimension rules (since hardware items have fixed mechanical dimensions).

`IMP-MS74` resolves these bottlenecks by establishing the first phase of the modular hardware accessories subsystem:
- **Third Product Classification ("Accessories"):** Extends the admin upload suite to introduce "Accessories" as a first-class product role alongside Standard Products and Add-on Accessories.
- **Dedicated 5-Step Authoring Wizard Workflow:** Establishes `ACCESSORY_PRODUCT_STEPS` consisting strictly of:
  1. `basic` (Basic Info: Name, description, base price, hardware category, and mounting type).
  2. `strategy` (Visualization: 3D bounding configuration, pivot anchor alignment, and thumbnail orientation).
  3. `components` (Components: Uploading 3D `.glb` mesh parts and assigning hardware finish material bindings).
  4. `validation` (Validation: Isolated 3D test-drive sandbox with orbit, zoom, and finish switching).
  5. `review` (Review & Publish: Final specification verification and catalog activation).
- **Admin Workbench Navigation & Filters (`ProductsContent.tsx`):** Adds a dedicated "Add Accessory" button and a new "Accessories" scope filter tab in the admin products catalog view.
- **Relational Persistence & Catalog Isolation:** Introduces `is_accessory`, `accessory_category`, and `accessory_mounting_type` columns into `public.products`, guaranteeing that accessories remain excluded from the public storefront while being queryable by host fixture part inspectors.

## 3. Non-Negotiable Invariants

1. **Exact 5-Step Authoring Sequence:** Authoring an accessory product must strictly navigate through exactly 5 steps in order: (1) Basic Info, (2) Visualization, (3) Components, (4) Validation, (5) Review & Publish. Step 3 (Assets) and Step 5 (Parameters & Rules) must be completely omitted from the wizard navigation tabs and URL routing.
2. **Public Catalog Isolation Invariant:** Products flagged with `is_accessory = true` must NEVER appear in the public customer-facing storefront (`/product`), public category filters, or search results per `PRD-F1`. They are sub-component attachments queryable only by host fixture assembly builders and administrative configuration drawers.
3. **Hardware Category Domain Enforcement:** The `accessory_category` field must be strictly constrained to the validated domain: `'handle'`, `'lock'`, `'hinge'`, `'roller'`, or `'other'`. Any attempt to persist an unlisted category must be rejected by both Zod schemas and PostgreSQL check constraints.
4. **Zero Em-Dashes:** In strict compliance with `BAN-PUNCT-01`, all UI headings, tooltips, choice card descriptions, validation errors, and code comments must use hyphens, colons, or parentheses. Never use em-dashes.
5. **Strict Type Safety:** Zero usage of `any` across TypeScript interfaces, form state hooks, and database DTOs per `BAN-TYPE-05`.
6. **Design Token Parity:** All UI additions to `BasicInfoSection.tsx`, `ProductSetupWizard.tsx`, and `ProductsContent.tsx` must reuse established Tailwind CSS tokens from `src/app/globals.css` (`rounded-[10px]`, `rounded-[20px]`, `rounded-[25px]`, `border-[#c3c3c3]`, `bg-[#0f1422]`, `text-[#07b6d3]`) per `BAN-UI-09`.

## 4. Technical Design & User Experience Architecture

### 4.1 Wizard Steps Definition (`wizardSteps.ts`)

In `src/lib/admin/products/wizardSteps.ts`, declare the formal step contract for accessories:

```typescript
export const ACCESSORY_PRODUCT_STEPS: WizardStepDefinition[] = [
  { key: "basic", label: "Basic Info", number: 1 },
  { key: "strategy", label: "Visualization", number: 2 },
  { key: "components", label: "Components", number: 3 },
  { key: "validation", label: "Validation", number: 4 },
  { key: "review", label: "Review & Publish", number: 5 },
];

export type ProductRole = "standard" | "addon" | "accessory";

export function getStepsForRole(role: ProductRole): WizardStepDefinition[] {
  switch (role) {
    case "accessory":
      return ACCESSORY_PRODUCT_STEPS;
    case "addon":
      return ADDON_PRODUCT_STEPS;
    case "standard":
    default:
      return STANDARD_PRODUCT_STEPS;
  }
}

export function getStepsForProduct(isAddon?: boolean, isAccessory?: boolean): WizardStepDefinition[] {
  if (isAccessory) return ACCESSORY_PRODUCT_STEPS;
  if (isAddon) return ADDON_PRODUCT_STEPS;
  return STANDARD_PRODUCT_STEPS;
}
```

## 5. Database Schema & Data Models

### 5.1 Supabase PostgreSQL Migration (`019_accessories_product_role.sql`)

```sql
-- Migration: 019_accessories_product_role.sql
-- Description: Adds is_accessory flag, accessory_category, and accessory_mounting_type to public.products

ALTER TABLE public.products
ADD COLUMN IF NOT EXISTS is_accessory BOOLEAN NOT NULL DEFAULT false,
ADD COLUMN IF NOT EXISTS accessory_category VARCHAR(50) NULL,
ADD COLUMN IF NOT EXISTS accessory_mounting_type VARCHAR(50) NULL;

-- Enforce mutual exclusivity: a product cannot be both an add-on and an accessory
ALTER TABLE public.products
DROP CONSTRAINT IF EXISTS check_product_role_mutual_exclusion;

ALTER TABLE public.products
ADD CONSTRAINT check_product_role_mutual_exclusion
CHECK (
  NOT (is_addon = true AND is_accessory = true)
);

-- Enforce valid accessory categories when is_accessory is true
ALTER TABLE public.products
DROP CONSTRAINT IF EXISTS check_valid_accessory_category;

ALTER TABLE public.products
ADD CONSTRAINT check_valid_accessory_category
CHECK (
  (is_accessory = false AND accessory_category IS NULL) OR
  (is_accessory = true AND accessory_category IN ('handle', 'lock', 'hinge', 'roller', 'other'))
);

-- Index for fast filtered catalog queries
CREATE INDEX IF NOT EXISTS idx_products_is_accessory
ON public.products (is_accessory, accessory_category)
WHERE is_accessory = true;

-- Update RLS to ensure accessories follow existing catalog access rules
-- (Public read for active items, admin full access)
```
