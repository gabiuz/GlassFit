**Project:** GlassFit (Web-Based Client-Space Visualization System for Customized Glass & Aluminum)

## 1. Authorized Requirement

The administrator products page currently displays two controls labeled "All categories" and "All Status". They only rotate their chevrons and do not show options or filter rows.

IMP-MS36 must deliver exactly these outcomes:

1. The "All categories" control filters the table using the product type sourced from `public.products.product_type`.
2. The "All Status" control filters the table using the product lifecycle status sourced from `public.products.status`.
3. Both filters work together and continue to work with the existing search field.
4. No product records, status values, or database schemas are mutated by filtering.

The requirement is satisfied only when selecting a product type changes the visible rows by product type and selecting a status changes the visible rows by status.

## 2. Verified Current State

### 2.1 Data flow

`src/features/admin/products/ProductsPage.tsx` selects these fields from `public.products`:

- `product_id`
- `product_name`
- `product_type`
- `description`
- `base_price`
- `status`

It maps the database row to `AdminProductItem` as follows:

| Database field | Client field | Client value |
|---|---|---|
| `product_type` | `type` | Canonical product type string |
| `status = 'Active'` | `status` | `Published` |
| `status = 'Inactive'` | `status` | `Draft` |

The database constraint permits these product types: `Window`, `Door`, `Partition`, `Cabinet`, `Enclosure`, `Railing`, and `Other`. It permits only `Active` and `Inactive` for product status.

### 2.2 UI defect

`src/features/admin/products/ProductsContent.tsx` currently stores `isCategoryOpen` and `isStatusOpen`, but neither state renders a menu. The existing `filtered` memo evaluates only `searchQuery`. The controls therefore provide no product type or status filtering.

### 2.3 Existing architecture to preserve

- `ProductsPage.tsx` remains responsible for the authenticated server-side query and database-to-client status mapping.
- `ProductsContent.tsx` remains responsible for client-side search and filtering of the already loaded rows.
- `productData.ts` remains the typed client model for admin product rows.
- Product creation, editing, duplication, deletion, and routing remain unchanged.

## 4. Functional Contract

### 4.1 Product type dropdown

| Attribute | Required behavior |
|---|---|
| Control label | Default label is `All categories`; after selection it shows the selected product type |
| Source field | `AdminProductItem.type`, mapped from `public.products.product_type` |
| Options | `All categories`, followed by unique non-empty types present in the current `products` array |
| Ordering | Canonical order: Window, Door, Partition, Cabinet, Enclosure, Railing, Other |
| Unknown values | Append unexpected non-empty values after canonical values in locale order so existing data is never hidden from the filter |
| Match rule | Exact equality after trimming; product type values are otherwise preserved for display |
| Default | All product types match |

Only types present in the loaded rows are listed. The dropdown must not offer zero-result canonical values merely because the schema permits them.

### 4.2 Status dropdown

| Attribute | Required behavior |
|---|---|
| Control label | Default label is `All Status`; after selection it shows `Published` or `Draft` |
| Source field | `AdminProductItem.status` |
| Options | `All Status`, `Published`, `Draft` |
| Published match | Client status is `Published`, originating from database status `Active` |
| Draft match | Client status is `Draft`, originating from database status `Inactive` |
| Default | Both statuses match |

The filter operates on the normalized client status. It must not compare `Published` or `Draft` directly against the database values.

### 4.3 Combined filtering

For each product, visibility is defined as:

```text
matchesSearch AND matchesProductType AND matchesStatus
```

Search retains its current fields: product ID, name, type, and description. Search remains case-insensitive and must trim leading and trailing whitespace from the query.

Examples:

| Search | Product type | Status | Expected rows |
|---|---|---|---|
| Empty | All categories | All Status | Every loaded product |
| Empty | Window | All Status | Every Window product |
| Empty | All categories | Draft | Every Draft product |
| `sliding` | Window | Published | Published Window products whose searchable fields contain `sliding` |

### 4.4 Counter and empty states

- The existing counter displays `Showing {filtered.length} of {products.length} products`.
- If `products.length === 0`, retain the catalog-level empty state meaning that no products exist.
- If `products.length > 0` and `filtered.length === 0`, show `No products match the current search and filters.`
- The no-match state provides a `Reset filters` action that clears search, product type, and status.
- Reset restores `All categories`, `All Status`, and all loaded rows.

### 4.5 Interaction and accessibility

The implementation must use either native select controls or an accessible single-selection control built from dependencies already present in `package.json`. It must not create an unstructured clickable `div` menu.

Required interaction behavior:

- Each control has an accessible name that identifies its purpose, such as `Filter products by product type` and `Filter products by status`.
- Current selection is exposed to assistive technology.
- Options can be reached and selected with the keyboard.
- Focus remains visible using the repository's established focus treatment.
- If a custom popup is used, opening one popup closes the other, Escape closes it, focus returns to its trigger, and outside interaction dismisses it.
- Motion respects `prefers-reduced-motion`.
- Product type and status are communicated by text, not color alone.

The existing button dimensions and responsive filter-row layout should be preserved. Visual additions must reuse repository styles and dependencies.

## 5. Technical Design

### 5.1 Filter state

Use `null` for the unfiltered state so no persisted label can collide with the sentinel:

```typescript
type ProductTypeFilter = string | null;
type ProductStatusFilter = AdminProductStatus | null;
```

Initial state:

```typescript
const [selectedType, setSelectedType] = useState<ProductTypeFilter>(null);
const [selectedStatus, setSelectedStatus] = useState<ProductStatusFilter>(null);
```

The existing open-state booleans are removed if native select controls are used. If a custom accessible popup is used, visibility state is retained only for popup behavior.

### 5.2 Pure filter utilities

Create `src/features/admin/products/productFilters.ts` so ordering and predicate behavior can be tested without rendering React.

The module must export typed utilities for:

1. Deriving unique product type options from `AdminProductItem[]`.
2. Filtering products using search, selected product type, and selected status.

The utilities must not use `any`, mutate their input array, access the DOM, or perform database calls.

### 5.3 Product type ordering

`productData.ts` may export the canonical order as a readonly tuple. The derivation utility must:

1. Trim candidate values.
2. Remove empty values.
3. Deduplicate exact canonical values.
4. Return present canonical values in schema order.
5. Append unexpected present values in locale order.

This behavior respects the current schema while remaining deterministic if legacy data is encountered.

### 5.4 Component integration

Update only the filter-related parts of `ProductsContent.tsx`:

- Replace placeholder toggle behavior with selectable product type and status options.
- Feed all three criteria to the pure filter utility through `useMemo`.
- Render the selected labels.
- Keep the counter synchronized.
- Add the no-match reset action.
- Keep row actions and mutation handlers unchanged.

`ProductsPage.tsx` requires no behavior change because it already selects both source fields and normalizes status correctly.

### 5.5 Deletion behavior

Deleting a visible product updates the local `products` array as it does today. Product type options and filtered rows recompute from the new array. If the deleted product was the last row for the selected type, reset only the now-invalid product type selection to `All categories`. Preserve search and status selections. This keeps the selected value valid without restoring the deleted row.

## 7. Acceptance Criteria (`QAD-TC51`)

### AC-1: Product type source

Given loaded products contain Window, Door, and Cabinet values, when the administrator opens the first dropdown, then its selectable values come from `AdminProductItem.type`, and selecting Window shows only Window rows.

### AC-2: Status source

Given loaded products include Published and Draft values, when the administrator selects Draft in the second dropdown, then only client rows normalized from database status `Inactive` remain visible.

### AC-3: Combined criteria

Given product type is Window and status is Published, when the administrator enters a search query, then a row is visible only if it satisfies the search, type, and status predicates.

### AC-4: Default state

Given the page first loads, then the controls display `All categories` and `All Status`, every product matches both filters, and the existing search behavior remains available.

### AC-5: Counter

Given any filter selection, then the counter's first value equals the number of rendered product rows and its second value equals the total loaded product count.

### AC-6: No match and reset

Given products exist but the active criteria produce no matches, then the no-match message is shown and `Reset filters` restores the default filter values, clears the search query, and shows all rows.

### AC-7: Accessibility

Given keyboard-only use, then both controls can receive visible focus and their options can be selected without a pointer. Accessible names distinguish product type from status. If a custom popup is used, Escape closes it and returns focus to the trigger.

### AC-8: Regression safety

Given a filtered result set, then Edit, Duplicate, and Delete continue to target the correct product. Clearing filters after a successful deletion does not restore the deleted local row.
