## 1. Outcome and Problem Context

In architectural glass and aluminum fabrication, secondary attachments such as insect screens and security grilles cannot be treated as generic floating planes. Their spatial viability and physical mounting locations are governed strictly by the kinematics of the host window or door and the physical accessibility of mechanical operating hardware.

This milestone resolves two critical real-world fenestration constraints in the administrative product setup wizard (`/admin/products/[productId]/setup`) and client visualization workspace (`ProductModelWorkspace.tsx`):
1. **Directional Mounting Side Compatibility (Front vs Back vs Both):** Restricting add-on attachment mounting to exterior (Front), interior (Back), or customer-selectable (Both) to prevent physical projection collisions with moving sashes (e.g., awning and casement windows).
2. **Operator-Targeted Screen Hatch Alignment and Dynamic Multi-Instance Generation:** Enabling administrators to bind screen access hatches directly to host product operating mechanisms (e.g., jalousie window operators), automatically cloning and positioning multiple hatches to match each operator in 3D space, and scaling bill-of-materials (BOM) hardware costs accurately.

| Challenge Domain | Physical Conflict / Limitation | Mandated Architectural Solution |
|---|---|---|
| 1. Sash Collision Hazard | Awning Window (opens outward) + Exterior Screen = physical collision on opening travel | Lock screen mounting compatibility strictly to Back (Interior) in Admin Setup |
| 2. Inaccessible Operator Hardware | Jalousie Window with Interior Screen + 2 right operators = screen blocks hand access to cranks | Multi-hatch auto-alignment binding screen hatches to target operator centroids |

### 1.1 Goal 1: Directional Mounting Side Compatibility (Front vs Back vs Both)

#### 1.1.1 The Physical Problem
In Philippine architectural practice:
- **Awning Windows:** The glazed sash is hinged at the head (top) and pushes outward from the sill (bottom). If an insect screen is installed on the exterior (Front), opening the sash pushes directly against the screen frame and wire mesh, causing immediate physical collision, mesh tearing, or mechanical binding. Therefore, awning windows must have insect screens mounted strictly on the interior (Back).
- **Casement Windows:** The sash projects outward laterally on friction stays. Exterior screens block opening travel; insect screens must be mounted on the interior (Back).
- **Hopper Windows:** The sash tilts inward from the top into the room. An interior screen blocks opening travel; screens must be mounted on the exterior (Front).
- **Sliding Windows:** Sash travel remains coplanar within the perimeter frame track. Depending on track extrusion profile (Series 798 / Series 900), screens can be mounted on the exterior track, interior track, or either side (`Both`).
- **Security Grilles:** When intended for burglar resistance, grilles are mounted on the exterior (`Front`). When intended as child safety barriers (such as in high-rise condominiums), grilles are often mounted on the interior (`Back`).

#### 1.1.2 Current System Limitations
1. In `src/features/admin/products/setup/AddonInheritanceSection.tsx`, administrators can only toggle whether an add-on (Screen or Grill) is enabled or disabled and select candidate template IDs. There is no mechanism to specify allowable mounting sides.
2. In the PostgreSQL schema (`public.product_compatible_addons`), the junction record stores only `(parent_product_id, addon_product_id, addon_type, is_default_enabled, display_order)`. It does not record whether the attachment is permitted on the front, back, or both sides.
3. In `parametricProductBuilder.ts`, the z-offset positioning uses a rudimentary `isRearMount` check derived from `addonConfig?.mountPosition === "rear"`. Because this is not persisted in the database per parent-addon relationship, client-space visualization defaults to front placement regardless of window type.

#### 1.1.3 Planned Outcome for Goal 1
- **Admin Configuration:** In `AddonInheritanceSection.tsx`, each compatible add-on entry exposes an accessible **Allowed Mounting Sides** selector with three explicit choices:
  - `Front (Exterior) Only`
  - `Back (Interior) Only`
  - `Both Sides (Customer Selectable)`
  Plus a **Default Mounting Side** selector (`Front` or `Back`) when `Both Sides` is enabled.
- **Physical Feasibility Guardrail:** When the host product is classified as an outward-projecting fixture (`Awning Window` or `Casement Window`), the UI automatically defaults insect screens to `Back (Interior) Only` and displays a high-visibility amber warning banner if the administrator attempts to permit `Front` mounting.
- **Customer Workspace Experience:**
  - If `allowed_sides` is `Back`, the add-on is fixed to the interior plane with an informative badge: `Interior Mount (Back) - Prevents Sash Collision`.
  - If `allowed_sides` is `Front`, the add-on is fixed to the exterior plane.
  - If `allowed_sides` is `Both`, the customer parameter dock renders a segmented control: `[ Exterior (Front) | Interior (Back) ]`.
- **Three.js Scene Graph:** Positions the add-on group along the Z axis relative to the host frame bounding box (`hostBounds.min.z` for rear mount, `hostBounds.max.z` for front mount) with an 8mm standard clearance gap.

### 1.2 Goal 2: Operator-Targeted Screen Hatch Alignment and Dynamic Multi-Instance Generation

#### 1.2.1 The Physical Problem
When an insect screen is installed on the interior side of a window (such as a Jalousie window or Awning window), the window's mechanical operating hardware (crank handles, manual rotators, or cam latches) is located behind or inside the screen perimeter.

To operate the window without having to unlatch and remove the entire screen frame, fabricators construct the screen with an **access hatch** (a small hinged or sliding wicket door built into the screen frame). Occupants open the hatch, reach through the aperture, turn the operator crank to adjust the louvers, and re-latch the hatch.

However, fenestration units frequently feature **multiple operators**:
- A standard Philippine Series 798 or heavy-duty jalousie window exceeding 1000mm in height typically has **2 separate window operators** mounted on the right stile (e.g., lower operator controlling the bottom bank of 8 louvers, upper operator controlling the top bank of 8 louvers).
- Very tall commercial jalousies or multi-bay units can feature **3 or more operators**, or operators split between left and right stiles.

#### 1.2.2 Current System Limitations
1. In MS78 and migration `022_nullable_position_options.sql`, GlassFit established the constituent mesh screen component `screen_access_hatch` with bilateral Left vs Right handing toggles (`allowHorizontalToggle: true`, `defaultHorizontal: "right"`).
2. However, this component exists only as a single discrete part within the add-on screen product. It is positioned at a fixed modeled offset or static horizontal position.
3. The system cannot currently associate the screen hatch with the host product's mechanical parts. If a jalousie window has 2 operators, applying the screen add-on renders only 1 hatch, leaving the second operator unreachable.
4. Administrators cannot select which constituent parts of the host window represent the operators that need hatch alignment.

#### 1.2.3 Planned Outcome for Goal 2
- **Admin Target Part Assignment:** In the admin setup wizard (Step 3 Components or Step 4 Addon Setup), when a screen add-on with a hatch component is linked to a host product:
  - The administrator can designate the specific host components that serve as **Hatch Target Parts** (e.g., `operator_lower`, `operator_upper`).
  - In the split-screen 3D viewport, selecting an operator part highlights it in cyan with a targeting crosshair, displaying its calculated 3D center coordinates.
- **Automated Dynamic Multi-Instance Generation:**
  - When the screen add-on is mounted in the 3D canvas (admin validation or customer workspace), the assembly engine (`parametricProductBuilder.ts`) inspects the host product definition for assigned hatch targets.
  - If $N$ operator parts are bound ($N \ge 1$), the engine automatically clones and generates **$N$ distinct access hatches** (one per operator).
  - Each hatch's $(X, Y)$ coordinate is aligned directly to the 3D bounding box centroid $(X_i, Y_i)$ of its respective operator part, offset to rest coplanar on the screen frame plane ($Z_{screen}$).
  - Handing is derived automatically from the operator's lateral coordinate: if an operator is on the right stile ($X_i > 0$), the corresponding hatch mirrors to right handing; if on the left stile ($X_i < 0$), it mirrors to left handing.
- **Parametric BOM Scaling:**
  - The parametric pricing engine (`pricingEngine.ts` and `addonPricingEngine.ts`) scales hatch hardware piece counts (wicket latches, hinges, friction clips) by $N$.
  - The frozen quotation item records: `hatch_count: N` and `hatch_targets: [...]`.
- **Consultation PDF Disclosure:**
  - The downloadable consultation PDF specifications column displays:
    `Add-on: Insect Screen (Interior Mount / Back, with 2x Operator Access Hatches)`.
    This provides explicit shop-drawing instructions for fabricators during cutting and screen assembly.

## 3. Detailed Experience and Architectural Contract

### 3.1 Directional Mounting Side Configuration (Admin UI)

In Step 4 / Step 5 (`AddonInheritanceSection.tsx`), each enabled compatible add-on card includes an interactive **Mounting Compatibility Section**:

| Control Surface Element | Type and Semantics | Default Value / Trigger Behavior |
|---|---|---|
| Enable Add-on Toggle | Boolean checkbox (`hasScreen` / `hasGrill`) | Checked when compatible bindings exist |
| Mounting Side Radio Group | Radio options: `Front (Exterior) Only`, `Back (Interior) Only`, `Both Sides` | Defaults to `Back` for Awning/Casement; `Both` for Sliding |
| Default Side Radio Group | Radio options: `Front`, `Back` (rendered only when `Both Sides` selected) | Defaults to `Back` |
| Architectural Conflict Notice | Contextual amber alert banner | Triggers if `Front` or `Both` is selected on outward-opening sashes |
| Compatible Templates List | Multi-select template cards with price badges | At least one template required when enabled |

1. **Option Values:**
   - `front`: The add-on can only be installed on the exterior face of the fixture.
   - `back`: The add-on can only be installed on the interior face of the fixture.
   - `both`: The add-on can be installed on either face. The customer can toggle between Front and Back during 3D visualization.
2. **Default Side Selection:** When `both` is selected, an auxiliary radio toggle appears:
   `Default Side: [ Front (Exterior) | Back (Interior) ]`.
3. **Physical Conflict Guardrail:**
   - The UI evaluates host product classification:
     ```typescript
     const isOutwardProjecting = hostProductType === "Awning Window" || hostProductType === "Casement Window";
     ```
   - If `isOutwardProjecting` is true and the add-on is of type `screen`:
     - The UI automatically selects `back` (Interior) by default.
     - If the administrator clicks `front` or `both`, an amber alert banner displays:
       `Physical Collision Warning: Awning and casement sashes project outward when opened. Exterior screens will be struck by the opening sash. Interior (Back) mounting is recommended.`
     - Publishing validation flags this as an architectural notice, requiring administrator confirmation.

### 3.2 Operator-Targeted Screen Hatch Alignment (Admin UI)

When an enabled screen add-on template contains a constituent hatch component (detected via `component_key ILIKE '%hatch%'` or `presentation_category = 'Hardware'` with removable or handing options), the setup wizard activates the **Hatch Operator Alignment Dock**:

| Interface Component | Display Content / Role | Behavioral Interaction |
|---|---|---|
| Target Component Checklist | List of candidate host hardware parts with component keys and Y elevation | Checkbox selection binds/unbinds part key to `hatch_target_component_keys` |
| 3D Viewport Target Crosshair | High-contrast reticle and bounding box on selected operator meshes | Canvas mesh click toggles component in checklist |
| Auto-Detection Suggestion | Identifies parts matching `*operator*`, `*crank*`, `*latch*` | Pre-selects operator targets for administrator review |
| Dynamic Instance Indicator | Counter badge showing number of active operator targets | Explains: `$N$ target operators selected; $N$ hatches will be generated` |

1. **Part Filter:** Populates exclusively with constituent parts of the host product from Step 3 (`product_components`), filtering for hardware, operators, latches, or custom components.
2. **Interactive 3D Picking:** Clicking an operator part in the split-screen Three.js canvas toggles its selection in the target list. Selected parts display a cyan bounding silhouette and a target crosshair.
3. **Automated Name Suggestion:** The system auto-suggests operator parts whose keys or filenames match `*operator*`, `*crank*`, `*handle*`, `*latch*`, or `*rotator*`.
4. **Target Count Invariant:**
   - If 0 targets are selected: The screen displays its default single hatch at the modeled base coordinates.
   - If 1 target is selected: The screen positions its single hatch directly aligned with that operator.
   - If $N \ge 2$ targets are selected: The screen dynamically clones the hatch component so that exactly $N$ hatches appear, each aligned with one target operator.

### 3.3 Customer Visualization Workspace & Scene Composition

In `ProductModelWorkspace.tsx`:

1. **Mounting Side Controller:**
   - When the customer activates an add-on (Screen or Grill):
     - If `allowed_sides === 'back'`: Renders a compact badge beside the add-on toggle:
       `Interior Mount (Back)`. The side toggle is locked.
     - If `allowed_sides === 'front'`: Renders badge: `Exterior Mount (Front)`. The side toggle is locked.
     - If `allowed_sides === 'both'`: Renders an interactive segmented control:
       `[ Exterior (Front) | Interior (Back) ]`, defaulting to `default_side`.
2. **Three.js Z-Axis Positioning:**
   - The assembly builder computes the host product world bounding box:
     ```typescript
     const hostBounds = new THREE.Box3().setFromObject(group);
     const clearanceMeters = 0.008; // 8mm architectural mounting clearance
     ```
   - Front Placement:
     $$\text{Target } Z = \text{hostBounds.max.z} - \text{addonBounds.min.z} + \text{clearanceMeters}$$
   - Back Placement:
     $$\text{Target } Z = \text{hostBounds.min.z} - \text{addonBounds.max.z} - \text{clearanceMeters}$$
3. **Multi-Hatch Alignment & Cloning Algorithm:**
   - For a screen add-on with hatch component `H` and host target operators $T_1, T_2, \dots, T_N$:
     1. Locate target meshes $M(T_i)$ within the host product group.
     2. For each $i \in \{1, \dots, N\}$:
        - Compute target centroid in host coordinate space:
          $$\vec{C}_i = \text{centroid}(M(T_i)) = (X_i, Y_i, Z_i)$$
        - Clone the hatch mesh template $H$.
        - Compute lateral handing:
          $$\text{Handing}_i = \begin{cases} \text{"right"} & \text{if } X_i \ge 0 \\ \text{"left"} & \text{if } X_i < 0 \end{cases}$$
        - Apply bilateral mesh reflection if $\text{Handing}_i$ differs from the template's modeled handing (per `IMP-MS78`).
        - Position cloned hatch at $(X_i, Y_i, Z_{\text{screen}})$.
        - Assign unique identification: `clone.userData.hatchIndex = i`, `clone.userData.targetComponentKey = T_i`.
        - Add clone to the screen add-on sub-assembly.
     3. Remove or hide the default unaligned hatch template from the sub-assembly to prevent orphan meshes.

### 3.4 Pricing and BOM Engine Contract

1. **Hardware Quantity Multiplier:**
   - Standard screen components (perimeter frame extrusions, wire mesh, spline rubber) scale with aperture dimensions (1D linear meters and 2D area).
   - Hatch constituent hardware (wicket latch, pivot hinges, corner keys) are defined with `dimension_binding = 'FIXED'` and `base_quantity = Q_base`.
   - When $N$ operator targets are bound, the effective quantity for hatch hardware components evaluates to:
     $$Q_{\text{effective}} = Q_{\text{base}} \times N$$
2. **Quotation Snapshot Itemization (`quotation_items.pricing_details`):**
   ```json
   {
     "addon": {
       "type": "screen",
       "name": "Series 798 Insect Screen with Operator Hatches",
       "mounting_side": "back",
       "allowed_sides": "back",
       "hatch_count": 2,
       "hatch_target_keys": ["comp_operator_lower", "comp_operator_upper"],
       "hatch_hardware_multiplier": 2,
       "unit_price": 1750.00
     }
   }
   ```
3. **Consultation PDF Specification Line:**
   - Formats the description for fabricator review:
     `Add-on: Insect Screen (Interior Mount / Back, with 2x Operator Access Hatches)`
   - Discloses mounting side and operator alignment without leaking internal BOM raw material unit costs or scrap allowances (preserving `BAN-SPEC-02` and `PRD-F11`).

## 4. Database Schema and Migration Design

A dedicated reversible migration file `supabase/migrations/024_addon_mounting_side_and_hatch_alignment.sql` establishes the schema extensions.

```sql
-- Migration: 024_addon_mounting_side_and_hatch_alignment.sql
-- Description: Add allowed mounting sides and operator hatch alignment to product_compatible_addons
-- Upstream Traceability: PRD-F5, PRD-F14, SDD-C4, SDD-C9, ERD-E3, IMP-MS80

-- 1. Extend product_compatible_addons with mounting side constraints
ALTER TABLE public.product_compatible_addons
ADD COLUMN IF NOT EXISTS allowed_sides varchar(10) NOT NULL DEFAULT 'both'
CHECK (allowed_sides IN ('front', 'back', 'both'));

ALTER TABLE public.product_compatible_addons
ADD COLUMN IF NOT EXISTS default_side varchar(10) NOT NULL DEFAULT 'back'
CHECK (default_side IN ('front', 'back'));

-- 2. Add hatch operator alignment columns
ALTER TABLE public.product_compatible_addons
ADD COLUMN IF NOT EXISTS hatch_target_component_keys text[] DEFAULT NULL;

ALTER TABLE public.product_compatible_addons
ADD COLUMN IF NOT EXISTS hatch_alignment_config jsonb DEFAULT NULL;

-- 3. Update existing records: default awning and casement screens to 'back' only
UPDATE public.product_compatible_addons pca
SET allowed_sides = 'back', default_side = 'back'
FROM public.products p
WHERE pca.parent_product_id = p.product_id
  AND p.product_type IN ('Awning Window', 'Casement Window')
  AND pca.addon_type = 'screen';

-- 4. Comment on columns for schema governance
COMMENT ON COLUMN public.product_compatible_addons.allowed_sides IS 
'Permitted mounting locations: front (exterior only), back (interior only), or both (customer selectable)';

COMMENT ON COLUMN public.product_compatible_addons.hatch_target_component_keys IS 
'Array of host product component keys that screen access hatches automatically align to';
```

### Reversible Rollback Script (Down Migration)
```sql
-- Down Migration for 024_addon_mounting_side_and_hatch_alignment.sql
ALTER TABLE public.product_compatible_addons DROP COLUMN IF EXISTS hatch_alignment_config;
ALTER TABLE public.product_compatible_addons DROP COLUMN IF EXISTS hatch_target_component_keys;
ALTER TABLE public.product_compatible_addons DROP COLUMN IF EXISTS default_side;
ALTER TABLE public.product_compatible_addons DROP COLUMN IF EXISTS allowed_sides;
```
