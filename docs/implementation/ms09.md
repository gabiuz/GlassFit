## 1. Objective and Current State

The Product Details page (`src/features/product-details/components/ProductDetails.tsx`) exposes aluminum finish, glass type, width, height, thickness, and quantity controls. The current 3D preview receives only `glbUrl`, so `ProductModel3D` continues to use its default white aluminum and clear glass materials. Width, height, thickness, and quantity have no preview effect.

IMP-MS09 binds every Design Specs control to the 3D preview:

1. Aluminum finish changes the frame material.
2. Glass type changes the optical glass mode.
3. Glass color tints the selected optical glass mode.
4. Glass thickness changes the optical thickness properties of the glass material.
5. Width and height, when both are valid, change the preview aspect ratio.
6. Quantity renders up to five arranged copies and reports any remaining count with a badge.

This is a visual configuration preview. Pricing and engineering-valid product sizing remain outside this implementation.

## 2. Business Rules Source and Scope

### 2.1 Reviewed Source

The R.R.D. rules document was reviewed in full. It defines:

- Standard aluminum finishes: White and Analok.
- Twenty-two special or powder-coated aluminum finishes.
- Glass types: Regular, Frosted, Mirror, Tempered, and Reflective.
- Glass colors: Clear, Bronze, Silver, and Blue.
- Glass thicknesses: 6 mm, 8 mm, and 12 mm. The 6 mm option is the default. The 3 mm option is explicitly excluded.
- Pricing classifications and multipliers for future pricing integration.
- Primary product categories: Windows, Doors, and Cabinets.

The R.R.D. document does not define per-product dimensional limits, per-product finish restrictions, or quantity limits. IMP-MS09 therefore must not invent structural or commercial constraints. It uses deterministic technical validation for safe preview rendering and applies the R.R.D. option catalog uniformly to Window, Door, and Cabinet products.

### 2.2 Supported Product Categories

The R.R.D. option catalog applies to these database product types:

```typescript
export type RrdSupportedProductType = "Window" | "Door" | "Cabinet";
```

For `Partition`, `Enclosure`, `Railing`, or `Other`, the existing product page remains usable, but IMP-MS09 configuration controls are not shown until an approved business-rules source defines their options. The 2D and 3D product inspection controls remain available.

### 2.3 Pricing Boundary

The source document includes special-color, premium-glass, and thickness pricing rules. IMP-MS09 records pricing classification metadata in its option definitions but does not recalculate `base_price`, BOM values, quotations, or estimates. Those calculations remain governed by PRD-F10 and the pricing subsystem.

- Analok, copper, champagne, and coffee finishes: `metalness: 0.55`, `roughness: 0.26`, `clearcoat: 0.45`, `clearcoatRoughness: 0.20`.
- Black, white, green, and blue powder-coated finishes: `metalness: 0.20`, `roughness: 0.30`, `clearcoat: 0.50`, `clearcoatRoughness: 0.20`.

### 5.2 Glass Type Mapping

| ID | User Label | R.R.D. Pricing Class | `GlassAppearanceMode` |
|---|---|---|---|
| `regular` | Regular | Standard | `clear` |
| `frosted` | Frosted | Standard | `frosted` |
| `mirror` | Mirror | Standard | `reflective` |
| `tempered` | Tempered | Premium | `clear` |
| `reflective` | Reflective | Premium | `reflective` |

Tempered glass maps to `clear` because tempering is a safety treatment and does not inherently make clear glass opaque or reflective. Pricing metadata remains available but is not used by IMP-MS09.

### 5.3 Glass Color Mapping

```typescript
export type GlassColorKey = "clear" | "bronze" | "silver" | "blue";
```

| ID | User Label | R.R.D. Pricing Class | Preview Tint |
|---|---|---|---|
| `clear` | Clear | Standard | `#F0F5F7` |
| `bronze` | Bronze | Standard | `#8B6F47` |
| `silver` | Silver | Premium | `#AEBCC5` |
| `blue` | Blue | Premium | `#7FA9C4` |

Glass color is independent of glass type. The selected tint is applied to the material produced by the mapped `GlassAppearanceMode`.

### 5.4 Glass Thickness Mapping

```typescript
export type GlassThicknessMm = 6 | 8 | 12;
```

The Product Details thickness control becomes a three-option selector. It must not remain an unrestricted numeric input, and 3 mm must not be offered.

Thickness is represented optically rather than by changing mesh geometry:

- `MeshPhysicalMaterial.thickness` is set to `thicknessMm / 1000`.
- `attenuationColor` uses the selected glass color.
- `attenuationDistance` is `2.4` for 6 mm, `1.8` for 8 mm, and `1.2` for 12 mm.
- Frame, hardware, and GLB geometry are not rescaled by thickness.

This produces deterministic visible absorption differences while avoiding unsafe assumptions about each GLB glass mesh's local depth axis.

### 5.5 Total Mapping Functions and Defaults

All UI state must use stable IDs, not display labels.

```typescript
export const DEFAULT_PRODUCT_PREVIEW_CONFIGURATION = {
  aluminumFinish: "white",
  glassType: "regular",
  glassColor: "clear",
  glassThicknessMm: 6,
  quantity: 1,
} as const;
```

Required functions:

```typescript
export function isRrdSupportedProductType(
  productType: string,
): productType is RrdSupportedProductType;

export function getAvailableFinishOptions(
  productType: RrdSupportedProductType,
): readonly FinishOption[];

export function getAvailableGlassTypeOptions(
  productType: RrdSupportedProductType,
): readonly GlassTypeOption[];

export function mapGlassTypeToAppearanceMode(
  glassType: GlassTypeKey,
): GlassAppearanceMode;
```

These functions must be exhaustive over their union types. They must not silently map unknown strings to arbitrary materials. Runtime values outside the defined catalog return a typed validation failure before rendering.

## 6. Product Details State and UI Behavior

### 6.1 Initial State

For Window, Door, and Cabinet products:

- Aluminum finish: White.
- Glass type: Regular.
- Glass color: Clear.
- Thickness: 6 mm.
- Width and height: empty.
- Quantity: 1.

Initial selection is derived from `DEFAULT_PRODUCT_PREVIEW_CONFIGURATION`, never from array position or a display label.

### 6.2 Controls

The existing visual language, layout, tokens, and shared components must be reused. The Design Specs panel contains:

1. Aluminum Finish option list using a color swatch derived from `previewHex`. Existing icon files may be used only when they correspond to the selected R.R.D. finish.
2. Glass Type segmented options.
3. Glass Color segmented options with tint swatches.
4. Thickness segmented options: 6 mm, 8 mm, and 12 mm.
5. Width and Height numeric inputs in centimeters.
6. Quantity integer stepper.

Every button must expose `aria-pressed`. Inputs must have explicit `label` associations, validation messages must use `aria-describedby`, and the overflow quantity badge must be screen-reader accessible.

### 6.3 Dimension Input State

Width and height are stored as strings while the user edits them. This prevents an empty field from becoming `NaN` or being forced immediately to zero.

A dimension pair is valid when:

- Both values parse to finite numbers greater than zero.
- The width-to-height ratio is between `0.1` and `10`, inclusive. This is a technical viewport guard, not a structural constraint.

Behavior:

- Both fields empty: render the GLB at its source aspect ratio.
- Only one field entered: retain the source aspect ratio and show `Enter both width and height to preview proportions.`
- Both fields valid: update the preview after 150 ms.
- Invalid or out-of-range ratio: retain the last valid preview transform and show a validation message.

The debounce must use a timer-backed `useEffect` or a reusable `useDebouncedValue` hook. `useMemo` must not be described or used as a debounce mechanism.

### 6.4 Quantity Input State

Quantity normalization is deterministic:

```typescript
export const MIN_PRODUCT_QUANTITY = 1;
export const MAX_PRODUCT_QUANTITY = 999;
export const MAX_VISIBLE_PREVIEW_MODELS = 5;
```

- Empty, non-finite, fractional, or lower-than-minimum input normalizes to 1 on blur.
- Fractional input is rounded down before clamping.
- Values greater than 999 normalize to 999.
- Increment and decrement buttons always operate on the normalized integer.
- Only `Math.min(quantity, 5)` models are rendered.
- If quantity exceeds 5, the badge text is `+${quantity - 5} more`.

The 999 limit is a UI safety bound, not a business or manufacturing limit.

## 7. Deterministic 3D Preview Behavior

### 7.1 Prop Contract

```typescript
interface ProductModel3DProps {
  glbUrl: string;
  aluminumFinish: AluminumFinishKey;
  glassAppearance: GlassAppearanceMode;
  glassColor: GlassColorKey;
  glassThicknessMm: GlassThicknessMm;
  widthCm?: number;
  heightCm?: number;
  quantity: number;
}
```

### 7.2 Material Application

`createMaterialPalette` and `applyPresentationMaterials` must accept a typed options object rather than additional positional strings:

```typescript
interface MaterialPaletteOptions {
  aluminumFinish: AluminumFinishKey;
  glassAppearance: GlassAppearanceMode;
  glassColor: GlassColorKey;
  glassThicknessMm: GlassThicknessMm;
}
```

Existing callers are migrated to explicit defaults so the visualization workspace retains its current behavior. The frame presentation comes from the aluminum catalog. Glass appearance, tint, and optical thickness are applied only to meshes classified as Glass.

### 7.3 Dimension Transform

The preview assumes catalog GLBs follow the existing authoring convention:

- Local X axis: product width.
- Local Y axis: product height.
- Local Z axis: product depth.

For a source bounding-box size `(sourceWidth, sourceHeight, sourceDepth)` and valid dimensions `(widthCm, heightCm)`:

1. Compute `targetRatio = widthCm / heightCm`.
2. If `targetRatio >= 1`, set `targetWidth = 2` and `targetHeight = 2 / targetRatio`.
3. Otherwise, set `targetWidth = 2 * targetRatio` and `targetHeight = 2`.
4. Set `scaleX = targetWidth / sourceWidth`.
5. Set `scaleY = targetHeight / sourceHeight`.
6. Set `scaleZ = Math.min(scaleX, scaleY)` to avoid stretching depth independently.
7. Recenter with the scaled source-box center.

If dimensions are absent, apply the current uniform normalization `2 / max(sourceWidth, sourceHeight, sourceDepth)`.

The transform calculation belongs in `productPreviewConfiguration.ts` as a pure function and must reject empty or degenerate bounding boxes.

### 7.4 Multi-Model Arrangement

Each visible model must be a distinct `Object3D` hierarchy. A single Three.js object must never be attached to multiple parents.

Implementation sequence:

1. Clone the loaded GLB once and apply the selected materials to create a prepared model.
2. Create one deep `Object3D` clone of the prepared model for each visible instance. Geometry and immutable material references may be shared.
3. Apply the dimension transform to each instance root.
4. Let `modelWidth` be the transformed bounding-box width.
5. Position instance `i` at `(i - (visibleCount - 1) / 2) * modelWidth * 1.15` on X.
6. Compute the complete group bounding box.
7. Uniformly scale and center the group so its maximum dimension fits the existing 2-unit preview envelope.

The camera position and FOV remain unchanged. This prevents camera-state jumps when quantity changes.

### 7.5 Overflow Badge

`ProductModel3D` returns a relative wrapper containing the `Canvas` and, when needed, an absolutely positioned DOM badge. The badge is not rendered as a Three.js primitive and does not require Drei `Html`.

### 7.6 Resource Lifecycle

- `useGLTF` cached geometry must not be disposed by this component.
- Materials created by `applyPresentationMaterials` must be disposed when the prepared model is replaced or unmounted.
- Instance clones share the prepared model's geometry and material references and must not dispose them individually.
- Dimension and quantity changes must not reload the GLB.

## 8. Error and Fallback Behavior

| Condition | Required Behavior |
|---|---|
| Product type is unsupported by R.R.D. | Hide configuration controls; retain ordinary product inspection |
| `preview_glb_url` is absent | Hide the 3D toggle; configuration state has no rendering side effects |
| GLB load fails | Show the existing preview area with a concise failure message and preserve the 2D toggle |
| Unknown configuration ID reaches runtime boundary | Reject it with a typed validation result; do not silently select another option |
| Bounding box is empty or degenerate | Show the GLB failure state and avoid division by zero |
| One dimension is missing | Preserve source proportions and request both values |
| Both dimensions are invalid | Preserve the last valid transform and display validation feedback |
| Quantity exceeds five | Render five instances and show the exact remaining count |

## 11. Risks and Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Preview colors differ from physical powder-coat samples | Medium | Label colors as screen approximations; preserve exact R.R.D. names and codes; replace hex values only when calibrated swatches are approved |
| Non-uniform width and height scaling distorts frame profiles | Medium | State that Product Details is an approximate proportion preview; preserve true parametric rebuilding for the visualization workspace |
| GLB axes do not follow X-width and Y-height convention | Medium | Treat axis convention as an asset requirement and fail acceptance for nonconforming preview GLBs |
| Material classification misses glass meshes | Medium | Retain the existing classification hierarchy and include representative GLB manual tests |
| Many instances increase render cost | Low | Render no more than five instances and share geometry and material references |
| Unsupported product categories lack approved options | Low | Hide configuration controls instead of inventing rules |
| R.R.D. pricing metadata is mistaken for live pricing | Medium | Keep pricing calculations explicitly out of scope and do not mutate the displayed base price |
