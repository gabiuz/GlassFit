In the GlassFit administrator catalog authoring wizard (`/admin/products/[id]/setup`), fenestration products (such as sliding windows, awning windows, casement doors, and shower enclosures) are configured with parametric dimensions and structural assembly rules. Currently, width and height parameters enforce rigid maximum bounds (3600mm and 3000mm), restricting large commercial storefronts, curtain walls, and custom panoramic openings. Furthermore, structural logic rules only support discrete "WHEN / THEN" relational comparisons (`>=`, `<=`, `==`). When an administrator needs a part (such as a horizontal mullion, glazing bead, or hinge) to scale linearly with dimension growth (e.g., adding 1 intermediate horizontal mullion for every 500mm of added height), they are forced to author dozens of repetitive, brittle rules for each discrete step. `IMP-MS43` eliminates the maximum dimension ceiling on width and height parameters while preserving their minimum and default constraints, and introduces first-class incremental step-loop logic rules ("FOR EVERY [step] mm ADD [quantity] parts") to the admin setup builder and structural resolution engine.

## 1. Authorized Requirement

In the GlassFit platform, custom glass and aluminum architectural fixtures are manufactured to order based on precise client opening measurements. The system is designed to accommodate both standard residential openings and expansive custom architectural apertures (such as commercial sliding window walls, expansive patio doors, and floor-to-ceiling glass enclosures).

### 1.1 Current Behavior & Bottlenecks

1. **Artificial Maximum Ceilings on Width and Height:**
   - In `src/features/admin/products/setup/ParametersAndRulesSection.tsx` (lines 58 to 83), default standard parameters for fenestration products hardcode `maximum_value: 3600` for `width` and `maximum_value: 3000` for `height`.
   - The parameter editing interface renders an editable number input for `Max` across all parameters.
   - When an administrator configures products designed for continuous or modular spans (e.g., multi-track sliding windows, storefronts, and commercial enclosures), they are forced to enter an arbitrary ceiling or encounter validation limits.
   - In reality, fabricators build customized spans with no strict theoretical upper limit as long as structural mullions and additional leaves are added incrementally.

2. **Repetitive, Discrete-Only Logic Rules ("WHEN / THEN"):**
   - In `ParametersAndRulesSection.tsx` (lines 456 to 524) and `structuralResolver.ts` (lines 44 to 51, 101 to 132), logic rules only support scalar relational operators (`>=`, `<=`, `==`, `>`, `<`).
   - If an awning window or high-span sliding window requires 1 additional horizontal reinforcement mullion for every 500mm of height added above the baseline, the administrator must create multiple manual rules:
     - Rule 1: `WHEN height >= 1500 THEN component mullion-bar set_quantity 1`
     - Rule 2: `WHEN height >= 2000 THEN component mullion-bar set_quantity 2`
     - Rule 3: `WHEN height >= 2500 THEN component mullion-bar set_quantity 3`
     - Rule 4: `WHEN height >= 3000 THEN component mullion-bar set_quantity 4`
     - Rule 5: `WHEN height >= 3500 THEN component mullion-bar set_quantity 5`
   - This approach is tedious, error-prone, violates DRY (Don't Repeat Yourself) principles, and completely fails if a client configures a dimension beyond the highest manually authored rule.

### 1.2 Required Behavior

`IMP-MS43` establishes two fundamental enhancements to the parametric product catalog and structural rule engine:

1. **Unconstrained Width and Height Dimension Bounds:**
   - In the administrator product creation/editing workflow (`Step 5: Parameters & Rules`), the `maximum_value` constraint for `width` and `height` parameters must be removed.
   - There must be no upper maximum ceiling for `width` and `height` (`maximum_value = null`), allowing infinite dimensional flexibility for custom fabrications.
   - The minimum constraint (`minimum_value`) and default starting value (`default_value`) must be strictly retained to prevent zero, negative, or structurally impossible initial configurations.
   - In the parameter table UI, the `Max` input column for width and height must reflect the unconstrained state (displaying "None / No Max" badge or omitting the input box), preventing accidental input of artificial ceilings.
   - The database schema already supports nullable `maximum_value` (`NUMERIC NULL`); this contract must be honored cleanly without breaking existing products.

2. **Incremental Step-Loop Logic Rules ("FOR EVERY ... ADD ..."):**
   - Introduce a new rule execution mode alongside the standard conditional ("WHEN / THEN"): the **Step-Loop Rule** (`loop` / `repeat_every`).
   - The administrator can configure structural rules that dynamically increment component quantities or parameters in proportion to dimension growth without repetitive manual steps.
   - Rule parameters:
     - **Dimension Source:** The parameter driving the increment (e.g., `height` or `width`).
     - **Step Interval:** The step size in millimeters (e.g., `500` mm).
     - **Base Threshold (Start Value):** The starting dimension above which the loop begins calculating (e.g., `1000` mm, or defaulting to the parameter's minimum or base value).
     - **Target Component:** The structural element receiving additional quantity (e.g., `horizontal-mullion`, `hinge`, `glass-panel`).
     - **Quantity per Step:** The number of parts added for each completed step interval (e.g., `+1` part).
   - Mathematical formula:
     $$\text{Steps} = \max\left(0, \left\lfloor \frac{\text{Current Value} - \text{Base Threshold}}{\text{Step Interval}} \right\rfloor\right)$$
     $$\text{Added Quantity} = \text{Steps} \times \text{Quantity Per Step}$$
     $$\text{Final Quantity} = \text{Base Quantity} + \text{Added Quantity}$$
   - Example: A window has a base height of 1000mm with 0 horizontal mullions. The admin defines: *"For every 500mm added in height above 1000mm, add 1 horizontal mullion"*.
     - At height = 1200mm: $\lfloor (1200 - 1000) / 500 \rfloor = 0$ additional mullions (Total: 0).
     - At height = 1500mm: $\lfloor (1500 - 1000) / 500 \rfloor = 1$ additional mullion (Total: 1).
     - At height = 2000mm: $\lfloor (2000 - 1000) / 500 \rfloor = 2$ additional mullions (Total: 2).
     - At height = 3500mm: $\lfloor (3500 - 1000) / 500 \rfloor = 5$ additional mullions (Total: 5).
   - This single rule automatically covers all heights from 1000mm to infinity without authoring dozens of duplicate rules.

## 4. Architectural, Mathematical & Schema Design

### 4.1 Parameter Unconstrained Dimension Design

Parameters represent the dimensional degrees of freedom for a product template (`ERD-E5`). For fenestration products, `width` and `height` govern overall aperture dimensions.

```
+-------------------------------------------------------------------------------+
|                             Product Parameter                                 |
+--------------------+---------------------+------------------------------------+
| Dimension Field    | Value Constraint    | Semantic Behavior                  |
+--------------------+---------------------+------------------------------------+
| minimum_value      | Mandatory (>= 100)  | Prevents invalid / zero geometries |
| default_value      | Mandatory (>= min)  | Starting size on workspace load    |
| maximum_value      | NULL (Unconstrained)| No upper limit for custom spans    |
| step_value         | Optional (e.g., 1)  | Discrete increment for sliders/keys|
+--------------------+---------------------+------------------------------------+
```

When `param.parameter_key === "width" || param.parameter_key === "height"`:
- `maximum_value` is stored as `null`.
- In the UI, the input is replaced by a compact badge:
  ```html
  <span class="text-xs font-medium text-emerald-700 bg-emerald-50 px-2 py-1 rounded-[6px] border border-emerald-200">
    Unconstrained
  </span>
  ```
- For custom parameters, an "Unlimited" toggle or empty input clears `maximum_value` to `null`.

### 4.2 Structural Rule Polymorphism (Threshold vs Step-Loop)

To maintain 100% backwards compatibility with all existing rules, structural rules (`ERD-E7`) adopt a discriminated union pattern inside the JSONB payload:

#### Mode A: Threshold Rule (`when_then`)
Standard relational comparison. Evaluates whether a parameter has crossed a specific boundary.
- **Trigger:** Single event when condition is met.
- **Use Case:** "When width >= 2400mm, switch to 3 panels" or "When width >= 1800mm, set center mullion to 1".
- **JSON Schema:**
  ```json
  {
    "rule_name": "2-Panel Wide Window",
    "priority": 1,
    "condition_data": {
      "rule_type": "when_then",
      "parameter_key": "width",
      "operator": ">=",
      "value": 1800
    },
    "action_data": {
      "target_type": "component",
      "target_key": "frame-center",
      "action_type": "set_quantity",
      "value": 1
    }
  }
  ```

#### Mode B: Step-Loop Rule (`loop`)
Continuous linear iteration. Adds components incrementally as dimensions grow.
- **Trigger:** Evaluated continuously based on distance beyond the base threshold.
- **Use Case:** "For every 500mm added in height above 1000mm, add 1 horizontal mullion".
- **JSON Schema:**
  ```json
  {
    "rule_name": "Intermediate Horizontal Mullions",
    "priority": 2,
    "condition_data": {
      "rule_type": "loop",
      "parameter_key": "height",
      "step_value": 500,
      "start_value": 1000
    },
    "action_data": {
      "target_type": "component",
      "target_key": "horizontal-mullion",
      "action_type": "add_quantity",
      "value": 1
    }
  }
  ```

### 4.3 Mathematical Formulation of Step-Loop Rule Evaluation

Let:
- $V_{\text{actual}}$ be the resolved numeric value of parameter $P$ in millimeters.
- $V_{\text{start}}$ be the starting threshold (`start_value`), defaulting to 0 if unspecified.
- $S$ be the step interval (`step_value`), where $S > 0$.
- $Q_{\text{step}}$ be the quantity to add per step (`action_data.value`), where $Q_{\text{step}} \ge 0$.
- $Q_{\text{base}}$ be the initial component base quantity defined in `product_components.base_quantity`.

#### Step Calculation:
$$\Delta V = V_{\text{actual}} - V_{\text{start}}$$

$$\text{Steps} = \begin{cases} 
0 & \text{if } \Delta V \le 0 \text{ or } S \le 0 \\
\left\lfloor \frac{\Delta V}{S} \right\rfloor & \text{if } \Delta V > 0 \text{ and } S > 0 
\end{cases}$$

#### Component Quantity Application:
If `action_data.action_type === "add_quantity"`:
$$Q_{\text{final}} = Q_{\text{current}} + (\text{Steps} \times Q_{\text{step}})$$

If `action_data.action_type === "set_quantity"`:
$$Q_{\text{final}} = \max(0, Q_{\text{step}} \times \text{Steps})$$

#### Edge Case Safeguards:
1. **Division by Zero:** If $S \le 0$, step count is forced to 0. No calculation is performed.
2. **Negative Delta:** If $V_{\text{actual}} < V_{\text{start}}$, step count is 0. Components are never decremented below their base configuration by this rule.
3. **Integer Component Quantities:** Component counts for physical hardware, profiles, and glass panels must always resolve to whole non-negative integers ($\lfloor \dots \rfloor$).

### 5.2 Step 2: Parametric Structural Resolver Upgrade

**Target File:** `src/lib/visualization/structuralResolver.ts`  
**Description:** Extend rule evaluation in `resolveProductStructure` to process both threshold conditions and step-loop increment rules.

In `structuralResolver.ts`:

```typescript
export function resolveProductStructure({
  definition,
  values = {},
}: ResolveProductStructureInput): ResolvedStructure {
  const resolvedValues: Record<string, unknown> = {
    ...definition.template.baseConfiguration,
  };
  const parameterKeys = new Set<string>();

  for (const parameter of definition.parameters) {
    parameterKeys.add(parameter.parameterKey);
    resolvedValues[parameter.parameterKey] = normalizeParameterValue(
      values[parameter.parameterKey] ?? resolvedValues[parameter.parameterKey] ?? parameter.defaultValue,
      parameter.parameterType,
      parameter.minimumValue,
      parameter.maximumValue,
      parameter.stepValue,
    );
  }

  for (const [key, value] of Object.entries(values)) {
    if (!parameterKeys.has(key)) {
      resolvedValues[key] = value;
    }
  }

  const componentQuantities: Record<string, number> = {};
  for (const component of definition.components) {
    componentQuantities[normalizeComponentKey(component.componentKey)] =
      component.baseQuantity;
  }

  const appliedRuleIds: string[] = [];
  for (const rule of [...definition.rules].sort((a, b) => a.priority - b.priority)) {
    const condition = rule.conditionData;
    const ruleType = condition.rule_type ?? (condition.step_value ? "loop" : "when_then");

    if (ruleType === "loop") {
      const isApplied = applyStepLoopRule(condition, rule.actionData, resolvedValues, componentQuantities);
      if (isApplied) {
        appliedRuleIds.push(rule.ruleId);
      }
    } else {
      if (!matchesCondition(condition, resolvedValues)) {
        continue;
      }
      applyRuleAction(rule.actionData, resolvedValues, componentQuantities);
      appliedRuleIds.push(rule.ruleId);
    }
  }

  return {
    resolvedValues,
    numericValuesMm: getNumericValuesMm(
      definition.template.measurementUnit,
      definition.parameters,
      resolvedValues,
    ),
    componentQuantities,
    appliedRuleIds,
  };
}

function applyStepLoopRule(
  condition: Record<string, unknown>,
  action: Record<string, unknown>,
  resolvedValues: Record<string, unknown>,
  componentQuantities: Record<string, number>,
): boolean {
  const paramKey = typeof condition.parameter_key === "string" 
    ? condition.parameter_key 
    : (typeof condition.parameter === "string" ? condition.parameter : null);

  if (!paramKey) return false;

  const actualValue = toNumber(resolvedValues[paramKey], Number.NaN);
  if (Number.isNaN(actualValue)) return false;

  const stepValue = toNumber(condition.step_value, 0);
  if (stepValue <= 0) return false; // Prevent division by zero or infinite loop

  const startValue = toNumber(condition.start_value, 0);
  const delta = actualValue - startValue;

  if (delta <= 0) return false;

  const steps = Math.floor(delta / stepValue);
  if (steps <= 0) return false;

  const quantityPerStep = toNumber(action.value, 1);
  const totalAdded = steps * quantityPerStep;

  const targetType = action.target_type;
  const targetKey = action.target_key;
  const actionType = action.action_type;

  if (typeof targetKey === "string" && targetType === "component") {
    const normalizedKey = normalizeComponentKey(targetKey);
    const currentQty = componentQuantities[normalizedKey] ?? 0;

    if (actionType === "set_quantity") {
      componentQuantities[normalizedKey] = Math.max(0, totalAdded);
    } else {
      // Default: "add_quantity"
      componentQuantities[normalizedKey] = Math.max(0, currentQty + totalAdded);
    }
    return true;
  } else if (typeof targetKey === "string" && targetType === "parameter") {
    const currentVal = toNumber(resolvedValues[targetKey], 0);
    resolvedValues[targetKey] = currentVal + totalAdded;
    return true;
  }

  return false;
}
```

## 6. Security, Performance, and Non-Regression Invariants

1. **Division by Zero & Infinite Loop Prevention:**
   - In `applyStepLoopRule`, any `step_value <= 0` immediately aborts evaluation and returns `false`.
   - The loop calculation is purely mathematical ($O(1)$ arithmetic: $\lfloor \Delta / S \rfloor$), executing in sub-microsecond time with zero risk of call stack exhaustion or infinite while-loops.

2. **Physical Quantity Clamping:**
   - Physical parts (aluminum extrusions, glass panels, rollers, hinges) cannot have negative or fractional quantities.
   - The engine strictly applies `Math.max(0, ...)` and integer step rounding ($\lfloor \dots \rfloor$).

3. **Database Parity & Zero DDL Requirement:**
   - PostgreSQL table `product_parameters` already permits `maximum_value numeric null`.
   - Table `structural_rules` stores `condition_data` and `action_data` in JSONB columns validated by `is_json_object`.
   - Therefore, zero schema migrations are needed (BAN-MIGR-06 fully satisfied).

4. **Strict Type Safety (BAN-TYPE-05):**
   - No `any` types are introduced in any TypeScript signatures or adapters. All inputs are typed via interfaces (`UpsertParameterInput`, `UpsertRuleInput`, `RuleConditionData`, `RuleActionData`).

5. **Punctuation & Style Governance (BAN-PUNCT-01 & BAN-UI-09):**
   - Zero em-dashes used anywhere in specifications or code comments. Standard hyphens, colons, or parentheses used exclusively.
   - UI controls strictly reuse existing Tailwind CSS design tokens and component patterns (`border-neutral-200`, `text-[#0f1422]`, `focus:border-[#07b6d3]`).
