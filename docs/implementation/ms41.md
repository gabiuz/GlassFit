## 1. Authorized Requirement

In the GlassFit client visualization workflow, prospective customers can browse the catalog, upload a photo of their space, configure customized 3D glass and aluminum products in the workspace (`/visualize/[productId]/workspace`), review visual comparisons (`/comparison`), and inspect estimated pricing on the quotation page (`/quotation`) without being forced to log in upfront.

When an unauthenticated user on `/quotation` clicks "Send Booking" to finalize a consultation request, the application correctly identifies that an authenticated account is required and routes the user to the login screen.

### 1.1 Current Behavior (Defect)

Two critical defects currently disrupt this workflow:

1. **Unintended Redirection to Homepage (`/`):**
   - When the user completes authentication on `/login`, the application redirects them to the homepage (`/`) instead of returning them to the consultation booking workflow (`/send-booking`).
   - For Google OAuth authentication, `LoginForm.tsx` hardcodes the OAuth callback redirect destination to `next=/`, completely discarding the `next=/send-booking` query parameter passed in the URL.
   - For user registration, when a new user clicks "Register here" on `/login?next=/send-booking`, the link drops the `next` parameter entirely. Upon registering, `RegisterForm.tsx` redirects auto-confirmed users to `/` and hardcodes `next=/` in email confirmation and Google sign-up options.
   - For email/password login, `LoginForm.tsx` executes `router.push(next)` immediately followed by `router.refresh()`, triggering a known Next.js App Router navigation conflict where the active server component refresh races against client route transitions.
   - In `BookingFlow.tsx`, action prompts route to `/login?redirect=/send-booking` (using parameter key `redirect`), whereas `LoginForm.tsx` looks strictly for `searchParams.get("next")`, falling back to `"/"`.

2. **Loss and Vanishing of Workspace Configurations:**
   - In `src/components/shared/LayoutWrapper.tsx`, the `LayoutContent` component defines two distinct, conditional branches based on `isAuthPage` (which is `true` for `/login` and `/register`, and `false` for `/quotation` and `/send-booking`).
   - Each branch mounts its own isolated `<VisualizationSessionProvider>`. Consequently, when navigating from `/quotation` to `/login`, React unmounts the active provider, destroying the in-memory React session state (including placed overlays, custom dimensions, calculated BOM pricing items, and structural definitions).
   - Although `VisualizationSessionProvider` attempts to serialize state to browser `sessionStorage`, large room photo backgrounds and rendered canvas snapshots frequently exceed the browser storage quota or trigger aggressive sanitization fallbacks that strip image data and placed overlay arrays.
   - When the user transitions from `/login` to `/send-booking` (or back to `/quotation`), a third provider instance mounts from scratch. If session storage was truncated or corrupted, the entire visualization progress vanishes, presenting the user with empty product lists, default fallback pricing, or broken previews.

### 1.2 Required Behavior

1. **Deterministic Post-Authentication Redirection:**
   - After successfully logging in via email/password or Google OAuth, the user must be redirected directly to `/send-booking`.
   - If the user chooses to create an account by clicking "Register here" from `/login?next=/send-booking`, the destination parameter must be preserved on `/register`. Upon completing registration (both auto-confirmed and email confirmation callbacks), the user must be directed to `/send-booking`.
   - If an authenticated user lands on `/login?next=/send-booking`, they must be redirected directly to the specified destination.
   - Return-path parameters must be validated to prevent open-redirect vulnerabilities (restricting destinations strictly to internal relative paths).

2. **Zero Configuration Loss:**
   - All product configurations generated in the workspace (product selections, dimensions, aluminum finishes, glass types, panel counts, sills, structural waivers, placed overlays, and rendered snapshot references) must remain intact throughout the entire authentication sequence.
   - `<VisualizationSessionProvider>` must wrap the application shell continuously without unmounting during transitions between public workflow pages, authentication routes, and booking pages.
   - Browser storage fallback must be fortified so that even across full-page OAuth redirects to external identity providers, all structural configurations and quotation drafts are restored without data loss.

No database migration, backend CV microservice change, or new third-party dependency is authorized. This document is an implementation specification; no application code is to be executed or committed during planning.

## 4. Architectural & Interaction Design

### 4.1 Layout Hierarchy Consolidation

To prevent React component destruction during route transitions, `<VisualizationSessionProvider>` must be hoisted above the conditional auth branch in `LayoutWrapper.tsx`.

Current Structure (Flawed):
```
LayoutWrapper
└── LayoutContent
    ├── [if isAuthPage]
    │   └── VisualizationSessionProvider (Instance A - Unmounts on navigation)
    │       └── children
    └── [else]
        └── VisualizationSessionProvider (Instance B - Unmounts on navigation)
            ├── Navbar
            ├── children
            └── Footer
```

Target Structure (Persistent):
```
LayoutWrapper
└── VisualizationSessionProvider (Unified Singleton Instance - Never unmounts)
    └── LayoutContent
        ├── [if isAuthPage]
        │   └── children
        └── [else]
            ├── Navbar
            ├── children
            └── Footer
```

By lifting `<VisualizationSessionProvider>` outside the conditional block:
1. In-memory session state persists continuously when transitioning from `/quotation` -> `/login` -> `/send-booking`.
2. Active placed overlays, calculated BOM definitions, and uploaded space image sessions remain accessible in memory.
3. Even if browser `sessionStorage` rejects large image payloads due to storage quota limits, the in-memory state remains fully intact for the user session.

### 4.2 Safe Return Path Resolution Contract

To prevent open-redirect vulnerabilities where malicious actors construct phishing URLs (e.g. `/login?next=https://malicious-site.com` or `/login?next=//malicious-site.com`), all destination parameters must be strictly sanitized.

Create helper `resolveSafeRedirectPath` in `src/lib/auth/redirectPath.ts`:

| Property | Rule | Valid Example | Invalid Example | Resolved Output |
|---|---|---|---|---|
| Relative Path Check | Must start with single `/` | `/send-booking` | `https://malicious.com` | `/` (fallback) |
| Protocol-Relative Check | Must not start with `//` | `/quotation` | `//malicious.com` | `/` (fallback) |
| Backslash Check | Must not contain backslashes | `/send-booking?step=1` | `/\\evil.com` | `/` (fallback) |
| Key Precedence | Checks `next`, then `redirect` | `?redirect=/send-booking` | `?unrelated=true` | `/send-booking` |
| Default Value | Configurable default fallback | N/A | `null` | Custom fallback or `/` |

Contract Signature:
```typescript
export function resolveSafeRedirectPath(
  searchParams: URLSearchParams | { get: (key: string) => string | null } | null | undefined,
  fallback = "/"
): string;
```

### 4.3 End-to-End Workflow Sequences

#### Scenario A: Existing User Logs In with Email and Password
1. User configures window product in workspace and navigates to `/quotation`.
2. User clicks "Send Booking".
3. `Quotation.tsx` checks auth; no session found; calls `router.push("/login?next=/send-booking")`.
4. User enters credentials on `/login` and submits form.
5. `LoginForm.tsx` executes `supabase.auth.signInWithPassword`.
6. Successful login resolves `resolveSafeRedirectPath(searchParams, "/")` -> `"/send-booking"`.
7. `LoginForm.tsx` performs `router.push("/send-booking")`.
8. User arrives at `/send-booking` with entire quotation configuration, placed overlays, and pricing view model completely preserved in memory and storage.

#### Scenario B: Existing User Logs In with Google OAuth
1. User is on `/login?next=/send-booking`.
2. User clicks "Log In with Google".
3. `LoginForm.tsx` resolves `nextPath = resolveSafeRedirectPath(searchParams, "/")`.
4. OAuth redirect options constructed:
   `redirectTo: `${window.location.origin}/auth/confirm?next=${encodeURIComponent(nextPath)}&type=oauth``
5. User completes Google authentication.
6. Browser returns to `/auth/confirm?code=...&next=/send-booking&type=oauth`.
7. `route.ts` exchanges code for session and executes:
   `NextResponse.redirect(new URL("/send-booking", request.url))`.
8. User lands on `/send-booking`. Session rehydrates from `sessionStorage` intact.

#### Scenario C: New User Registers an Account
1. User is on `/login?next=/send-booking`.
2. User clicks "Register here".
3. Link navigates to `/register?next=%2Fsend-booking`.
4. User fills in profile details (name, email, Philippine phone, password) and registers.
5. If auto-confirmed: `RegisterForm.tsx` redirects directly to `/send-booking`.
6. If email confirmation required: `emailRedirectTo` contains `/auth/confirm?next=%2Fsend-booking`.
7. Clicking the confirmation email redirects user to `/send-booking` upon session activation.

## 5. Implementation Plan & Detailed Code Specifications

### 5.1 Create Safe Redirect Utility (`src/lib/auth/redirectPath.ts`)

Create a pure utility function providing robust URL validation:

```typescript
export function resolveSafeRedirectPath(
  searchParams?: { get: (key: string) => string | null } | null,
  fallback = "/"
): string {
  if (!searchParams) {
    return fallback;
  }

  const candidate = searchParams.get("next") || searchParams.get("redirect");
  if (!candidate) {
    return fallback;
  }

  const trimmed = candidate.trim();

  // Must start with a single forward slash and not a protocol-relative slash
  if (!trimmed.startsWith("/") || trimmed.startsWith("//")) {
    return fallback;
  }

  // Must not contain backslashes or null bytes
  if (trimmed.includes("\\") || trimmed.includes("\0")) {
    return fallback;
  }

  return trimmed;
}
```

## 6. Security, RLS, and Cross-Cutting Concerns

### 6.1 Open Redirect Prevention

All query parameters determining client navigation must pass through `resolveSafeRedirectPath`. Direct assignment of unvalidated URL parameters to `router.push()` or `window.location` is strictly banned.

Security tests must assert that:
- External domains (`https://example.com`) fall back to `/`.
- Protocol-relative URLs (`//example.com`) fall back to `/`.
- Embedded schemes (`javascript:...`, `data:...`) fall back to `/`.
- Control characters and backslash sequences fall back to `/`.

### 6.2 Supabase RLS and Session Integrity

- No RLS bypass is introduced (`BAN-RLS-07`). User profile access on `/send-booking` relies on standard authenticated cookies synchronized via `proxy.ts`.
- When an unauthenticated session gains credentials, the Supabase Auth listener in `AuthProvider.tsx` updates `user` state reactively without requiring manual document reloads.

### 6.3 Browser Storage Isolation

- Session storage continues to use the dedicated namespace `glassfit.visualization.session`.
- Because `<VisualizationSessionProvider>` is hoisted, state is maintained in React memory, drastically reducing dependency on immediate browser storage serialization during fast in-tab transitions.

1. Valid internal paths (`/send-booking`, `/quotation`, `/visualize/p1/workspace`) return the exact path.
