## 1. Outcome and Scope

Switching the active editor between two different 3D products in one room must feel like switching between two placed overlays of the same product. The room photo, placed layers, workspace component, canvas DOM node, and WebGL context stay mounted. There is no route loading skeleton, page flash, loss of placement, or period in which controls, price, or snapshot data belong to a different product than the visible active model.

This applies to all three existing product-selection modes: editing a placed overlay, adding another product, and changing the active product. It applies to both parametric and fixed-model definitions. Direct entry and refresh at `/visualize/[productId]/workspace` continue to use the server page.

There are no schema migrations, CV service changes, new dependencies, or visual redesigns. Reuse existing workspace controls and error presentation. Do not use continuous camera tracking or bypass Supabase RLS.

### 1.1 Non-negotiable invariants

1. At every committed render, `activeProductId === activeDefinition.product.productId`. Session `selectedProductId` and `structuralDefinition` must represent that same pair.
2. A product switch never changes the room image, unaffected placed overlay identities or coordinates, viewport scroll position, canvas element, or `ProductModelRenderer` instance. An edit or add may change only the involved active and target layers at commit. The active model group may change.
3. While a target product is loading, the last committed product remains visible and usable for viewing. A selection request cannot partly update active identity, pricing, controls, saved configuration, or URL.
4. A successful switch commits the target definition, target configuration, active model, layer changes, session state, and URL as one logical activation. No intermediate frame may use the target definition with the source configuration or vice versa.
5. A failed or superseded request leaves the last committed product and URL intact. Retry is possible without a refresh.
6. Same-product overlay selection retains its current direct path and must not issue a definition request.
7. Existing quotation, comparison, snapshot, guardrail, occlusion, placement, and mobile editor behavior must still work after either direction of a cross-product switch.

## 3. State Ownership and Activation Contract

### 3.1 One active product pair

`ProductAwareWorkspacePage` owns the active `{ productId, definition }` pair used for all `ProductModelWorkspace` props. Initialize it from the server page. Validate that the server definition's product ID equals the route ID. The session mirrors a committed pair for persistence and downstream quotation; it is not a second independent source that may override the visible pair.

The current effect that unconditionally calls `setStructuralDefinition(structuralDefinition)` must become an initialization or genuine server-route synchronization path. A native history update must not replay the original server definition. On a real route remount or refresh, the server route ID is authoritative. If the stored session ID differs, do not reuse its active configuration for the new route ID; retain only scene data that is valid for that room session.

Every product-specific read in the workspace must use the committed pair, including name, type, assets, structural rules, price, quotation recipe, variation recipe, and snapshot metadata. No consumer should infer product identity from the original server prop after a client switch.

### 3.2 Session transition

Extend `TransitionWorkspaceProductOptions` with a required definition for cross-product commits. Validate that it belongs to `nextProductId`. In `transitionSessionState`, set `selectedProductId`, `structuralDefinition`, and `productConfiguration` together. Keep the current same-product behavior for existing callers, and retain clearing only for explicit navigation flows that do not supply a definition. Do not call `setStructuralDefinition` separately after the transition.

The activation path must suppress `onConfigurationChange` while the target configuration is being installed, then publish the final target snapshot once. This prevents a mount-era source snapshot from overwriting the session's new product configuration. Existing session storage serialization remains the persistence mechanism.

### 3.3 Scene state versus active-product state

| State | Cross-product behavior |
|---|---|
| Room photo, image session, lighting analysis, detected objects, background, canvas size, page scroll, placed overlay records, layer order, and stored layer imagery | Preserve. |
| WebGL renderer, canvas DOM node, room compositor, and cached layer display | Preserve their instances. Replace only the active product model group and its owned resources. |
| Edit a placed overlay | Restore that overlay's complete saved `ProductConfigurationSnapshot`: dimensions, materials, panel/sill values, waiver, quantity, position, size/zoom, orientation, perspective fit, occlusion selections/mask, and active layer identity. |
| Add a different product | First capture the current active product as a placed overlay exactly once. Initialize the new product from its own template/default or matching seed, with no width, panel, sill, waiver, material, or geometry value leaked from the previous product. Preserve the room and placed layers. Preserve the user's workspace view and its current zoom where that zoom is part of the shared view; use the new product's own placement defaults for product-specific transforms. |
| Change the active product | Do not place a duplicate of the source product. Use the target product's structural defaults for model-specific values and preserve the current active placement and zoom where valid, so the product stays in the same opening. Clear incompatible product-specific settings such as an unsupported panel count or waiver. |
| Same-product overlay edit | Keep the existing direct configuration application with no network request or remount. |

The existing `zoomLevel` is stored in the product configuration, so implementation must explicitly apply the edit target's saved zoom and define the retained zoom for change mode. Do not rely on `useState` initializers. For add mode, test that the room and existing overlays do not move even when the new active product starts at its own defaults.

Replace the template-default effect's broad `templateId` reset with an activation-aware rule. Apply structural defaults only when creating a new active product with no saved configuration. An edited overlay's saved width and height win over template defaults. Do not treat `templateId` as a unique product identity; use `productId` and an activation revision or equivalent explicit marker.

## 4. Staged Switch Algorithm

### 4.1 Prepare, then commit

For a different product ID, follow this order:

1. Capture a switch intent containing target ID, mode, target overlay ID and saved configuration if editing, source active configuration, and the proposed overlay/layer changes. Compute additions and replacements without publishing them. `createPlacedOverlay` may render an image during preparation but must not mutate placed layers yet.
2. Assign a monotonically increasing request ID. A new request or session reset invalidates older requests. Prevent duplicate submissions for the same pending intent. Keep the current committed scene visible; selection controls may show their existing loading state or be temporarily disabled.
3. Obtain the target definition from the session-scoped client cache or the server function. Validate the returned `definition.product.productId` against the requested ID and reject unavailable products.
4. Build the target active configuration according to section 3.3. Normalize it against target parameters and model strategy. Reject invalid or unavailable assets before changing the committed state.
5. Prepare the target model group with the target definition and configuration while retaining the current visible model group. Once its geometry and required assets are ready, check that the request ID and room `assetSessionId` are still current.
6. Commit the prepared model and activation together: install the target configuration, update the active pair and the session through one transition, apply proposed layer changes once, and update the URL. Swap and draw the prepared model in the existing canvas in the same pre-paint commit, or retain the previous canvas frame until the matching React state commits. The new product name, controls, BOM price, active layer, quotation and snapshot metadata must all point to this target after the commit. Close or reset any source-product modal or validation state that cannot safely carry over.
7. Release superseded model resources after the new group is visible. Resume configuration publication only after the committed target snapshot is installed.

An implementation may use an activation reducer, an explicit prepared-model API, or equivalent internal coordination. The observable order and invariants above are mandatory. A `useEffect` that starts a model build only after publishing a new definition is insufficient if it renders an old model with new-product pricing or controls while the build is pending.

### 4.2 Failure and concurrency behavior

- Definition fetch failure, inactive product, invalid response, GLB/model build failure, or missing required asset: keep the last committed active product, layers, configuration, session, and URL. Surface an actionable message through the existing workspace error presentation and allow retry.
- If a newer selection is made while an older fetch or model build is pending, only the newest request may commit. Dispose a completed stale group without adding it to the scene. A request invalidated by a new room session or component unmount may not commit.
- If capture of the source active overlay fails during add or edit, do not silently proceed with a partial layer transition. Keep the prior committed state and show an error.
- Avoid duplicate layer insertion and replacement if a user clicks rapidly or retries. Use overlay IDs and the existing transition semantics; preserve layer numbers and current image data.
- For same-product selection, do not enter the cross-product request path.

## 5. Data Fetch and Cache Contract

Create a client-callable read-only server function in a dedicated `"use server"` file under `src/app/visualize/`. It accepts a validated product ID and returns only the `ProductStructuralDefinition` needed by the workspace. Reuse `getProductStructuralDefinition`, which already queries active product and template rows with the server Supabase client. Do not use the service-role key for this public catalog read. Keep validation and unavailable-product behavior aligned with the direct server page. Do not return raw database errors or secrets to the browser.

Create a client-side definition loader under `src/lib/visualization/` with a cache keyed by both `assetSessionId` and product ID. Seed it from the server-provided definition. Deduplicate concurrent requests for the same key with a shared pending promise; retain only successful validated results, and evict rejected promises. Clear the cache on `resetVisualizationSession`, on a new prepared space image/session, and when the workspace's session identity changes. Cached definitions are an in-session optimization, not a source of authority for a new room session. A later direct refresh still gets the current server definition.

No new package is needed. Follow the installed Next.js `use server` guide at `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md` for client imports, input validation, and constrained return values.

## 6. Renderer and Canvas Lifecycle

Keep one `ProductModelRenderer` instance for the workspace lifetime. `loadModel` is the existing rebuild entry point; there is no existing `setDefinition` method. Refactor the renderer as necessary so model preparation is asynchronous but active-group replacement is atomic. The old model remains renderable until the target group is ready. A failed or stale build does not remove the old group.

Track ownership when releasing meshes. Dispose cloned or generated materials, generated geometries, and disposable fixed-model resources owned by that group. Component model clones share geometry with `componentModelCache` sources, so do not dispose those shared cached geometries during a switch. Do not dispose the renderer, WebGL context, shared environment map, background image, or component cache on each switch. Dispose a superseded prepared group and its owned resources. Existing renderer unmount cleanup still runs on actual workspace exit.

The current model-loading effect depends on definition and configuration fields and can issue overlapping builds. Preserve its legitimate within-product parameter rebuilding while applying the request-version rule to both cross-product and same-product rebuilds. Reject stale completion before changing capabilities, model revision, visible canvas, or error state. Render the new group into the existing canvas after the committed swap. Verify that material capabilities, projected bounds, lighting, occlusion, and perspective rendering are recalculated for the target rather than inherited from the source.

## 7. URL and Browser History

After a successful activation, use `window.history.replaceState(null, "", "/visualize/<encoded-product-id>/workspace")`. Preserve any supported query string and hash only if the workspace currently uses them; never construct a URL from an unvalidated ID. This changes the address without a Next.js route navigation or `loading.tsx` render. Do not use `router.push`, `router.replace`, or `router.refresh` for a product switch.

Replacement is intentional: product switches do not create browser history entries. Browser Back returns to the history entry before this workspace entry; it is not an undo-product control. If Back later returns to the workspace through a normal navigation, the route and server definition establish the active pair. Refresh after a switch uses the new product ID in the URL and restores the matching session configuration when its ID matches. The existing `onBack` path to upload remains a normal navigation and still resets the session.

## 9. Verification and Acceptance

### 9.1 `QAD-TC59`: Cross-product workspace continuity (P0)

**Fixture:** One room photograph with two placed windows and one placed door. Use products with different structural templates and component assets. Include one parametric and one fixed-model product if the active catalog supports both. Give each overlay distinct dimensions, material, position, zoom, yaw/pitch, occlusion, and layer number. Record the room image, placed overlay IDs and coordinates, canvas DOM identity, renderer/WebGL context identity, active price, and session ID before switching.

| Case | Action | Required result |
|---|---|---|
| A | Edit Window 1, Window 2, Door, then Window 1 | Same-product edits make no definition request. Cross-product edits make at most one request per uncached product. Every edit restores exactly that overlay's saved configuration and matching geometry, controls, price, active layer, and session product ID. |
| B | Add a door while a window is active | The window is placed exactly once, all existing layers keep coordinates and imagery, and the new door uses door defaults or a valid seed. No window-specific panel, sill, waiver, dimension, or material value leaks into the new door. |
| C | Change the active window to a door | No duplicate of the source is placed. Position and zoom remain appropriate for the same opening, target structural defaults apply, and pricing and quotation use the door. |
| D | Observe a cache miss with throttled network and slow GLB | The old committed scene stays visible. No `loading.tsx`, page flash, blank room, workspace/canvas remount, or second WebGL context occurs. The new product appears only when its geometry, configuration, controls, and price are ready together. |
| E | Make a definition request fail, then a model load fail | Active product, overlays, session, and URL remain at the last successful commit. Error is visible and retry succeeds without refresh. |
| F | Rapidly request Window, Door, Window; reset the room during a pending request | Only the latest valid request for the same room may commit. Stale fetches and model groups cannot restore an older product or repopulate a reset session. |
| G | Switch to Door, refresh, then use browser Back | URL and server route load Door on refresh with its matching session configuration. Back follows the prior history entry as defined in section 7; no ghost product state appears on return. |
| H | Repeat A through D on compact mobile viewport and with perspective fit, occlusion, comparison, snapshot, and quotation flows | Scroll lock, touch controls, masking, composition, stored layers, final snapshot, and quotation still correspond to the active product and room. |
| I | Alternate products and change dimensions repeatedly | WebGL context identity remains stable; old owned materials/generated geometry and superseded prepared groups are released. Shared component-cache geometry stays usable when revisiting a product. No steadily increasing orphaned model groups or console errors. |

Automate reducer/cache/request-order tests and renderer ownership tests where practical. Add a browser-level test or repeatable instrumented manual check for canvas identity, absence of loading skeleton, URL, visible model, and failure recovery. Run existing `QAD-TC5`, `QAD-TC6`, `QAD-TC8`, `QAD-TC17`, `QAD-TC28`, `QAD-TC52`, and `QAD-TC55` regressions that touch the modified paths.
