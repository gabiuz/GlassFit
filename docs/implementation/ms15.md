## 1. Executive Summary & Problem Context

In the GlassFit platform, customers complete the visualization workflow, receive an itemized parametric Bill of Materials (BOM) quotation, and initiate an asynchronous consultation request via Facebook Messenger or Viber (`src/features/booking/components/BookingFlow.tsx`). This handoff records an entry in `public.booking_requests` via `recordBookingRequest` (`src/lib/booking/bookingActions.ts`).

### The Observed Defect
Administrators report an inconsistent system state:
1. **Admin Dashboard Metric Cards (`/admin`):** The "New Booking" and "Pending booking" KPI counter cards reflect newly submitted bookings accurately.
2. **Admin Bookings Management Page (`/admin/bookings`):** The page displays an empty state ("No bookings found") and fails to reflect any incoming customer bookings.
3. **Admin Dashboard Recent Bookings Table (`/admin`):** The "Recent Bookings" table also silently fails to display recent booking rows despite the metric counter displaying positive numbers.

## 2. Root Cause Analysis

Investigation of the persistence, service, and presentation layers reveals seven interrelated architectural deficiencies causing or amplifying this divergence:

### 2.1 PostgREST Foreign Key Relationship Ambiguity (`PGRST201`)
The primary failure preventing bookings from rendering on `/admin/bookings` is an ambiguous relational join in PostgREST.

In `supabase/migrations/001_backend_core.sql` and `supabase/migrations/complete_schema.sql`, the `public.booking_requests` table defines **two** foreign keys targeting `public.profiles`:
1. `booking_requests_profile_fk`: `booking_requests(profile_id)` references `profiles(profile_id)` (the customer who initiated the consultation).
2. `booking_requests_updated_by_fk`: `booking_requests(updated_by)` references `profiles(profile_id)` (the administrator or staff member who triaged or updated the booking status).

In `src/features/admin/bookings/BookingsPage.tsx` (lines 10-33), the Supabase query attempts to embed the customer profile using unqualified syntax:
```typescript
const { data: bookingsData } = await supabase
  .from("booking_requests")
  .select(`
    booking_request_id,
    status,
    created_at,
    selected_platform,
    signed_booking_links!inner (
      quotation_estimates!inner ( ... )
    ),
    profiles!inner (
      full_name,
      email,
      contact_number
    )
  `)
  .order("created_at", { ascending: false });
```

Because two relationships connect `booking_requests` and `profiles`, PostgREST cannot determine which foreign key to use. PostgREST aborts the query and responds with HTTP 300 and error code `PGRST201`:
```json
{
  "code": "PGRST201",
  "message": "Could not embed because more than one relationship was found for 'booking_requests' and 'profiles'",
  "hint": "Try changing 'profiles' to one of the following: 'profiles!booking_requests_profile_fk', 'profiles!booking_requests_updated_by_fk'."
}
```

### 2.2 Silent Failure and Nil Degradation
In `src/features/admin/bookings/BookingsPage.tsx`, the code does not inspect the `error` property returned by Supabase:
```typescript
const formattedBookings: AdminBookingItem[] = (bookingsData || []).map((b: any) => { ... });
```
When PostgREST emits `PGRST201`, `bookingsData` is `null`. The code falls back to `[]`, silently swallowing the critical database exception and rendering an empty list in `<BookingsContent initialBookings={[]} />`.

### 2.3 Why Dashboard Metric Cards Reflect while Bookings Page Does Not
In `src/features/admin/components/DashboardPage.tsx` (lines 41-56), the KPI metrics are computed using raw `count` queries without table joins:
```typescript
const { count: pendingBookingsCount } = await supabase
  .from("booking_requests")
  .select("*", { count: "exact", head: true })
  .eq("status", "Pending");
```
Because these count queries do not embed `profiles`, they succeed completely and report the accurate tally (for example, "New Booking: 2").

However, the "Recent Bookings" table on the same dashboard (lines 83-96) also uses unqualified `profiles!inner(full_name)`, which triggers the identical `PGRST201` error. As a result, the dashboard displays conflicting visual data: metric counters show active bookings, while both the dashboard recent bookings list and the dedicated bookings management page remain empty.

### 2.4 Incomplete Path Revalidation in Server Actions
In `src/lib/booking/bookingActions.ts` (`recordBookingRequest` lines 369-370, 397-398 and `updateBookingRequestStatus` lines 721-722), the revalidation statements are:
```typescript
revalidatePath("/admin/bookings");
revalidatePath("/dashboard");
```
In the Next.js 16 App Router structure, the administrative dashboard is mounted at `/admin` (`src/app/admin/(protected)/page.tsx`), not `/dashboard` (which is the customer dashboard). Omitting `revalidatePath("/admin")` leaves the administrative overview outside the explicit mutation invalidation contract. Although the route is currently request-time rendered, all booking consumers must be listed so client navigation behavior remains deterministic and future cache changes do not reintroduce drift.

### 2.5 Route Freshness Contract Is Not Explicit
Both admin server components create their Supabase client through `createSupabaseServerClient()`, which calls the request-time `cookies()` API. Under the repository's current Next.js 16 configuration (`cacheComponents` is not enabled), this already makes the routes dynamically rendered. The Supabase queries are also not wrapped in `unstable_cache` or `use cache`.

Therefore, `dynamic = "force-dynamic"` and `revalidate = 0` are not required to fix this defect and shall not be added. They are redundant under the current configuration, and Next.js 16 removes these route exports if Cache Components is enabled later. The implementation shall instead preserve request-time rendering, use `revalidatePath` for mutation-driven invalidation, and use `router.refresh()` only for an administrator-requested refresh of the current route.

### 2.6 Client State Desynchronization in `BookingsContent.tsx`
In `src/features/admin/bookings/BookingsContent.tsx` (line 30):
```typescript
const [bookings, setBookings] = useState<AdminBookingItem[]>(initialBookings);
```
`useState(initialBookings)` initializes once upon initial component mount. When a navigation or manual route refresh passes updated `initialBookings` props, `BookingsContent` lacks a synchronization strategy for the booking collection, selected booking, and editable status. Updating only the booking array would still leave `currentStatus` stale when the selected booking changes or is removed.

Furthermore, `BookingsContent` lacks a user-initiated "Refresh" trigger, leaving administrators without an on-demand mechanism to pull current booking requests without hard-refreshing the browser window. This milestone guarantees fresh data on navigation and manual refresh. It does not claim push-based live updates while the page remains idle.

### 2.7 Hard Ban Violation: TypeScript `any` (`BAN-TYPE-05`)
In `BookingsPage.tsx` (line 9 and line 35) and `DashboardPage.tsx` (line 98), the codebase explicitly bypasses type safety:
```typescript
// We use type any because the deeply nested join types from Supabase can be problematic
const formattedBookings: AdminBookingItem[] = (bookingsData || []).map((b: any) => { ... });
```
This violates `BAN-TYPE-05` ("Using any in TypeScript files degrades type safety across API contracts"). Strongly typed relational DTOs must be established.

## 5. Technical Specifications & Contract Architecture

### 5.1 Relational Query Disambiguation Contract
To resolve `PGRST201`, all PostgREST embeddings between `booking_requests` and `profiles` must explicitly state the foreign key constraint. Relationships shall also be given semantic aliases so customer and updater data cannot be confused in mapping code:

```typescript
customer:profiles!booking_requests_profile_fk (
  full_name,
  email,
  contact_number
)
```

The relationship constraints are non-null in ERD-E15 and ERD-E16, but the presentation query shall use left embedding so a recoverable relational-data defect remains visible as a booking row with explicit fallbacks instead of silently removing the booking. The authoritative query for `BookingsPage.tsx` shall be:

```typescript
const { data: bookingsData, error: bookingsError } = await supabase
  .from("booking_requests")
  .select(`
    booking_request_id,
    status,
    created_at,
    selected_platform,
    booking_link:signed_booking_links!booking_requests_link_fk (
      quotation:quotation_estimates!signed_booking_links_quotation_fk (
        quotation_number,
        pdf_r2_object_key,
        created_at,
        quotation_items (
          item_name,
          pricing_details
        )
      )
    ),
    customer:profiles!booking_requests_profile_fk (
      full_name,
      email,
      contact_number
    )
  `)
  .order("created_at", { ascending: false })
  .overrideTypes<BookingRequestWithRelationsRow[], { merge: false }>();

if (bookingsError) {
  console.error("[BookingsPage] Failed to fetch booking requests from Supabase:", bookingsError);
  return (
    <BookingsContent
      initialBookings={[]}
      loadError="Unable to load booking requests. Refresh to try again."
    />
  );
}
```

And for `DashboardPage.tsx`:
```typescript
const { data: recentBookingsData, error: recentError } = await supabase
  .from("booking_requests")
  .select(`
    booking_request_id,
    status,
    customer:profiles!booking_requests_profile_fk (
      full_name
    ),
    booking_link:signed_booking_links!booking_requests_link_fk (
      quotation:quotation_estimates!signed_booking_links_quotation_fk (
        quotation_items (
          item_name,
          pricing_details
        )
      )
    )
  `)
  .order("created_at", { ascending: false })
  .limit(5)
  .overrideTypes<DashboardRecentBookingRow[], { merge: false }>();

if (recentError) {
  console.error("[DashboardPage] Failed to fetch recent bookings from Supabase:", recentError);
}
```

`DashboardPage` shall pass a nullable error message to `DashboardContent` and `RecentBookingsTable`. A failed recent-bookings query must render a `role="alert"` message distinct from the successful empty state. Each metric count query shall destructure and log its own error; a failed metric shall display `Unavailable` rather than the misleading numeric value `0`.

### 5.2 Strict Relational Type Contracts (Eliminating `any`)
In `src/lib/booking/types.ts`, define strict database query return structures that match the aliased, many-to-one relationship shape:

```typescript
export type BookingDatabaseStatus = "Pending" | "Ongoing" | "Done" | "Cancelled";
export type BookingPlatform = "Messenger" | "Viber";

export interface RawQuotationItemRecord {
  item_name: string;
  pricing_details: Record<string, unknown> | null;
}

export interface RawQuotationEstimateRecord {
  quotation_number: string;
  pdf_r2_object_key: string | null;
  created_at: string;
  quotation_items: RawQuotationItemRecord[];
}

export interface RawSignedBookingLinkRecord {
  quotation: RawQuotationEstimateRecord | null;
}

export interface RawProfileRecord {
  full_name: string | null;
  email: string | null;
  contact_number: string | null;
}

export interface BookingRequestWithRelationsRow {
  booking_request_id: string;
  status: BookingDatabaseStatus;
  created_at: string;
  selected_platform: BookingPlatform;
  booking_link: RawSignedBookingLinkRecord | null;
  customer: RawProfileRecord | null;
}

export interface DashboardRecentBookingRow {
  booking_request_id: string;
  status: BookingDatabaseStatus;
  customer: { full_name: string | null } | null;
  booking_link: {
    quotation: {
      quotation_items: RawQuotationItemRecord[];
    } | null;
  } | null;
}
```

The query must bind these types with `.overrideTypes<..., { merge: false }>()`; annotating a `.map()` callback alone is not an acceptable query contract. No new `any` may be introduced in touched files.

### 5.3 Fixture Summary Mapping Contract
`src/features/admin/bookings/adminBookingMapper.ts` shall contain pure functions used by both admin views. It shall not treat `quotation_items.length` as a product count because ERD-E14 stores BOM groups.

For each quotation item:

1. Read `pricing_details.item_id`, `pricing_details.product_name`, and `pricing_details.item_quantity` only after type guards confirm their runtime types.
2. Deduplicate fixture records by `item_id`. If `item_id` is absent, use `product_name` as the compatibility key for older single-product quotations.
3. Count each fixture quantity once, not once per BOM group.
4. Show up to two distinct fixture names and append `and N more` for additional distinct fixtures.
5. If no valid product metadata exists, use `Product details unavailable`. Never label BOM group rows as products.
6. Map database statuses through exhaustive functions: `Ongoing` to `Reviewing` and `Done` to `Confirmed` on the bookings page; `Ongoing` to `Pending` and `Done` to `Confirmed` on the dashboard.

For the bookings page, the exact successful summary format is `<total quantity> Product` or `<total quantity> Products`, followed by ` · ` and the name summary. A fixture with quantity greater than one prefixes its name with `<quantity>x`. If product metadata is unavailable, the entire summary is `Product details unavailable` and no count is inferred from BOM rows. For the dashboard, use the first distinct product name and append ` and N more` when additional distinct products exist.

The mapper shall expose named functions such as `mapAdminBookingRow`, `mapDashboardBookingRow`, and `summarizeQuotationFixtures` so `node:test` can exercise behavior without rendering React components.

### 5.4 Next.js 16 Rendering and Freshness Contract
Do not add `dynamic = "force-dynamic"` or `revalidate = 0` to the route files. The current server client calls `cookies()`, which makes both routes request-time rendered under the current configuration. This requirement shall be protected by a source contract test confirming the server client continues to call `cookies()` and that `cacheComponents` remains disabled unless a later specification defines the migration.

Freshness behavior is:

- A new request or client navigation executes current Supabase queries.
- Booking mutations invalidate `/admin`, `/admin/bookings`, and `/dashboard`.
- A manual refresh requests and merges a new RSC payload for the current route.
- An idle page does not receive push-based updates in this milestone.

### 5.5 Comprehensive Path Revalidation Protocol
Whenever a booking is recorded or updated, all associated ingress paths must be invalidated:

```typescript
// src/lib/booking/bookingRevalidationPaths.ts
export const BOOKING_REVALIDATION_PATHS = [
  "/admin",
  "/admin/bookings",
  "/dashboard",
] as const;

// src/lib/booking/bookingActions.ts
// This helper remains unexported because a `use server` module may export only async functions.
function revalidateBookingPaths(): void {
  for (const path of BOOKING_REVALIDATION_PATHS) {
    revalidatePath(path);
  }
}
```
This helper shall be invoked by:
1. `recordBookingRequest` (on initial booking insertion).
2. `recordBookingRequest` (on platform/re-submission update).
3. `updateBookingRequestStatus` (on administrator triage and status transition).

### 5.6 Client State Synchronization, Error State, and UI Refresh
In `src/features/admin/bookings/BookingsContent.tsx`:

1. Add a pure reducer and `reconcileBookingState` helper in `src/features/admin/bookings/bookingState.ts`. Replace independently synchronized booking, selection, and editable-status state with that reducer. When a successful `initialBookings` payload changes, preserve the current selection only if that ID still exists, otherwise select the first row. In both cases, reset `currentStatus` from the selected row returned by the new server payload.
2. Accept `loadError?: string | null`. When present, render a visible `role="alert"` message and do not show the successful "No bookings found" state. A failed refresh shall retain any previously displayed client rows instead of replacing them with the error payload's empty array. An initial-load failure naturally has no retained rows. Keep the refresh control available so the administrator can retry.
3. Use `useTransition` for the real refresh lifecycle instead of a fixed timer:

   ```typescript
   const router = useRouter();
   const [isRefreshing, startRefreshTransition] = useTransition();

   const handleManualRefresh = () => {
     startRefreshTransition(() => {
       router.refresh();
     });
   };
   ```

4. After a successful status update, update the local reducer state and call `router.refresh()` inside a transition so dashboard and refreshed server props converge on the persisted database status.
5. Render the refresh button adjacent to `SearchBar` using established GlassFit tokens. It must have `type="button"`, `aria-label="Refresh booking requests"`, `aria-busy`, a disabled state during refresh, a minimum 44 by 44 pixel target, visible focus treatment, and text or screen-reader feedback. Any spin animation must use `motion-reduce:animate-none`.
