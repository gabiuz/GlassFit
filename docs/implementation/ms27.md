## 1. Executive Summary & Problem Context

In the GlassFit back-office architecture (`/admin/staff`), business Owners and Managers govern administrative accounts responsible for catalog authoring, raw materials maintenance, and customer consultation booking triage.

### 1.1 The Reported Defect & Operational Bottleneck

Under the current implementation in `src/app/admin/(protected)/staff/actions.ts` and `src/features/admin/staff/InviteStaffDialog.tsx`, administrative staff invitations do not work in practice. Specifically:

1. **Unreliable Email Dispatch:** The backend relies entirely on `supabase.auth.admin.inviteUserByEmail()`. This method delegates email delivery to Supabase's default mail infrastructure, which experiences silent dropouts, strict rate limits, and generic unbranded layouts that fail Philippine SME operational delivery requirements.
2. **Hard Block on Registered Customers:** When an administrator attempts to invite an individual whose email is already registered as a GlassFit customer, `inviteStaff` queries `public.profiles` and immediately throws an error: `"An account with this email already exists."` Furthermore, Supabase Auth's `inviteUserByEmail` crashes when invoked on an existing `auth.users` record. In real-world fabrication shops, estimators and staff frequently create client accounts first to test the application or book consultations before being officially hired as back-office operators.
3. **Absence of Two-Party Authorization (Out-of-Band Code):** There is no two-party verification mechanism. Anyone with temporary inbox access could claim an administrative seat. The system requires an out-of-band 6-digit verification code generated for the inviting administrator that must be entered by the invited staff member during activation.
4. **Disjointed Activation & Password Experience:** The current activation form (`AdminInviteForm.tsx`) only requests a password and confirm password. It does not capture the staff member's Philippine mobile number (`+639XXXXXXXXX`), nor does it visually match the high-end GlassFit customer registration experience.
5. **Missing Staff Removal for Owners:** The actions menu (`StaffActionsMenu.tsx`) provides only "Suspend", "Reactivate", and "Resend Invite". There is no mechanism for an Owner to formally remove or de-escalate a staff member from the administrative roster.
6. **Inoperative Resend Invite:** The "Resend Invite" action triggers the same brittle Supabase admin API without refreshing verification credentials or providing feedback to the administrator.

### 1.2 Required System Behavior

To address these requirements, the staff management workflow must function as follows:

1. **Email Invitation Input:** The administrator inputs the staff member's email address in `/admin/staff`.
2. **6-Digit Admin Verification Code:** Upon invite creation, the system generates a cryptographically random 6-digit numeric verification code (OTP) and displays it directly to the inviting administrator in a confirmation modal. The administrator communicates this code to the staff member through an out-of-band channel (e.g. In-person, phone call, SMS, or internal company chat).
3. **Branded Email with Activation Link:** The staff member receives an email delivered via Resend. The email uses the official GlassFit design system (dark teal header, logo, clean typography, cyan action button) and contains a secure activation link: `${origin}/admin/invite?token=${token}`.
4. **Staff Activation Form:** Upon opening the link, the staff member must enter the identical 6-digit code received from the administrator, their Philippine contact number, and a new password with password confirmation. The interface and password validation rules strictly replicate the customer registration screen (`RegisterForm.tsx`).
5. **Customer-to-Staff Promotion:** If the invited email address belongs to an existing customer, the account is seamlessly promoted to an Admin profile with the Staff role upon successful code verification, preserving previous records while granting back-office access.
6. **Owner-Exclusive Staff Removal:** Users with the "Owner" title are empowered to remove staff members, immediately revoking all back-office sessions and resetting their administrative access.
7. **Reliable Resend Action:** Resending an invitation regenerates/refreshes the 6-digit code and token, re-dispatches the branded Resend email, and presents the new code to the administrator.

## 3. Architecture & Security Workflow Invariants

### 3.1 Two-Factor Out-of-Band Staff Invitation Architecture

To prevent unauthorized account takeovers and eliminate dependency on unauthenticated email registration, GlassFit implements a two-party verification model:

```
[Administrator (Owner)]                  [GlassFit Backend]                  [Invited Staff Member]
         │                                       │                                     │
         │ 1. Submits email in /admin/staff      │                                     │
         ├──────────────────────────────────────>│                                     │
         │                                       │ 2. Generates 64-char token          │
         │                                       │    Generates 6-digit code           │
         │                                       │    Inserts staff_invitations record │
         │                                       │                                     │
         │                                       │ 3. Dispatches Branded Email via     │
         │                                       │    Resend with link                 │
         │                                       ├────────────────────────────────────>│
         │ 4. Receives 6-digit code on UI        │                                     │
         │<──────────────────────────────────────┤                                     │
         │                                       │                                     │
         │ 5. Communicates 6-digit code out-of-band (In-person, SMS, Voice, Chat)      │
         │────────────────────────────────────────────────────────────────────────────>│
         │                                       │                                     │
         │                                       │ 6. Clicks link in email             │
         │                                       │    Opens /admin/invite?token=...    │
         │                                       │<────────────────────────────────────┤
         │                                       │                                     │
         │                                       │ 7. Submits 6-digit code, phone,     │
         │                                       │    and new password                 │
         │                                       │<────────────────────────────────────┤
         │                                       │                                     │
         │                                       │ 8. Verifies code, updates auth user,│
         │                                       │    promotes profile to Admin/Staff  │
         │                                       │    Marks invite Accepted            │
         │                                       │                                     │
         │                                       │ 9. Redirects to /admin or login     │
         │                                       ├────────────────────────────────────>│
```

1. **Party 1 (Inviting Admin):** Submits the email address. The server creates the invitation record, generates both a 64-character URL token and a random 6-digit verification code, and displays the 6-digit code to the Admin on screen.
2. **Party 2 (Delivery Channel):** The system dispatches an HTML email via Resend to the invited email containing the activation link: `${origin}/admin/invite?token=${token}`. The email deliberately does NOT include the 6-digit code.
3. **Party 3 (Invited Staff Member):** Receives the email, clicks the link, and arrives at the activation portal. To complete registration, the staff member must enter the 6-digit code obtained directly from the administrator, their Philippine contact number, and a new password conforming to customer registration rules.
4. **Out-of-Band Security Guarantee:** Compromising either the email inbox alone or the administrator's physical workspace alone is insufficient to compromise administrative back-office access. Both channels must be satisfied.

### 3.2 Account Transition & Customer Promotion Model

A major point of friction in the existing system is the hard block when an invited staff email already belongs to a registered customer.

The account transition model enforces the following rules:

1. **Existing Active Admin:** If `profiles.email` exists and `account_type = 'Admin'` with `status = 'Active'`, the invitation is rejected: `"This user is already an active administrator."`
2. **Existing Customer Account:** If `profiles.email` exists and `account_type = 'Customer'`:
   - The invitation is created successfully.
   - Upon entering the correct 6-digit code, phone, and password, the existing `auth.users` record is updated with the new password and phone via `service.auth.admin.updateUserById()`.
   - The associated `public.profiles` record is updated:
     - `account_type = 'Admin'`
     - `admin_role_id = <Staff_Role_UUID>`
     - `phone = <Normalized_Phone>`
     - `status = 'Active'`
     - `updated_at = now()`
   - All historical customer requests, configurations, and bookings remain intact, preserving foreign key integrity while granting administrative permissions.
3. **Brand New User:** If no record exists in `auth.users` or `public.profiles`:
   - The user is created via `service.auth.admin.createUser({ email, password, email_confirm: true, phone, user_metadata: { first_name, last_name } })`.
   - The profile is created or updated via upsert with `account_type = 'Admin'`, `admin_role_id = <Staff_Role_UUID>`, and `status = 'Active'`.

### 3.3 Role Hierarchy & Owner Deletion Invariant

Back-office account management adheres to strict role authorization boundaries:

| Acting User Role | Target User Role | Permitted Actions | Restricted Actions |
|---|---|---|---|
| **Owner** | Staff | View, Suspend, Reactivate, Resend Invite, **Remove Staff** | None |
| **Owner** | Another Owner | View | Suspend, Reactivate, Remove (Cannot remove fellow Owners) |
| **Owner** | Self | View | Suspend, Remove (Cannot remove or suspend self) |
| **Manager** | Staff | View, Suspend, Reactivate, Resend Invite | **Remove Staff** (Forbidden) |
| **Staff** | Anyone | View (if granted) | All mutations |

When an Owner removes a staff member:
1. Target `profile_id` must have `admin_roles.role_name.toLowerCase() === 'staff'`.
2. Target `profile_id` must NOT equal the acting Owner's `profile_id`.
3. All active authentication sessions for the target user are immediately revoked via `service.auth.admin.signOut(targetProfileId, "others")`.
4. The target profile is demoted to prevent orphaned relational records:
   - `account_type = 'Customer'`
   - `admin_role_id = NULL`
   - `status = 'Inactive'` (or `'Active'` if retained as client)
5. Any pending invitations associated with the target email are transitioned to `status = 'Revoked'`.

## 4. Database Persistence & Migration Schema

To persist invitations, 6-digit codes, expiration timestamps, and audit references, a dedicated relational table `public.staff_invitations` is introduced via migration `010_staff_invitations_and_roles.sql`.

### 4.1 Migration DDL (`supabase/migrations/010_staff_invitations_and_roles.sql`)

```sql
-- Migration: 010_staff_invitations_and_roles.sql
-- Description: Establishes staff_invitations persistence table, status constraints, and RLS policies

-- 1. Create public.staff_invitations table
CREATE TABLE IF NOT EXISTS public.staff_invitations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email VARCHAR(255) NOT NULL,
    token VARCHAR(64) UNIQUE NOT NULL,
    verification_code VARCHAR(6) NOT NULL,
    role_id UUID NOT NULL REFERENCES public.admin_roles(role_id) ON DELETE CASCADE,
    invited_by UUID NOT NULL REFERENCES public.profiles(profile_id) ON DELETE CASCADE,
    status VARCHAR(20) NOT NULL DEFAULT 'Pending',
    expires_at TIMESTAMPTZ NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT staff_invitations_status_check CHECK (status IN ('Pending', 'Accepted', 'Expired', 'Revoked')),
    CONSTRAINT staff_invitations_code_check CHECK (verification_code ~ '^[0-9]{6}$')
);

-- 2. Indexes for query optimization
CREATE INDEX IF NOT EXISTS idx_staff_invitations_token ON public.staff_invitations(token);
CREATE INDEX IF NOT EXISTS idx_staff_invitations_email ON public.staff_invitations(lower(email));
CREATE INDEX IF NOT EXISTS idx_staff_invitations_status ON public.staff_invitations(status);

-- 3. Trigger for updated_at
CREATE OR REPLACE TRIGGER set_staff_invitations_updated_at
BEFORE UPDATE ON public.staff_invitations
FOR EACH ROW EXECUTE FUNCTION public.set_updated_at();

-- 4. Enable Row Level Security (RLS)
ALTER TABLE public.staff_invitations ENABLE ROW LEVEL SECURITY;

-- 5. RLS Policies
-- Only authenticated Admins with manage_roles permission can read invitations
CREATE POLICY "staff_invitations_admin_read" ON public.staff_invitations
    FOR SELECT TO authenticated
    USING (
        EXISTS (
            SELECT 1 FROM public.profiles p
            JOIN public.admin_roles r ON r.role_id = p.admin_role_id
            WHERE p.profile_id = auth.uid()
            AND p.account_type = 'Admin'
            AND p.status = 'Active'
            AND (r.role_name = 'Owner' OR (r.permissions->>'manage_roles')::boolean = true)
        )
    );

-- Mutations restricted to service role client (via Server Actions)
CREATE POLICY "staff_invitations_service_all" ON public.staff_invitations
    FOR ALL TO service_role
    USING (true)
    WITH CHECK (true);
```

## 6. Server Actions & Backend Workflow Contracts

All staff lifecycle operations are implemented as Next.js Server Actions in `src/app/admin/(protected)/staff/actions.ts` and `src/app/admin/(auth)/invite/actions.ts`.

### 6.1 `inviteStaff` Server Action

```typescript
export type InviteStaffResult =
    | {
          success: true;
          message: string;
          verificationCode: string;
          email: string;
          expiresAt: string;
      }
    | { success: false; error: string };

export async function inviteStaff(formData: {
    email: string;
    firstName?: string;
    lastName?: string;
}): Promise<InviteStaffResult>;
```

#### Operational Logic:
1. **Authorization Gate:** Calls `requirePermission("manage_roles")`.
2. **Email Sanitization:** Normalizes `formData.email.trim().toLowerCase()`. Validates format via `validateEmail()`.
3. **Role Verification:** Queries `public.admin_roles` for active `Staff` role. Fails if role is unavailable.
4. **Existing Account Inspection:**
   - Queries `public.profiles` for `trimmedEmail`.
   - If profile exists and `account_type === 'Admin'` with `status === 'Active'`, returns `{ success: false, error: "This user is already an active administrator." }`.
   - If profile exists and `account_type === 'Customer'`, logs intention to promote upon activation.
5. **Pending Invitation Check:**
   - Queries `public.staff_invitations` for active `Pending` invites for this email.
   - If active invite exists and not expired, revokes existing record (`status = 'Revoked'`).
6. **Credential Generation:**
   - Generates 64-character hex URL token: `crypto.randomBytes(32).toString("hex")`.
   - Generates 6-digit numeric verification code: `Math.floor(100000 + Math.random() * 900000).toString()`.
   - Computes expiration cutoff: `new Date(Date.now() + 48 * 60 * 60 * 1000).toISOString()`.
7. **Database Persistence:**
   - Inserts record into `public.staff_invitations` via service client with `status = 'Pending'`.
8. **Resend Email Delivery:**
   - Constructs activation URL: `${origin}/admin/invite?token=${token}`.
   - Dispatches branded email via `sendStaffInviteEmail({ to: trimmedEmail, activationUrl })`.
   - If email dispatch fails, throws error and removes pending database row to prevent phantom invites.
9. **Return Payload:** Returns `{ success: true, verificationCode, email: trimmedEmail, expiresAt, message: "..." }`. The 6-digit code is returned so the Admin UI can display it immediately.

```typescript
};

export type CompleteStaffRegistrationResult =
    | { success: true; message: string; email: string }
    | { success: false; error: string };

export async function completeStaffRegistration(
    input: CompleteStaffRegistrationInput
): Promise<CompleteStaffRegistrationResult>;
```

#### `completeStaffRegistration` Operational Logic:
1. **Token & Code Validation:**
   - Looks up `staff_invitations` record by `token`.
   - Verifies `status === 'Pending'`.
   - Verifies `now() < expires_at`.
   - Validates that `input.verificationCode.trim() === invitation.verification_code`. If incorrect, increments attempt count or fails with `"Invalid 6-digit verification code. Please request the correct code from your administrator."`
2. **Phone Number & Password Validation:**
   - Validates phone format via `validatePhoneNumber(input.phone)`.
   - Checks password requirements via `checkPasswordRequirements(input.password)`. Both must pass.
   - Normalizes phone to E.164 via `normalizePhoneNumber(input.phone)` (`+639XXXXXXXXX`).
3. **Identity Resolution & Promotion:**
   - Checks if user exists in Supabase `auth.users` via `service.auth.admin.getUserByEmail(invitation.email)`:
     - **Branch A: User Exists (e.g. Existing Customer):**
       - Updates auth user password: `service.auth.admin.updateUserById(existingUser.id, { password: input.password, phone: normalizedPhone })`.
       - Updates `public.profiles`:
         ```sql
         UPDATE public.profiles
         SET account_type = 'Admin',
             admin_role_id = invitation.role_id,
             phone = normalizedPhone,
             status = 'Active',
             updated_at = now()
         WHERE profile_id = existingUser.id;
         ```
     - **Branch B: Brand New User:**
       - Creates user: `service.auth.admin.createUser({ email: invitation.email, password: input.password, phone: normalizedPhone, email_confirm: true })`.
       - Upserts `public.profiles` with `profile_id`, `account_type = 'Admin'`, `admin_role_id = invitation.role_id`, `status = 'Active'`.
4. **Mark Invitation Accepted:**
   - Updates `staff_invitations`: `status = 'Accepted'`, `updated_at = now()`.
5. **Audit Logging & Return:**
   - Revalidates `/admin/staff`.
   - Returns `{ success: true, message: "Staff account activated successfully.", email: invitation.email }`.

### 6.3 `resendStaffInvite` Server Action

```typescript
export async function resendStaffInvite(email: string): Promise<InviteStaffResult>;
```

#### Operational Logic:
1. Calls `requirePermission("manage_roles")`.
2. Locates existing `staff_invitations` record for `email.trim().toLowerCase()`.
3. Generates a fresh 6-digit verification code and fresh 64-character URL token.
4. Extends `expires_at` to `Date.now() + 48 hours`.
5. Updates the database record with the new code, token, and expiration timestamp.
6. Re-dispatches the branded Resend email.
7. Returns `{ success: true, verificationCode: newCode, email, expiresAt, message: "..." }` so the administrator can immediately view the renewed code.

### 6.4 `removeStaff` Server Action (Owner Exclusive)

```typescript
export async function removeStaff(targetProfileId: string): Promise<StaffActionResult>;
```

#### Operational Logic:
1. **Authorization Gate:** Calls `requireOwner()` from `src/lib/auth/admin.ts`.
2. **Self-Deletion Ban:** If `ctx.profileId === targetProfileId`, rejects with `"You cannot remove your own account."`
3. **Target Validation:**
   - Queries `public.profiles` joined with `public.admin_roles` for `targetProfileId`.
   - If profile does not exist or `account_type !== 'Admin'`, returns error.
   - If target role is `Owner`, returns error: `"Owners cannot be removed through this interface."`
4. **Session Invalidation:**
   - Calls `service.auth.admin.signOut(targetProfileId, "others")` to invalidate all active session tokens.
5. **Account De-escalation & Relational Integrity Preservation:**
   - To avoid deleting historical client booking consultations, quotation overrides, and catalog records created by the staff member, the system de-escalates the account:
     ```sql
     UPDATE public.profiles
     SET account_type = 'Customer',
         admin_role_id = NULL,
         status = 'Inactive',
         updated_at = now()
     WHERE profile_id = targetProfileId;
     ```
6. **Revoke Active Invitations:**
   - Updates any `Pending` invitations for this profile's email to `Revoked`.
7. **Cache Revalidation:**
   - Calls `revalidatePath("/admin/staff")`.
   - Returns `{ success: true, message: "Staff member has been removed and back-office access revoked." }`.
