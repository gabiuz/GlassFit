> **Identifier note:** `IMP-MS34` succeeds `IMP-MS33` (Unified Cross-Browser GlassFit Brand Theme Scrollbar System) in the sequential implementation specification series in `docs/implementation/`. This specification resolves a critical production-only defect where the image upload and CV analysis pipeline operates correctly on localhost but returns HTTP 502 Bad Gateway after approximately 6-7 seconds on the deployed Vercel + Railway infrastructure. The user-facing symptom is the `ImageErrorModal` appearing with "Image analysis failed." followed by "Please upload a clearer photo and try again." The root cause is the FastAPI Uvicorn worker process being killed by the Railway container runtime due to memory exhaustion when three ML models (YOLOv8s-seg instance segmentation, Depth Anything V2 monocular depth estimation, and SegFormer ADE20K semantic scene segmentation) are loaded and executed concurrently during the `/analyze-image` request handler.

## 1. Executive Summary & Problem Context

The GlassFit visualization pipeline relies on a client-side `fetch()` call from the user's browser directly to the FastAPI CV microservice at the `/analyze-image` endpoint. Locally, this pipeline runs on the developer's workstation, which typically has 8-32 GB of RAM. In production, the FastAPI service is deployed to Railway, where container memory is constrained (typically 512 MB on the free tier, 8 GB on the Pro tier with default limits).

### 1.1 The Reported Defect & Architectural Root Cause

When a user uploads a room photo on the deployed Vercel frontend:
- The browser sends a `POST /analyze-image` request to the Railway-hosted FastAPI service.
- The request reaches the Railway service (CORS and environment variables are correctly configured).
- The FastAPI handler begins processing: EXIF extraction, orientation correction, brightness analysis, lighting analysis.
- The handler then enters the heavy ML inference pipeline, sequentially loading and running three models.
- Approximately 6-7 seconds into processing, Railway's container runtime kills the Uvicorn worker process due to memory exhaustion (OOM).
- Railway's reverse proxy returns HTTP **502 Bad Gateway** because the upstream worker is no longer alive.
- The browser receives the 502, and the `ImageErrorModal` is displayed.

**Confirmed diagnostic evidence:**
- Browser DevTools Network tab shows: `analyze-image | 502 | fetch | 6.62s | 0.0 kB` (zero response body, worker died before sending a response).
- Railway health check `GET /health` returns `{"status": "ok"}` successfully (this endpoint does not invoke ML models).
- `NEXT_PUBLIC_IMAGE_API_URL` is correctly set to the Railway public URL on Vercel.
- `ALLOWED_ORIGINS` is correctly set to the Vercel domain on Railway.

### 1.2 Memory Budget Analysis

The three ML models loaded during `/analyze-image` have the following approximate memory footprints when fully loaded into CPU memory with PyTorch:

| Model | Source File | Model Identifier | Disk Size | Estimated CPU RAM (Inference) | Purpose |
|---|---|---|---|---|---|
| YOLOv8s-seg | [segmentation.py](file:///c:/Users/reyna/GlassFit/fastapi-service/segmentation.py) | `yolov8s-seg.pt` (bundled) | ~24 MB | 150-300 MB | Instance segmentation of room objects (chairs, tables, etc.) |
| Depth Anything V2 Small | [depth.py](file:///c:/Users/reyna/GlassFit/fastapi-service/depth.py) | `depth-anything/Depth-Anything-V2-Small-hf` (HuggingFace) | ~100 MB | 300-500 MB | Monocular depth map estimation |
| SegFormer B0 ADE20K | [scene_detection.py](file:///c:/Users/reyna/GlassFit/fastapi-service/scene_detection.py) | `nvidia/segformer-b0-finetuned-ade-512-512` (HuggingFace) | ~14 MB | 100-200 MB | Semantic scene segmentation (floor, wall, ceiling detection) |
| **Python + PyTorch + OpenCV + Uvicorn runtime** | N/A | N/A | N/A | 200-400 MB | Interpreter, framework, and library baseline |
| **Image processing buffers** | N/A | N/A | N/A | 50-150 MB | Input image, intermediate arrays, mask buffers, depth arrays |
| **Total estimated peak** | | | | **800-1550 MB** | |

On a developer workstation with 8+ GB RAM, this fits comfortably. On a Railway container with 512 MB (free tier) or even the default memory allocation on Pro tier, this exceeds the available memory, triggering an OOM kill.

### 1.3 Why It Works Locally

On a developer workstation:
- Typical available RAM: 8-32 GB.
- All three ML models load and execute concurrently without approaching memory limits.
- PyTorch CPU inference completes within 5-15 seconds depending on hardware.
- The full response is returned successfully.

### 1.4 Why It Fails on Railway

On the Railway container:
- Available RAM is constrained by the container's memory limit (Railway allocates based on plan tier and configuration).
- The `warmup_models()` startup function in [`main.py`](file:///c:/Users/reyna/GlassFit/fastapi-service/main.py#L66-L89) attempts to pre-load all three models at container startup. If startup succeeds (models fit in memory at rest), the container reports healthy.
- When `/analyze-image` is called, all three models execute sequentially but remain loaded in memory simultaneously. Combined with the input image buffers, intermediate processing arrays (depth maps, segmentation masks, resized workspace images), and Python runtime overhead, peak memory usage exceeds the container limit.
- The Linux OOM killer terminates the Uvicorn worker process. Railway's reverse proxy detects the dead upstream and returns 502 Bad Gateway.
- The 6.62s timing suggests the crash occurs during or after the Depth Anything V2 inference step, which is the most memory-intensive operation.

### 1.5 Required System Behavior

To resolve this defect, the following strategies are available (in order of implementation priority):

1. **Increase Railway Container Memory:** Upgrade the Railway service plan or increase the container memory limit to at least 2 GB (preferably 4 GB) to accommodate all three ML models concurrently. This is the simplest fix with zero code changes.

2. **Graceful Model Unloading (Sequential Load/Unload):** Modify the inference pipeline to load each model, run inference, extract results, and then explicitly unload the model (`del model; gc.collect(); torch.cuda.empty_cache()` for GPU or equivalent CPU cleanup) before loading the next model. This reduces peak memory to approximately the size of the single largest model plus runtime overhead.

3. **Configurable Pipeline Stage Toggles:** Introduce environment variables (`ENABLE_DEPTH_ESTIMATION`, `ENABLE_SCENE_DETECTION`) that allow disabling non-essential pipeline stages on memory-constrained deployments. The visualization workspace already handles missing depth and scene data gracefully (the fields are optional in the `ImageAnalysisResponse` interface).

4. **Uvicorn Worker Timeout Configuration:** Set an explicit Uvicorn timeout in [nixpacks.toml](file:///c:/Users/reyna/GlassFit/fastapi-service/nixpacks.toml) to prevent Railway's proxy from timing out before the worker completes inference. This addresses the timeout component but not the OOM component.

5. **Defensive Error Messaging:** Enhance the `analyzeImage()` function in [`src/lib/imageApi.ts`](file:///c:/Users/reyna/GlassFit/src/lib/imageApi.ts) to distinguish 502 gateway errors from image quality issues, providing more actionable user-facing messages.

### 1.6 Scope Boundaries & Non-Goals

- **Non-Goal (GPU Inference):** Railway does not provide GPU-accelerated containers on standard plans. The CPU-only PyTorch configuration (`torch==2.13.0+cpu`) in `requirements.txt` is correct and intentional.
- **Non-Goal (Model Quantization or Distillation):** Reducing model precision (INT8, FP16) or using distilled model variants is not in scope for this milestone but may be explored in future optimizations.
- **Non-Goal (Server-Side Proxy through Vercel):** Routing image uploads through a Next.js API route would hit Vercel's 4.5 MB serverless function body limit and is architecturally undesirable.
- **Non-Goal (Switching Cloud Providers):** The specification addresses the defect within the existing Vercel + Railway deployment topology.

## 4. Implementation Specification

### 4.1 Strategy A: Increase Railway Container Memory (Infrastructure-Only Fix)

If the Railway plan supports memory configuration:

1. Navigate to the Railway dashboard for the FastAPI service.
2. Under service settings, increase the memory limit to at least **2 GB** (recommended: **4 GB** for comfortable headroom).
3. Redeploy the service.
4. Verify `/analyze-image` completes successfully with a room photo upload.

This is the simplest fix and requires zero code changes. However, it may require a paid Railway plan upgrade.

### 4.2 Strategy B: Sequential Model Load/Unload with Explicit Memory Reclamation

Modify the inference pipeline to avoid holding all three models in memory simultaneously. Each model is loaded, used, results extracted, and then explicitly freed before loading the next model.

**Target modifications in `fastapi-service/main.py`:**

The `analyze_image()` handler currently calls `analyze_objects()`, `estimate_depth()`, and `detect_scene_regions()` sequentially, but each function caches its model in a global variable (`_YOLO_MODEL_CACHE`, `_depth_pipe`, `_scene_model`) so all three persist in memory simultaneously.

Introduce an environment variable `CONSERVE_MEMORY` (default `false`) that, when set to `true` or `1`, causes each model module to release its cached model after inference:

```python
import gc

def _should_conserve_memory() -> bool:
    return os.getenv("CONSERVE_MEMORY", "").lower() in ("1", "true", "yes")
```

After each inference stage in `analyze_image()`, if memory conservation is enabled, clear the model cache:

```python
# After segmentation
segmentation_result = analyze_objects(upload_path, session_mask_dir)
# ... extract results ...
if _should_conserve_memory():
    from segmentation import _YOLO_MODEL_CACHE
    _YOLO_MODEL_CACHE.clear()
    gc.collect()

# After depth estimation
depth_result = estimate_depth(image_bgr, upload_id, ...)
# ... extract results ...
if _should_conserve_memory():
    import depth as depth_module
    depth_module._depth_pipe = None
    gc.collect()

# After scene detection
scene_result = detect_scene_regions(image_bgr, upload_id, ...)
# ... extract results ...
if _should_conserve_memory():
    import scene_detection as scene_module
    scene_module._scene_processor = None
    scene_module._scene_model = None
    gc.collect()
```

When `CONSERVE_MEMORY=true`, peak memory usage drops from ~1.2-1.5 GB (all models loaded) to ~500-600 MB (single largest model + runtime). Models are re-downloaded from HuggingFace cache on each request, but the HuggingFace `transformers` library caches model weights on disk, so subsequent loads read from disk cache (no network download).

**Railway environment variable:**

| Variable Name | Value | Rationale |
|---|---|---|
| `CONSERVE_MEMORY` | `true` | Enables sequential model unloading to reduce peak memory on Railway |

When this variable is set, the `warmup_models()` startup function should also be skipped or modified to avoid pre-loading models that will be immediately unloaded.

### 4.3 Strategy C: Configurable Pipeline Stage Toggles

Introduce environment variables to disable non-essential ML pipeline stages entirely on memory-constrained deployments:

| Variable Name | Default | Effect When Set to `false` |
|---|---|---|
| `ENABLE_DEPTH_ESTIMATION` | `true` | Skips Depth Anything V2 inference; returns `{ "available": false, "mode": "disabled" }` |
| `ENABLE_SCENE_DETECTION` | `true` | Skips SegFormer scene segmentation; returns `{ "available": false, "method": "disabled" }` |

The visualization workspace already handles missing depth and scene data gracefully:
- `depth?: DepthAnalysis` is optional in the `ImageAnalysisResponse` interface ([imageApi.ts line 90](file:///c:/Users/reyna/GlassFit/src/lib/imageApi.ts#L90)).
- `scene?: SceneAnalysis` is optional in the `ImageAnalysisResponse` interface ([imageApi.ts line 91](file:///c:/Users/reyna/GlassFit/src/lib/imageApi.ts#L91)).

Disabling both depth and scene detection reduces peak memory to just YOLOv8s-seg (~300-500 MB total including runtime), which fits comfortably in Railway's default allocation. The tradeoff is reduced visualization quality (no depth-aware product placement and no automatic floor/wall detection), but the core functionality (room photo with object segmentation and brightness/lighting analysis) remains fully operational.

### 4.4 Uvicorn Timeout Configuration in `nixpacks.toml`

The current Uvicorn start command in `nixpacks.toml` does not specify a request timeout:

```toml
[start]
cmd = "uvicorn main:app --host 0.0.0.0 --port ${PORT:-8000}"
```

On CPU-only inference with constrained resources, the ML pipeline can take 30-60 seconds. Add an explicit `--timeout-keep-alive` and consider adding `--timeout-graceful-shutdown` to prevent Railway's proxy from timing out before inference completes:

```toml
[start]
cmd = "uvicorn main:app --host 0.0.0.0 --port ${PORT:-8000} --timeout-keep-alive 120"
```

Note: This addresses timeout issues but does not resolve OOM crashes. If the worker is OOM-killed, no timeout configuration can prevent the 502.

### 4.5 Defensive Error Messaging Enhancement in `src/lib/imageApi.ts`

The current `analyzeImage()` function does not distinguish between network-level failures, 502 gateway crashes, and HTTP error responses from the FastAPI server. When a 502 is received with an empty body, `response.json()` throws, and the generic "Image analysis failed." message is shown, which is misleading because it implies the photo is at fault.

**Target modification in `src/lib/imageApi.ts`:**

```typescript
export async function analyzeImage(file: File): Promise<SpaceImageSession> {
  const formData = new FormData();
  formData.append("image", file);

  const apiBaseUrl = getImageApiBaseUrl();
  let response: Response;

  try {
    response = await fetch(`${apiBaseUrl}/analyze-image`, {
      method: "POST",
      body: formData,
    });
  } catch (networkError) {
    console.error(
      "[GlassFit] Image analysis network error. Verify NEXT_PUBLIC_IMAGE_API_URL " +
      `(${apiBaseUrl}) is reachable and CORS is configured for this origin.`,
      networkError,
    );
    throw new Error(
      "Could not connect to the image analysis service. Please try again later.",
    );
  }

  if (!response.ok) {
    // 502/503 from Railway indicates the worker crashed (likely OOM) or is unavailable.
    if (response.status === 502 || response.status === 503) {
      console.error(
        `[GlassFit] Image analysis service returned ${response.status}. ` +
        "The server may have run out of memory during ML inference.",
      );
      throw new Error(
        "The image analysis service is temporarily unavailable. Please try again in a moment.",
      );
    }

    let message = "Image analysis failed.";

    try {
      const errorBody = (await response.json()) as { detail?: string };
      if (errorBody.detail) {
        message = errorBody.detail;
      }
    } catch {
      // Keep the generic message when the service returns non-JSON errors.
    }

    throw new Error(message);
  }

  const payload = (await response.json()) as ImageAnalysisResponse;
  return toSpaceImageSession(payload, file.name, apiBaseUrl);
}
```

This change ensures:
- 502/503 responses produce "The image analysis service is temporarily unavailable." instead of "Image analysis failed."
- Network failures (unreachable server, DNS failure) produce "Could not connect to the image analysis service."
- HTTP 400 errors from FastAPI continue to display server-provided detail messages.
- Developer console logs include diagnostic context pointing to OOM as the likely cause.

## 5. Recommended Implementation Order

| Priority | Strategy | Code Change? | Effect on Memory | Tradeoff |
|---|---|---|---|---|
| 1 | **4.5: Defensive Error Messaging** | Yes (TypeScript) | None | Zero functional impact; better UX for all error types |
| 2 | **4.3: Pipeline Stage Toggles** | Yes (Python) | Reduces peak by 400-700 MB | Loses depth and scene features; core visualization intact |
| 3 | **4.2: Sequential Model Unload** | Yes (Python) | Reduces peak by 500-800 MB | Slower per-request (models reload from disk cache); all features preserved |
| 4 | **4.4: Uvicorn Timeout** | Yes (TOML) | None | Prevents timeout-only failures; does not fix OOM |
| 5 | **4.1: Increase Railway Memory** | No (Infrastructure) | Raises ceiling to 2-4 GB | May require plan upgrade; simplest fix if budget allows |

For the fastest resolution, combine Strategy 4.5 (error messaging) with either Strategy 4.1 (increase memory) or Strategy 4.3 (disable depth + scene on Railway).
