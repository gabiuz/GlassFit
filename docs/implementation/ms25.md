> **Identifier note:** `IMP-MS25` succeeds `IMP-MS24` in the sequential implementation specification series in `docs/implementation/`. While `IMP-MS24` established per-piece jalousie glass ingestion and administrative labor fee entry, `IMP-MS25` resolves a critical regression in administrative booking management (Issue #52): when an admin attempts to negotiate the price of a booking request whose quotation contains only a single product, the interface displays an inconsistent "Edit Final Price" action instead of "Edit Price", and attempting to save results in an unhandled validation rejection ("Invalid ISO datetime"). This specification provides the complete architectural contract to normalize datetime validation with timezone offset tolerance and unify single-product and multi-product quotation price editing.

## 1. Executive Summary & Problem Context

In the GlassFit administrative workbench (`/admin/bookings`), authorized booking managers review customer consultation requests, assess site conditions, adjust installation labor fees, and negotiate final product prices prior to formal confirmation.

### 1.1 The Reported Behavior & Defect Manifestation
Under Milestone 17 (`IMP-MS17`), quotation pricing was migrated from quotation-total negotiation to canonical per-item line subtotal negotiation (`updateItemNegotiatedPrice`). Under this system:
1. **Multi-Product Quotations Work As Designed:** When a quotation has multiple products (e.g. 2 or more fixtures), the admin interface displays a list titled "Per-item final prices" where each fixture displays an **"Edit Price"** button. The administrator can click "Edit Price", specify an agreed final price for that fixture, and save cleanly.
2. **Single-Product Quotations Exhibit Inconsistent UI and Crash:** When a quotation contains only one product, instead of displaying "Edit Price", the UI renders an "Edit Final Price" button accompanied by the message "Per-item editing unavailable for legacy quotation".
3. **Validation Failure ("Invalid ISO datetime"):** When the administrator clicks "Edit Final Price", enters a new price, and clicks "Save", the operation immediately fails, presenting an alert message: **`Invalid ISO datetime`**. The price cannot be saved, blocking booking processing for single-product consultations.

### 1.2 Root Cause Analysis

Investigation of the data layer, schema definitions, and UI rendering logic reveals three interconnected root causes:

#### Root Cause 1: Inconsistent ISO 8601 Datetime Validation Across Zod Schemas
In `src/lib/booking/types.ts`:
- `UpdateNegotiatedPriceInputSchema` (used by the total-level "Edit Final Price" action) defines:
  ```typescript
  expectedUpdatedAt: z.string().datetime()
  ```
  By default in Zod, `.datetime()` strictly requires an ISO 8601 UTC string ending with `Z` (e.g., `2026-09-28T15:19:50.247Z`). It explicitly rejects any ISO string containing a timezone offset such as `+00:00`, `+00`, or `+08:00`.
- In contrast, PostgreSQL `timestamptz` columns (`quotation_estimates.updated_at`) returned via Supabase PostgREST serialize timestamps with timezone offsets (e.g., `2026-09-28T15:19:50.247571+00:00` or `2026-09-28 15:19:50.247571+00`).
- While `UpdateItemNegotiatedPriceInputSchema` was configured with `expectedUpdatedAt: z.string().datetime({ offset: true })` and `UpdateBookingLaborInputSchema` with `z.string().datetime({ offset: true }).or(z.string().datetime())`, `UpdateNegotiatedPriceInputSchema` was never updated to accept timezone offsets.
- Consequently, passing `selectedBooking.quotation.updatedAt` to `updateNegotiatedPrice` immediately causes Zod validation to fail with the exact issue message: `"Invalid ISO datetime"`.

#### Root Cause 2: Asymmetrical Quotation Negotiation Capability Mapping
In `src/features/admin/bookings/adminBookingMapper.ts`:
- Quotation negotiation support is mapped as:
  ```typescript
  supportsItemNegotiation: parsedDocument.success
  ```
  Where `parsedDocument = QuotationDocumentSnapshotV1Schema.safeParse(quotation?.quotation_document_snapshot)`.
- If a quotation is a legacy record (where `quotation_document_snapshot` is `null`), `parsedDocument.success` is `false`. Even though `reconstructLegacyQuotationDocument` successfully reconstructs a single-fixture quotation item, `supportsItemNegotiation` evaluates to `false`.
- In `src/features/admin/bookings/BookingsContent.tsx`:
  - When `supportsItemNegotiation` is `false`, the UI displays:
    ```tsx
    <p className="text-xs text-amber-800">Per-item editing unavailable for legacy quotation</p>
    ...
    <button type="button" onClick={() => setIsEditingPrice(true)}>Edit Final Price</button>
    ```
  - This forces single-product quotations into the legacy `updateNegotiatedPrice` flow.
- Furthermore, in `src/lib/booking/bookingActions.ts`, line 671 explicitly restricts `updateNegotiatedPrice`:
  ```typescript
  if (current.quotation_document_snapshot !== null) {
    return { ok: false, code: "UNSUPPORTED_QUOTATION", message: "Canonical quotations require per-item price editing." };
  }
  ```
  This creates an architectural impasse: canonical quotations are prohibited from using total-level negotiation, yet single-product quotations were routed toward it whenever per-item negotiation capability was misflagged.

#### Root Cause 3: Optimistic Concurrency Inconsistency Across Timestamp Representations
Both `updateNegotiatedPrice` and `updateItemNegotiatedPrice` perform optimistic concurrency checks:
```typescript
if (current.updated_at !== parsed.data.expectedUpdatedAt) {
  return { ok: false, code: "CONFLICT", message: "This quotation was updated in another session. Review the latest values and try again." };
}
```
Direct string comparison (`current.updated_at !== parsed.data.expectedUpdatedAt`) is fragile when timestamps are passed between PostgreSQL, JSON serialization, and client states. Discrepancies between trailing zeros (e.g. `.247000+00` vs `.247+00:00`) or ISO UTC conversions can cause spurious `CONFLICT` rejections even when no concurrent write occurred.

## 3. Architecture & Domain Invariants

### 3.1 Single-Product Negotiation Parity Invariant
Every quotation in GlassFit (whether containing 1 product fixture or N fixtures) must provide a unified, predictable price negotiation experience for administrators. A single-product quotation is architecturally an itemized quotation of length 1:
- The UI must render the standard item card with the **"Edit Price"** button.
- Editing the price of a single product fixture must execute through `updateItemNegotiatedPrice`, recording the override in `item_price_overrides` JSONB.
- The button label must consistently read **"Edit Price"** across all product items, eliminating the confusing "Edit Final Price" label for single fixtures.
- The misleading warning banner "Per-item editing unavailable for legacy quotation" must never appear for valid canonical quotations or successfully reconstructed single-product fixtures.

### 3.2 ISO Datetime Offset Tolerance Invariant
All server action input schemas in `src/lib/booking/types.ts` that accept an `expectedUpdatedAt` timestamp must natively tolerate ISO 8601 strings with or without timezone offsets:
```typescript
expectedUpdatedAt: z.string().datetime({ offset: true }).or(z.string().datetime())
```
No server action may reject a timestamp string simply because it contains a PostgreSQL timezone offset (such as `+00:00`, `+00`, or `+08:00`).

### 3.3 Concurrency & Optimistic Locking Invariant
When validating optimistic concurrency (`expectedUpdatedAt`), server actions must compare timestamp values based on millisecond epoch values (`new Date(current.updated_at).getTime() === new Date(expectedUpdatedAt).getTime()`), or use string normalization that eliminates formatting discrepancies. This prevents false `CONFLICT` rejections caused by varying string serializations of the same instant in time.

### 3.4 Legacy Quotation Fallback Invariant
For historical quotations created prior to snapshot introduction (`quotation_document_snapshot === null`) where line items cannot be reconstructed into canonical items:
- The fallback total-level price editor must function cleanly.
- `updateNegotiatedPrice` must successfully validate the input timestamp without throwing `"Invalid ISO datetime"`.
- Saving a total price override on a legacy quotation must update `negotiated_amount`, `negotiated_by`, and `negotiated_at` as designated by `IMP-MS16`.

## 4. Data Layer, Schema & Server Actions Specifications

### 4.1 Schema Normalization (`src/lib/booking/types.ts`)

Update `UpdateNegotiatedPriceInputSchema` to match the offset-tolerant pattern established in `UpdateBookingLaborInputSchema`:

```typescript
// src/lib/booking/types.ts

export const UpdateNegotiatedPriceInputSchema = z.object({
  quotationId: z.string().uuid(),
  negotiatedAmount: z.number().finite().min(0).max(9_999_999_999.99).nullable().refine(
    (value) => value === null || Math.abs(value * 100 - Math.round(value * 100)) < 1e-7,
    "Negotiated amount must have at most two decimal places",
  ),
  expectedUpdatedAt: z.string().datetime({ offset: true }).or(z.string().datetime()),
});
```

Ensure all booking actions schemas maintain uniform timestamp validation:
- `UpdateNegotiatedPriceInputSchema`: `z.string().datetime({ offset: true }).or(z.string().datetime())`
- `UpdateItemNegotiatedPriceInputSchema`: `z.string().datetime({ offset: true }).or(z.string().datetime())`
- `UpdateBookingLaborInputSchema`: `z.string().datetime({ offset: true }).or(z.string().datetime())`

### 4.2 Optimistic Concurrency Normalization (`src/lib/booking/bookingActions.ts`)

In `updateNegotiatedPrice`, `updateItemNegotiatedPrice`, and `updateBookingLaborCharge`, harden the optimistic concurrency check:

```typescript
// src/lib/booking/bookingActions.ts

function areTimestampsEquivalent(dbTimestamp: string, expectedTimestamp: string): boolean {
  if (dbTimestamp === expectedTimestamp) return true;
  const dbTime = new Date(dbTimestamp).getTime();
  const expectedTime = new Date(expectedTimestamp).getTime();
  return !Number.isNaN(dbTime) && !Number.isNaN(expectedTime) && dbTime === expectedTime;
}
```

In `updateNegotiatedPrice`:
```typescript
if (!areTimestampsEquivalent(current.updated_at, parsed.data.expectedUpdatedAt)) {
  return { ok: false, code: "CONFLICT", message: "This quotation was updated in another session. Review the latest values and try again." };
}
```

In `updateItemNegotiatedPrice`:
```typescript
if (!areTimestampsEquivalent(current.updated_at, parsed.data.expectedUpdatedAt)) {
  return { ok: false, code: "CONFLICT", message: "This quotation was updated in another session. Review the latest values and try again." };
}
```

When executing database updates, match by `quotation_id` and ensure concurrency safety using the database `updated_at` column:
```typescript
const { data: updated, error } = await supabase
  .from("quotation_estimates")
  .update({
    negotiated_amount: pricing.negotiatedFinalPrice,
    negotiated_by: negotiatedBy,
    negotiated_at: negotiatedAt,
  })
  .eq("quotation_id", parsed.data.quotationId)
  .eq("updated_at", current.updated_at)
  .select("updated_at")
  .maybeSingle();
```

### 4.3 Quotation Mapper Reconciliation (`src/features/admin/bookings/adminBookingMapper.ts`)

Ensure that `supportsItemNegotiation` evaluates to `true` whenever an item list with valid IDs is present, including single-product canonical quotations and successfully reconstructed single-fixture quotations:

```typescript
// src/features/admin/bookings/adminBookingMapper.ts

const hasValidItems = Boolean(
  (document && document.items && document.items.length > 0) ||
  (quotation?.quotation_items && quotation.quotation_items.length > 0)
);

const supportsItemNegotiation = parsedDocument.success || (document !== null && document.items.length > 0);
```

When a single-product quotation is processed, its item pricing view is constructed via `deriveQuotationPricingFromItems(document, itemPriceOverrides)`, ensuring that `itemPricing` contains exactly one item with its calculated subtotal, effective subtotal, and modification status.

## 5. UI & Administrative Workflows (`src/features/admin/bookings/BookingsContent.tsx`)

### 5.1 Single-Product Quotation Price Negotiation Experience

In `src/features/admin/bookings/BookingsContent.tsx`:
1. **Per-Item Final Prices Section Rendering:**
   - When `selectedBooking.quotation.supportsItemNegotiation` is `true`, render the `Per-item final prices` container.
   - For single-product quotations, this container renders exactly one fixture card.
   - The card displays:
     - Product Name and Quantity (e.g. `Custom Architectural Fenestration × 1`).
     - Calculated Subtotal: `Calculated: ₱X,XXX.XX`.
     - Effective Subtotal: `₱Y,YYY.XX` in emerald font.
     - "Negotiated" badge if modified.
     - Action buttons: **"Edit Price"** and **"Reset"** (disabled if unmodified).
2. **Inline Item Price Editor:**
   - Clicking **"Edit Price"** opens the inline input:
     - Accessible label: `Final item price for {item.productName}`.
     - Input field with decimal step and current effective value pre-populated.
     - Action buttons: "Save" (invokes `handleItemPriceSave`) and "Cancel".
3. **Execution Path:**
   - Saving calls `saveItemPrice(item.itemId, value)`.
   - `saveItemPrice` invokes `updateItemNegotiatedPrice({ quotationId, itemId, negotiatedSubtotal, expectedUpdatedAt })`.
   - The server validates the timestamp with offset support, updates `item_price_overrides` and `negotiated_amount`, and returns the refreshed pricing view.
   - The UI updates optimistically, displays a success toast ("Item price updated successfully"), and refreshes server components via `router.refresh()`.

### 5.2 Legacy Fallback Price Editor Hardening

For un-reconstructable legacy quotations where `supportsItemNegotiation` is genuinely `false`:
1. The UI renders the legacy pricing view with calculated and final price displays.
2. Clicking **"Edit Final Price"** opens the total price editor.
3. Clicking **"Save"** calls `handlePriceSave()` -> `saveNegotiatedPrice(value)`.
4. `saveNegotiatedPrice` calls `updateNegotiatedPrice`.
5. Because `UpdateNegotiatedPriceInputSchema` now permits timezone offsets, validation succeeds without throwing `"Invalid ISO datetime"`.
6. Concurrency check uses `areTimestampsEquivalent`, preventing spurious rejections.
7. The total is persisted, and the success toast ("Final price updated successfully") is presented.
