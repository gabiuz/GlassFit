**Project:** GlassFit (Web-Based Client-Space Visualization System for Customized Glass & Aluminum)  
**Document ID:** IMP-MS19  
**Document Function:** Implementation contract for the authenticated customer My Requests page  
**Version:** 2.0.0  
**Date:** September 27, 2026  
**Owner:** Reynard John B. Rabanal (Lead Product / Systems Architect) & GlassFit Capstone Team (PUP CCIS)  
**Status:** Implementation Ready. The visual baseline is documented in Section 6.1. Production implementation is not authorized until the human maintainer gives an explicit implementation instruction after reviewing the mockup.  
**Scope:** Authenticated frontend route, deterministic fixture-backed request tracking, customer navigation, and automated state tests. No booking-data query, mutation, migration, or real PDF download is included.  
**Primary Traceability:** PRD-F12, PRD-F17, SDD-C10, DSD-UI12, ERD-E2, QAD-TC32. ERD-E10, ERD-E13, ERD-E15, and ERD-E16 are future live-integration references only.

A later data-integration milestone will replace fixtures with RLS-filtered customer reads without changing the view model or interaction contract defined here.

## 1. Objective and Route Contract

Build `/my-requests` as the dedicated request-tracking destination for authenticated customers and active administrators using the customer-facing application. The existing `/dashboard` route remains the broader PRD-F17 customer overview. `/my-requests` is a subordinate customer-portal screen reached from the profile navigation.

The route must:

1. Verify an authenticated Supabase user on the server.
2. Verify that the linked profile has `account_type = 'Customer'` or `account_type = 'Admin'` and `status = 'Active'`.
3. Redirect an unauthenticated user to `/login?next=/my-requests`.
4. Redirect a profile with an unsupported account type or non-Active status to `/`.
5. Render deterministic fixture data only after authorization succeeds.

The route guard may read authentication and profile identity through the existing server Supabase adapter. It must not query booking, quotation, snapshot, or signed-link tables in this milestone.

Authentication and profile lookup outcomes are distinct:

- Missing Supabase user: redirect to `/login?next=/my-requests`.
- Existing user with no profile, an unsupported account type, or a non-Active profile: redirect to `/`.
- Existing active Customer or Admin profile: render the page.
- Supabase profile query failure: fail closed by throwing the query error into the Next.js route error boundary. Do not render fixture content and do not misclassify an infrastructure failure as an unauthorized profile.

## 3. Canonical Status and Progress Contract

The view model stores the canonical `BookingRequestStatus` from `src/lib/booking/types.ts`. Display labels are derived through one exhaustive mapper. Fixture data must not store alternate display statuses.

| Database status | Customer label | Filter | Badge | Progress behavior |
|---|---|---|---|---|
| `Pending` | Submitted | Active | Amber | Submitted is current; later steps are future |
| `Ongoing` | Under Review | Active | Amber | Submitted is complete; Under Review is current |
| `Done` | Completed | Completed | Green | All three progress steps are complete |
| `Cancelled` | Cancelled | Cancelled | Red | Standard progress is replaced by a red terminal Cancelled state |

The standard progress steps are exactly:

1. Submitted
2. Under Review
3. Completed

Cancelled requests do not infer the stage at which cancellation happened. Their detail panel shows the Cancelled terminal state and the recorded update timeline.

The status banner is conditional:

| Status | Banner title | Supporting copy | Treatment |
|---|---|---|---|
| Submitted | Request received | We will review your consultation PDF and contact you. | Light cyan with cyan icon |
| Under Review | Review in progress | Our team is reviewing the request details. | Light amber with amber icon |
| Completed | Request completed | Your request has been processed. Check the latest update below. | Light green with green check |
| Cancelled | Request cancelled | This request is no longer active. Contact GlassFit if you need assistance. | Light red with red icon |

## 4. Deterministic View Model and Fixtures

`requestData.ts` must define:

```typescript
import type { BookingRequestStatus } from "@/lib/booking/types";

export type RequestFilter = "All" | "Active" | "Completed" | "Cancelled";

export interface RequestUpdate {
  id: string;
  occurredAt: string;
  title: string;
  description: string;
}

export interface ClientRequestQuotation {
  filename: string;
  generatedAt: string;
  availability: "prototype-only";
}

export interface ClientRequestItem {
  id: string;
  referenceNo: string;
  productName: string;
  productCount: number;
  submittedAt: string;
  status: BookingRequestStatus;
  quotation: ClientRequestQuotation;
  updates: RequestUpdate[];
}
```

The fixture array must contain exactly the five records in Appendix A. Their expected filter counts are All 5, Active 2, Completed 2, and Cancelled 1. The fixtures use stable UUIDs, stable `CF-2026-000` references, offset-aware ISO-8601 timestamps, singular and plural product counts, one request with no updates, and one request with five deliberately out-of-order updates.

Pure helper functions must provide exhaustive database-status-to-label, badge, filter, progress, and banner mappings. An unreachable status must fail TypeScript exhaustiveness through a `never` assertion rather than fall back to a default style.

## 5. State and Interaction Contract

`requestState.ts` owns all list-selection state:

```typescript
export interface RequestState {
  requests: ClientRequestItem[];
  selectedRequestId: string;
  activeFilter: RequestFilter;
  expandedTimelineRequestId: string | null;
}
```

Actions are `select`, `set-filter`, and `toggle-timeline`.

State invariants:

1. Initial filter is `All` and the first request is selected.
2. Changing filters retains the selection only when that request remains visible.
3. If the selection becomes hidden, the first visible request is selected.
4. If a filter has no results, `selectedRequestId` becomes an empty string and the detail panel shows an empty state.
5. Returning to a filter with results selects its first visible request when no visible selection exists.
6. Timeline expansion is scoped to the selected request and resets when selection changes.
7. Search and server refresh are not part of this milestone.

Timeline rules:

- Sort updates newest first using `occurredAt`.
- Collapsed mode displays the newest three updates.
- `View all updates` expands in place and becomes `Show latest updates`.
- The toggle is hidden when there are three or fewer updates.
- An empty update list displays `No request updates yet.`

Quotation preview rules:

- `View PDF` opens an accessible prototype dialog containing the fixture filename, generated date, and an explicit preview-unavailable notice.
- `Download PDF` is disabled and accompanied by `Download becomes available when live quotation files are connected.`
- No button may appear active while doing nothing.

## 6. Layout and Responsive Contract

The approved implementation direction must preserve these structural contracts:

- Reuse the GlassFit hero background, gradient heading, colors, radii, shadows, typography, and spacing patterns.
- Page heading: `MY REQUESTS`.
- Filters: All, Active, Completed, Cancelled, each with a deterministic count.
- Desktop Standard from 1024px through 1439px: request list and detail panel are visible side by side within the DSD 1200px maximum container.
- Large Display at 1440px and above: the same two-column composition is centered within the DSD 1400px maximum container.
- Tablet Intermediate from 640px through 1023px: list and detail stack vertically to preserve readable card widths and 44px targets.
- Mobile Compact below 640px: filters scroll horizontally; list and detail stack; the selected detail follows the list.
- Responsive margins and gutters inherit the authoritative values in `docs/dsd-glassfit.md`.
- The page must remain usable at 375px, 768px, 1280px, and 1440px.

The shared hero background must hide continuous video under `prefers-reduced-motion: reduce` and reveal a static gradient or poster fallback.

## 7. Accessibility Contract

- Request cards are semantic `<button type="button">` controls, not clickable `div` elements.
- Each card exposes its selected state with `aria-pressed` and a visible 2px focus ring.
- Filter controls are grouped with an accessible label and use `aria-pressed`.
- All interactive targets are at least 44px by 44px.
- The progress component is an ordered list. The current step uses `aria-current="step"`; completed, current, and future states include text or icons and never rely on color alone.
- The Cancelled terminal state includes visible text and an icon.
- The PDF prototype dialog has a title, initial focus, focus containment, Escape dismissal, close control, and focus restoration.
- Timeline toggle text describes its current action.
- Text and controls must meet WCAG 2.1 AA contrast.
- Motion is limited to transform and opacity, completes within 300ms, and is disabled or reduced when the user requests reduced motion.

## 9. Empty, Loading, and Error States

| State | Required result |
|---|---|
| Authorization pending | Server route does not stream private page content before verification |
| Unauthenticated | Redirect to `/login?next=/my-requests` |
| Unauthorized profile | Redirect to `/` |
| No fixture requests | List shows `You have no consultation requests yet.` with an Explore Catalog link; detail panel is not rendered |
| Filter has no matches | List shows `No requests match this filter.`; detail shows `Choose another filter to view a request.` |
| No updates | Timeline shows `No request updates yet.` |
| Preview opened | Accessible prototype dialog explains that live PDF content is not connected |

No fixture `loadError` state is included because fixture loading cannot fail. Authentication and profile-query failures still follow the fail-closed route behavior in Section 1. The future data-integration milestone must add loading, last-success, and booking-query error behavior when it introduces live request reads.

## 12. Required Automated Tests

`tests/unit/myRequestsState.test.ts` must cover:

1. Exhaustive mapping of all four database statuses.
2. Active filter composition from Pending and Ongoing only.
3. Completed and Cancelled filter membership.
4. Correct deterministic counts for all five fixtures.
5. Initial selection.
6. Selection retention when still visible.
7. First-visible selection when the current request is hidden.
8. Empty selection when a filter has no rows.
9. Timeline newest-first sorting without mutating fixture input.
10. Three-item collapsed timeline and full expanded timeline.
11. Empty update-list behavior.
12. Empty fixture collection initialization.
13. Compile-time exhaustive status mapping through the `never` assertion.

`tests/unit/customerAuthGuard.test.ts` must cover unauthenticated, missing-profile, inactive Customer, inactive Admin, active Customer, active Admin, and profile-query failure outcomes through a dependency-injected or otherwise isolated authorization boundary. The failure case must assert that no fixture payload is returned and that the original query failure is propagated rather than converted into a redirect.

Manual verification must cover responsive overflow at 375px, 768px, 1280px, and 1440px; keyboard request and filter selection; dialog focus containment, Escape dismissal, and focus restoration; authenticated desktop and mobile navigation; and the reduced-motion hero fallback. These checks implement QAD-TC32 and must be recorded in the pull request verification notes.
