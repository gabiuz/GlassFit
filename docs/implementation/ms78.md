## 1. Executive Summary, Outcome, and Problem Context

This milestone specification consolidates two critical capabilities in the administrative product setup pipeline (`/admin/products/[productId]/setup`), unifying non-parametric product part decomposition and geometric bilateral hardware accessory authoring.

### 1.1 Goal 1: Fixed-Price Component Upload for Fixed Visualization Strategy

In architectural glass and aluminum fabrication, not every product is parametric. Fabricators frequently offer pre-fabricated, standardized, or modular catalog units (such as standardized sliding window units, fixed louver vents, pre-assembled shower glass cubicles, or prefabricated aluminum medicine cabinets) configured under Step 2 (**Visualization Strategy**) as `model_strategy = 'Fixed'`.

Under previous workflows:
1. When an administrator configured a product strategy as `Fixed`, Step 3 (**Structural Components**) was completely suppressed by a hardcoded short-circuit in `StructuralComponentsSection.tsx` (`if (modelStrategy !== "Parametric") return <NotApplicableNotice />`).
2. This prevented administrators from uploading constituent 3D mesh components (e.g. glass panels, sub-frames, handles, sills) for fixed products.
3. If fabricators wanted to itemize individual sub-assemblies or incorporate swappable accessories (such as alternative door handles on a fixed swing door), they were forced to mark the product as `Parametric`, which in turn forced them to map every component to linear-meter extrusions, glass stock sheets, scrap allowances, and formulas in the raw materials catalog (`raw_materials`).
4. For pre-fabricated units, fabricators purchase or assemble units at a known unit cost (PHP). They do not calculate linear-meter saw cuts for fixed models.

**Planned Outcome for Goal 1:**
- When `model_strategy = 'Fixed'`, Step 3 (**Structural Components**) remains fully unlocked and functional. Administrators can upload decomposed or discrete `.glb` meshes for the fixed fixture.
- In `PartInspectorDrawer.tsx`, the inspector detects that the product is a Fixed model (or the pricing method is fixed) and renders a direct **Fixed Component Price (PHP)** numeric input field.
- Material assignment from the `raw_materials` master catalog becomes optional. Administrators do not need to assign extrusion profiles, glass infills, or dimension bindings (`WIDTH`, `HEIGHT`, `AREA`, `GRILLE_LINEAR`).
- The bill-of-materials and pricing engine (`pricingEngine.ts`) evaluates fixed components as `base_quantity * unit_price` without parametric scaling, factoring the cost cleanly into itemized quotation snapshots and consultation PDFs.

### 1.2 Goal 2: Hardware Accessory Bilateral Handing Mesh Mirroring (Left vs Right)

In MS74, MS75, and MS76, GlassFit established modular hardware accessories (handles, locks, knobs, hinges, rollers) and swappable accessory slots on host fixtures. A key feature of architectural fixtures is lateral handing: doors and windows open either Left-handed or Right-handed, requiring the handle and lock to be mounted on either the Left stile or Right stile.

Under previous workflows:
1. In `parametricProductBuilder.ts`, switching an accessory slot from Right to Left applied a literal 180-degree yaw rotation around the vertical axis (`clone.rotation.y = Math.PI`).
2. A 180-degree rotation is geometrically invalid for asymmetric hardware:
   - For an asymmetric lever handle or keyed latch lock, rotating 180 degrees around Y flips the exterior escutcheon plate to face backwards into the glass or door interior (-Z).
   - The keyhole or privacy thumbturn faces the wrong direction, and the handle lever either collides with the host glass or points into the frame cavity.
3. True architectural handing requires a geometric **bilateral mirror** (reflection across the lateral X=0 plane):
   - The exterior mounting face remains oriented outward towards the customer (+Z).
   - The vertical mounting height remains upright (+Y).
   - The lateral lever/latch projection reflects across the X axis.
4. Fabricators and 3D artists rarely create both Left and Right GLB files in CAD. Usually, only one handing is exported.

**Planned Outcome for Goal 2:**
- When uploading a hardware accessory (`is_accessory = true`) in Step 3 (**Structural Components**), the administrative interface provides an automated **Bilateral Handing Mirror Generator**.
- The system generates the reflected counterpart of the uploaded `.glb` mesh in Three.js (reflecting X coordinates, reversing triangle face index winding, and inverting vertex normals to maintain proper lighting and backface culling).
- The administrator selects which handing corresponds to the uploaded source file:
  - **Option A:** Uploaded model is **Right-Handed** (System assigns uploaded model to Right, generated mirror to Left).
  - **Option B:** Uploaded model is **Left-Handed** (System assigns uploaded model to Left, generated mirror to Right).
- The system stores both Left and Right asset references within `product_components.component_data` and `public.product_assets`.
- When the accessory is mounted onto a host fixture in the customer workspace (`ProductModelWorkspace.tsx`) or admin test-drive sandbox (`ValidationWorkspaceSection.tsx`), toggling between Left and Right handings dynamically mounts the true matching handed GLB mesh. The lever points toward the correct side with zero backface inversion.

## 3. Non-Negotiable Invariants and Hard Bans

1. **Zero Em-Dashes (BAN-PUNCT-01):** In strict accordance with `AGENTS.md`, em-dashes are banned across all markdown specifications, UI strings, placeholder text, code comments, and tooltips. Use standard hyphens, colons, or parentheses exclusively.
2. **Strict Type Safety (BAN-TYPE-05):** Zero usage of `any` across TypeScript interfaces, form state hooks, Three.js transformations, and database DTOs. Use explicit schemas, generics, or unknown with type narrowing.
3. **Specification Precedence (BAN-SPEC-02):** All changes must maintain traceability back to `PRD-F5`, `PRD-F10`, `PRD-F14`, `SDD-C4`, `SDD-C7`, `SDD-C9`, `ERD-E6`, `DSD-UI10`, and `QAD-TC93`.
4. **No Raw Diagrams or Trees (BAN-DIAG-03):** No ASCII trees or box diagrams in code blocks. Use standard Markdown tables and ordered prose.
5. **Fixed Model Component Invariant:** Products configured with `model_strategy = 'Fixed'` must permit uploading and saving `.glb` components. When a component is assigned a fixed unit price, `raw_material_id` is permitted to be null.
6. **Mathematical Fixed Pricing Invariant:** For fixed components, `computed_subtotal = round2(base_quantity * unit_price)`. Scrap factors, area multipliers, and linear extrusion span ratios are bypassed (waste factor = 0%). Labor and contractor margin formulas continue to apply according to the established pricing model.
7. **Bilateral Handing Geometric Invariant:** The mirrored accessory variant must be produced by lateral reflection across the X=0 plane (`x' = -x`), accompanied by face index winding inversion and normal negation. It must NEVER be produced by rotating 180 degrees around the Y axis, as this inverts the front/rear face orientation.
8. **Explicit Handing Selection Invariant:** When an accessory model is uploaded, the system must require the administrator to declare whether the uploaded source file is "Right" or "Left". The system must never guess handing heuristically without administrator confirmation.
9. **UI Design Token Parity (BAN-UI-09):** All new UI controls in `PartInspectorDrawer.tsx` and `StructuralComponentsSection.tsx` must reuse established design tokens (`rounded-[10px]`, `rounded-[16px]`, `border-[#c3c3c3]`, `bg-[#0f1422]`, `text-[#07b6d3]`) from `src/app/globals.css`.

### 4.2 Hardware Accessory Bilateral Handing Mesh Mirroring

#### 4.2.1 Bilateral Reflection Mathematics & Normals Inversion

In Three.js, reflecting geometry across the lateral X axis requires:
1. Negating the X coordinate of every vertex position: `p.x' = -p.x`.
2. Negating the X component of every vertex normal: `n.x' = -n.x`.
3. Inverting the triangle face winding order (reversing the indices of vertices 1 and 2 for each triangle face) so that the surface normal faces outward, preventing backface culling from turning the mesh invisible or inside-out.
4. Reflecting tangent vectors if present in the GLTF mesh.

```typescript
/**
 * Bilaterally mirrors a Three.js Object3D hierarchy across the X=0 plane.
 * Inverts triangle vertex index winding to preserve outward-facing surface normals.
 * Traceability: PRD-F5, SDD-C4, IMP-MS78, QAD-TC93.4
 */
export function mirrorObjectHierarchyAcrossX(source: THREE.Object3D): THREE.Object3D {
    const clone = source.clone(true);

    clone.traverse((child) => {
        if (child instanceof THREE.Mesh && child.geometry) {
            // Clone geometry to avoid mutating cached original
            child.geometry = child.geometry.clone();
            const geom = child.geometry as THREE.BufferGeometry;

            // 1. Mirror vertex positions across X
            const posAttr = geom.getAttribute("position");
            if (posAttr) {
                for (let i = 0; i < posAttr.count; i++) {
                    posAttr.setX(i, -posAttr.getX(i));
                }
                posAttr.needsUpdate = true;
            }

            // 2. Mirror vertex normals across X
            const normAttr = geom.getAttribute("normal");
            if (normAttr) {
                for (let i = 0; i < normAttr.count; i++) {
                    normAttr.setX(i, -normAttr.getX(i));
                }
                normAttr.needsUpdate = true;
            }

            // 3. Invert triangle winding order so front faces remain front faces
            const index = geom.getIndex();
            if (index) {
                const indices = index.array;
                for (let i = 0; i < indices.length; i += 3) {
                    const temp = indices[i + 1];
                    indices[i + 1] = indices[i + 2];
                    indices[i + 2] = temp;
                }
                index.needsUpdate = true;
            } else if (posAttr) {
                // Non-indexed geometry: swap consecutive vertices in groups of 3
                for (let i = 0; i < posAttr.count; i += 3) {
                    const x1 = posAttr.getX(i + 1);
                    const y1 = posAttr.getY(i + 1);
                    const z1 = posAttr.getZ(i + 1);

                    posAttr.setXYZ(i + 1, posAttr.getX(i + 2), posAttr.getY(i + 2), posAttr.getZ(i + 2));
                    posAttr.setXYZ(i + 2, x1, y1, z1);
                }
                posAttr.needsUpdate = true;
            }

            geom.computeVertexNormals();
            geom.computeBoundingBox();
            geom.computeBoundingSphere();
        }
    });

    return clone;
}
```

#### 4.2.2 Admin Handing Selection Workflow in Setup Wizard

When an accessory product (`is_accessory = true`) is authored in Step 3 (**Structural Components**):
1. The administrator uploads the primary `.glb` file (e.g. `lever_handle_modern.glb`).
2. The UI renders the **Bilateral Handing Configuration** card below the uploaded file preview.
3. The administrator is prompted with two distinct choice cards to declare the uploaded model's handing:
   - **"Uploaded model is Right-Handed"** (Recommended for standard Philippine door handles where lever points leftward toward door panel).
   - **"Uploaded model is Left-Handed"**.
4. The system automatically runs `mirrorObjectHierarchyAcrossX`, displaying a dual-viewport comparison card:
   - Left Viewport: **Left Handing Model** (Tagged "Uploaded" or "Generated Mirror").
   - Right Viewport: **Right Handing Model** (Tagged "Uploaded" or "Generated Mirror").
5. Both viewports support interactive 3D orbiting and PBR finish preview.

#### 4.2.3 Runtime Dynamic Handing Mounting (`parametricProductBuilder.ts`)

In `src/lib/visualization/parametricProductBuilder.ts`, the mounting function `mountAccessoryMesh` is updated to discard the flawed `clone.rotation.y = Math.PI` rotation logic. Instead, it checks whether handing-specific models exist:

```typescript
export function mountAccessoryMesh(
    parentGroup: THREE.Group,
    accessoryModel: THREE.Object3D,
    hostBounds: { widthM: number; heightM: number; depthM: number },
    positionOptions?: AccessoryPositionOptions | null,
    horizontal: "left" | "right" = "right",
    vertical: "bottom" | "up" = "up",
    finishKey: string = "matte_black",
    handingVariantMesh?: THREE.Object3D | null, // Pre-resolved handed mesh (Left vs Right)
): THREE.Object3D {
    // If a dedicated handed variant is provided, use it; otherwise use base clone
    const targetModel = handingVariantMesh || accessoryModel;
    const clone = targetModel.clone(true);

    // Apply PBR finish material
    const hardwareMaterial = createHardwareFinishMaterial(finishKey);
    clone.traverse((child) => {
        if (child instanceof THREE.Mesh) {
            child.material = hardwareMaterial;
            child.castShadow = true;
            child.receiveShadow = true;
        }
    });

    // Calculate strict lateral X-axis coordinate for Left vs Right handings
    const lateralMarginM = (positionOptions?.horizontalOffsetMm ?? 45) / 1000;
    const targetXM = horizontal === "left"
        ? -hostBounds.widthM / 2 + lateralMarginM
        : hostBounds.widthM / 2 - lateralMarginM;

    // Calculate strict vertical Y-axis coordinate for Bottom vs Up elevations
    const verticalMarginM = (positionOptions?.verticalOffsetMm ?? 1000) / 1000;
    const targetYM = vertical === "bottom"
        ? -hostBounds.heightM / 2 + verticalMarginM
        : hostBounds.heightM * 0.05;

    // Maintain Z depth flush to front surface
    const targetZM = hostBounds.depthM / 2 + 0.002;

    clone.position.set(targetXM, targetYM, targetZM);

    // Zero out rotation: geometry is already correctly handed
    clone.rotation.set(0, 0, 0);

    parentGroup.add(clone);
    return clone;
}
```

In `ProductModelWorkspace.tsx` and `parametricProductBuilder.ts`, when resolving the accessory mesh for an active slot:
1. The engine checks the slot's current `horizontalPosition` ("left" or "right").
2. It looks up `handing_metadata` on the accessory component.
3. If `horizontalPosition === "left"` and `leftGlbUrl` exists, it loads the Left GLB asset.
4. If `horizontalPosition === "right"` and `rightGlbUrl` exists, it loads the Right GLB asset.
5. If no pre-rendered mirrored GLB asset is stored, the engine dynamically applies `mirrorObjectHierarchyAcrossX` in memory on the client.
