## 1. Executive Summary & Problem Context

In GlassFit, customers design customized architectural glass and aluminum fixtures (sliding windows, awning windows, frameless glass doors, shower enclosures, and partitions), verify real-world dimensions via the Measurement Confirmation Modal (`DSD-UI7`), generate a canonical parametric Bill of Materials (BOM) quotation, and initiate an asynchronous consultation handoff to Facebook Messenger or Viber (`src/features/booking/components/BookingFlow.tsx`). This handoff records an immutable customer inquiry row in `public.booking_requests` via `recordBookingRequest` (`src/lib/booking/bookingActions.ts`).

### The Current State
In Milestone 19 (`docs/implementation/ms19.md`), the authenticated customer portal route at `/my-requests` was established with:
1. An authenticated server route guard (`requireActiveCustomer` in `src/lib/auth/customer.ts`) verifying active customer profile status.
2. A responsive two-column master-detail layout adhering to the approved visual baseline (`docs/implementation/assets/ms19-my-requests-desktop-v2.png`).
3. An interactive client island (`MyRequestsContent.tsx`) driven by a local reducer (`requestReducer`).
4. Hardcoded deterministic mock fixtures (`CANONICAL_REQUEST_FIXTURES` in `src/features/my-requests/requestData.ts`) consisting of 5 static mock requests with fixed IDs (`CF-2026-001` through `CF-2026-005`).

### The Business and Engineering Need
Customers visiting `/my-requests` currently see hardcoded mock requests rather than their actual consultation submissions. When a customer sends a booking request via Messenger or Viber, or when administrative staff review and update the status of that request in `/admin/bookings`, the customer's portal remains static and disconnected from real persistence.

To fulfill `PRD-F17` (Customer Consultation History Dashboard) and resolve the delivery boundary established in `IMP-MS19`, `IMP-MS20` connects `/my-requests` to the active PostgreSQL database.

### Core Architectural Directives
1. **Preserve Current UI Layout & Design Tokens:** Do not alter the visual styling, spacing, colors, border radii, or typography established in `ms19.md`. If new UI states are required (such as loading skeletons or query retry notices), they must strictly reuse existing repository UI components, tokens, and classes (`BAN-UI-09`).
2. **Preserve Mock Data Process and Progression:** Retain the exact 4-stage visual progress flow (`Submitted` -> `Under Review` -> `Confirmed` -> `Completed`) and terminal Cancelled banner behavior.
3. **Synthesize Chronological Request Updates:** Because PostgreSQL does not store an ad-hoc updates table, the system must deterministically derive request timeline events from real database timestamps (`booking_requests.created_at`, `booking_requests.updated_at`, `quotation_estimates.created_at`, `quotation_estimates.negotiated_at`, and `booking_requests.status`).
4. **Strict RLS Tenant Isolation:** Queries must execute using the authenticated Supabase client (`createSupabaseServerClient()`), enforcing `profile_id = auth.uid()` at the PostgreSQL Row-Level Security layer (`BAN-RLS-07`).
5. **Zero Hallucinated Dependencies & Zero `any`:** Implement all queries, mappers, and state synchronizers using existing repository dependencies and strict TypeScript types (`BAN-TYPE-05`).

## 3. Database Schema & Relational PostgREST Query Contract

### 3.1 Relational Architecture and Joins
The customer's booking history is rooted in `public.booking_requests` (`ERD-E16`). In accordance with the relational schema in `supabase/migrations/001_backend_core.sql` and `supabase/migrations/complete_schema.sql`, the query must traverse the foreign key relationships to retrieve the attached quotation and item details:

```
public.booking_requests (ERD-E16)
  └── [booking_requests_link_fk] ──> public.signed_booking_links (ERD-E15)
        └── [signed_booking_links_quotation_fk] ──> public.quotation_estimates (ERD-E13)
              ├── [quotation_items_quotation_fk] ──> public.quotation_items (ERD-E14)
              └── [quotation_estimates_snapshot_fk] ──> public.visualization_snapshots (ERD-E10)
```

### 3.2 Relational Disambiguation Guard
As established in `IMP-MS15` (Section 2.1), `booking_requests` defines two foreign keys targeting `public.profiles`:
1. `booking_requests_profile_fk`: `booking_requests(profile_id)` references the customer.
2. `booking_requests_updated_by_fk`: `booking_requests(updated_by)` references the admin who reviewed the request.

For customer queries on `/my-requests`, embedding `profiles` is completely unnecessary because the customer's identity is already verified via server authentication. Eliminating the profile join entirely prevents any possibility of PostgREST relationship ambiguity (`PGRST201`) and minimizes query overhead.

### 3.3 Authoritative PostgREST Query String
The dedicated query contract must be defined in `src/features/my-requests/clientRequestQueries.ts`:


### 3.5 Row-Level Security Verification (`BAN-RLS-07`)
In PostgreSQL, `public.booking_requests` is guarded by:
```sql
CREATE POLICY "booking_requests_select_own_or_admin" 
ON "public"."booking_requests" 
FOR SELECT TO "authenticated" 
USING ((profile_id = auth.uid()) OR public.is_admin());
```
When `createSupabaseServerClient()` is invoked in the App Router Server Component, the user's JWT cookie is passed to Supabase. PostgreSQL evaluates `auth.uid()`, guaranteeing that no customer can read another customer's booking rows. In addition, the query builder enforces `.eq("profile_id", user.id)` as an explicit application-layer guard.

## 4. Domain Mapping & Entity Transformation Contract

### 4.1 Product Identity and Count Summarization
In the mock data, each card displayed a `productName` and `productCount` (e.g., "Series 798 Sliding Window", 3 Products). With actual database records, quotations may contain a single product or multiple products.

The pure mapper in `src/features/my-requests/clientRequestMapper.ts` extracts product details according to the following precedence:

1. **Canonical V1 Quotation Snapshot:** If `quotation_document_snapshot` parses successfully using `QuotationDocumentSnapshotV1Schema`:
   - Inspect `snapshot.items`:
     - If `snapshot.items.length === 1`:
       - `productName` = `snapshot.items[0].productName`.
       - `productCount` = `snapshot.items[0].quantity`.
     - If `snapshot.items.length > 1`:
       - `productName` = `${snapshot.items[0].productName} and ${snapshot.items.length - 1} more`.
       - `productCount` = sum of all `item.quantity` across `snapshot.items`.
2. **Legacy Quotation Items Fallback:** If the canonical snapshot is absent or unparseable:
   - Extract item fixtures using `extractQuotationFixtures(quotation.quotation_items)` (matching the proven logic in `adminBookingMapper.ts`).
   - If fixtures exist:
     - `productName` = `${fixtures[0].name}${fixtures.length > 1 ? ` and ${fixtures.length - 1} more` : ""}`.
     - `productCount` = sum of `fixture.quantity`.
   - If no fixtures or items exist:
     - `productName` = "Custom Consultation Fixture".
     - `productCount` = 1.

### 4.2 Reference Number Formatting
- If `quotation.quotation_number` is present (e.g. `Q-2026-001`), the customer reference number is derived as:
  - Canonical format: `quotation.quotation_number.replace(/^Q-/, "CF-")` (e.g. `CF-2026-001`).
  - Fallback: If no quotation is attached, format using the booking ID prefix: `CF-${row.booking_request_id.slice(0, 8).toUpperCase()}`.

### 4.3 Quotation File Artifact Mapping
In `requestData.ts`, `ClientRequestQuotation` is extended to support live artifacts:

```typescript
export interface ClientRequestQuotation {
  filename: string;
  generatedAt: string;
  availability: "available" | "pending" | "prototype-only";
  referenceCode: string;
  shareableUrl: string;
  r2ObjectKey: string | null;
}
```

Mapping rules:
- `filename`: If `quotation.pdf_r2_object_key` exists, extract the file basename: `quotation.pdf_r2_object_key.split("/").pop() ?? "Quotation.pdf"`. If absent, fallback to `${referenceNo}-quotation.pdf`.
- `generatedAt`: `quotation.created_at ?? row.created_at`.
- `availability`: Set to `"available"` if `quotation.pdf_r2_object_key` or `quotation.quotation_id` exists; otherwise `"pending"`.
- `referenceCode`: The canonical `CF-...` code.
- `shareableUrl`: `/q/${referenceCode}` (pointing to the public consultation snapshot viewer).
- `r2ObjectKey`: `quotation.pdf_r2_object_key ?? null`.

## 6. Chronological Request Updates Synthesis

### 6.1 Rationale for Deterministic Event Synthesis
The PostgreSQL database persists the core consultation entities (`booking_requests`, `signed_booking_links`, `quotation_estimates`), but does not contain an arbitrary `request_updates` logging table.

In the mock data, each request had an array of `RequestUpdate` entries with timestamps and descriptions (e.g., "Request submitted", "Quotation received", "Under review", "Measurements noted", "Request completed").

To keep this process completely intact with actual data, `IMP-MS20` specifies a deterministic synthesizer function: `synthesizeRequestUpdates(row: ClientBookingRequestRow)`. This function derives chronological milestone events from the actual entity state and timestamps.

### 6.2 Milestone Synthesis Rules

For any given `ClientBookingRequestRow`, the timeline events are generated as follows:

```typescript
export function synthesizeRequestUpdates(row: ClientBookingRequestRow): RequestUpdate[] {
  const updates: RequestUpdate[] = [];
  const quotation = row.booking_link?.quotation;
  const requestId = row.booking_request_id;
  const platform = row.selected_platform;

  // 1. Initial Submission Milestone (Always present)
  updates.push({
    id: `upd-${requestId}-submitted`,
    occurredAt: row.created_at,
    title: "Request submitted",
    description: `Your consultation request has been received via ${platform}.`,
  });

  // 2. Quotation Generation Milestone (Present if quotation exists)
  if (quotation) {
    updates.push({
      id: `upd-${requestId}-quotation`,
      occurredAt: quotation.created_at,
      title: "Quotation received",
      description: `Consultation quotation ${quotation.quotation_number} is attached to this request.`,
    });
  }

  // 3. Status Milestone: Ongoing (Under Review)
  if (row.status === "Ongoing" || row.status === "Done") {
    // If ongoing, timestamp is row.updated_at. If already Done, order before completion.
    const reviewTime = row.status === "Ongoing" 
      ? row.updated_at 
      : quotation?.created_at && row.updated_at > quotation.created_at
        ? new Date((new Date(quotation.created_at).getTime() + new Date(row.updated_at).getTime()) / 2).toISOString()
        : row.updated_at;

    updates.push({
      id: `upd-${requestId}-review`,
      occurredAt: reviewTime,
      title: "Under review",
      description: "Our team is reviewing your room specifications and product dimensions.",
    });
  }

  // 4. Quotation Negotiation / Price Confirmation Milestone (Present if negotiated_at exists)
  if (quotation?.negotiated_at) {
    updates.push({
      id: `upd-${requestId}-pricing`,
      occurredAt: quotation.negotiated_at,
      title: "Quotation confirmed",
      description: "Consultation pricing has been confirmed by the fabrication team.",
    });
  }

  // 5. Terminal Milestone: Completed
  if (row.status === "Done") {
    updates.push({
      id: `upd-${requestId}-completed`,
      occurredAt: row.updated_at,
      title: "Request completed",
      description: "Your consultation request has been processed.",
    });
  }

  // 6. Terminal Milestone: Cancelled
  if (row.status === "Cancelled") {
    updates.push({
      id: `upd-${requestId}-cancelled`,
      occurredAt: row.updated_at,
      title: "Request cancelled",
      description: "This consultation request is no longer active.",
    });
  }

  // Sort newest first per Section 5 of MS19
  return getSortedTimelineUpdates(updates);
}
```

### 6.3 Timeline Component Integration
The synthesized updates feed directly into `RequestTimeline.tsx`:
- Sorted newest-first by `occurredAt`.
- Shows top 3 updates by default.
- If total updates > 3, displays the "View all updates" / "Show latest updates" toggle button.
- If 0 updates (edge case), displays "No request updates yet."

## 8. Route Freshness, Cache Invalidation & State Synchronization

### 8.1 Server Rendering and Freshness
`src/app/my-requests/page.tsx` is an App Router Server Component. It calls `createSupabaseServerClient()`, which accesses request-time cookies. Therefore, Next.js dynamically renders the route on each customer visit.

### 8.2 Path Invalidation Contract (`bookingRevalidationPaths.ts`)
To ensure that any status update performed by an administrator or any new consultation booking submitted by a customer is immediately reflected on `/my-requests`, the shared revalidation constant must be updated:

```typescript
// src/lib/booking/bookingRevalidationPaths.ts
export const BOOKING_REVALIDATION_PATHS = [
  "/admin",
  "/admin/bookings",
  "/dashboard",
  "/my-requests",
] as const;
```

This guarantees that:
1. `recordBookingRequest` (`src/lib/booking/bookingActions.ts`) invalidates `/my-requests` upon initial handoff.
2. `updateBookingRequestStatus` (`src/lib/booking/bookingActions.ts`) invalidates `/my-requests` when staff transition a request from `Pending` to `Ongoing`, `Done`, or `Cancelled`.
3. `updateItemNegotiatedPrice` and `updateNegotiatedPrice` invalidate `/my-requests` when pricing overrides are persisted.

### 8.3 Client State Synchronization in `MyRequestsContent.tsx`
When a customer navigates back to `/my-requests` or when the route revalidates, updated `initialRequests` props arrive from the server.

The client island must synchronize without resetting the user's active filter or selected request if it remains present in the dataset:
- If `props.initialRequests` changes, update internal requests state.
- If the previously selected request ID exists in the new requests list, keep it selected.
- If the previously selected request was deleted or filtered out, select the first visible request in the active filter.

## 10. Non-Goals

To prevent scope creep and maintain architectural boundaries, the following operations are explicitly excluded from MS20:
1. **No Customer-Side Booking Mutation on `/my-requests`:** Customers do not create or modify bookings on this page; booking creation belongs to `/booking` via `BookingFlow.tsx`.
2. **No Admin Status Updates on `/my-requests`:** Triage and status mutations belong exclusively to `/admin/bookings`.
3. **No Database Schema Migrations:** All required tables (`booking_requests`, `signed_booking_links`, `quotation_estimates`, `quotation_items`, `visualization_snapshots`) already exist with complete RLS policies. No new DDL migration is needed.
4. **No Third-Party External Libraries:** No external charting, animation, or UI component libraries may be added.
5. **No WebSocket or Continuous Polling Daemon:** Data freshness is delivered via server rendering, route revalidation, and manual refresh, avoiding battery drain and unnecessary network saturation.
