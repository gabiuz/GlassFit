## 1. Required Outcome

1. **Deterministic Base Frame Color Selection:** In the client visualization workspace, clicking any aluminum finish swatch under the "Design and Customization Option" accordion immediately updates all structural framing members of the active product to the selected finish across both 3D rendering and 2D canvas blits. This change must persist deterministically without reverting, flickering, or stalling, regardless of whether custom part materials were previously selected in the Part Materials Picker, whether a saved configuration was loaded, or whether the product uses natural assembly, window-like parametric assembly, or fixed-model GLTF assets.
2. **Deterministic Add-on Frame Color Selection:** Under the "Add-on Options" accordion, clicking any finish swatch for an active add-on (such as Screen Frame Finish or Grille Bar Finish) immediately and reliably updates all structural frame members, intermediate tie bars, repeated middle grille pattern tiles, and screen access hatch sub-frames of the add-on to the chosen finish without altering the host window or door frame finish.
3. **Mutual Independence of Host and Add-on Finishes:** Changing the host product's aluminum finish must never overwrite or contaminate the independently selected add-on finish. Conversely, changing the add-on finish must never alter the host product's frame finish.
4. **Glass Color and Appearance Invariance:** Clicking glass color swatches (Clear, Bronze, Silver, Blue) or glass appearance modes under the "Design and Customization Option" accordion must reliably update the glass material transmission, color tint, and opacity without being overwritten or reverted by asynchronous model rebuilds.
5. **Real-Time Presentation and Asynchronous Rebuild Parity:** In-place fast-path material updates (sub-16ms) and asynchronous full model re-assemblies (`loadModel()`) must yield identical visual outcomes. The cache invalidation and skip-rebuild keys must remain strictly synchronized to eliminate race conditions between immediate 2D canvas blits and background model commits.
6. **Planning Scope:** This document is an architectural diagnosis and implementation specification only. It does not authorize immediate code changes, database migrations, or production deployments.

## 2. Verified Starting Point and Root-Cause Diagnosis

Investigation of the GlassFit visualization pipeline revealed multiple interlocking architectural gaps across `ProductModelWorkspace.tsx`, `modelRenderer.ts`, `materialClassifier.ts`, and `parametricProductBuilder.ts` that explain why color selections "sometimes work and sometimes do not":

| Current Path | Evidence in Code | Root Cause and Intermittent Failure Mechanism |
|---|---|---|
| Workspace Build Key Cache | `ProductModelWorkspace.tsx` lines 1339 and 2011 | **Severe Build Key Schema Mismatch:** `applyWorkspacePresentation()` constructs `nextBuildKey` using 15 tokens (`productId:width:height:panelCount:includeSill:activeAddon:addonMountingSide:addonAluminumFinish:aluminumFinish:glassAppearance:glassColor:glassThicknessMm:includeHatch:screenMeshDensity:nextRemovableKey`), while the reactive `useEffect` computes `buildKey` with different tokens in a different sequence (`productId:width:height:panelCount:includeSill:selectedAddon:addonMountingSide:selectedAddonProductId:addonAlumFinish:alumFinish:glassAppearance:glassColor:glassThicknessMm:includeHatch:accessoriesKey:removableStatesKey`). Because `skipPreparedBuildRef.current === buildKey` is never true, every single color click triggers an unwanted background `loadModel()` rebuild. When the background rebuild finishes 50 to 200ms later, it can clobber or revert the instantaneous presentation update depending on state synchronization timing. |
| Dual State Disconnect in Workspace | `ProductModelWorkspace.tsx` lines 3570-3599 and `modelRenderer.ts` lines 254-260 | **Raw Material Overrides Reversion:** In `handleBaseFinishSelect()`, the system updates `alumFinish` and attempts to synchronize `selectedMaterials` by searching `materialCustomizationGroups`. However: (1) The database `raw_materials` table only seeds White and Analok; selecting any of the other 22 finishes in `ALUMINUM_FINISH_OPTIONS` yields no matched raw material option, leaving `selectedMaterials` pointing to the prior raw material ID. (2) `handleBaseFinishSelect()` does not reset `hasExplicitOverrides` to false. If the user previously touched `PartMaterialsPicker`, `hasExplicitOverrides` remains true. When the asynchronous `loadModel()` completes, `modelRenderer.ts` executes `updateCustomMaterials(customMaterials.selectedMaterials, ...)`, instantly reverting the 3D model back to the old raw material. When `hasExplicitOverrides` is false, it works; when true, it reverts. |
| Add-on Mesh Hierarchy Inspection | `modelRenderer.ts` lines 336-348 and `parametricProductBuilder.ts` lines 3899-4090 | **Leaf Mesh Selector Failure on Uploaded Add-on Components:** In `modelRenderer.updatePresentation()`, the traversal checks: `isAddonFrame = child.name.startsWith("Screen_Frame_") \|\| child.name.startsWith("Grill_Frame_") \|\| child.name.startsWith("Grill_Bar_") \|\| (child.userData.isAddon && child.userData.presentationCategory === "Framing")`. For procedural screen frames, names match `Screen_Frame_` and color pick works. But for uploaded add-on components, middle grille tiles, and wicket hatches, `isAddon` and `presentationCategory` are assigned to the parent Group container (`wrapperGroup` or `tileWrapper`), not to the child `THREE.Mesh`. In addition, child mesh names from GLB assets (such as `Cube_0` or `Extrusion_1`) do not match the prefix. Consequently, `isAddonFrame` evaluates to false, and the add-on finish color is never applied. |
| Host Presentation Overwrite on Add-on Meshes | `modelRenderer.ts` lines 318-325 and `materialClassifier.ts` lines 510-555 | **Global Presentation Trampling Add-on Framing:** When `updatePresentation()` runs, it calls `applyPresentationMaterials(this.modelGroup, ...)`. This traverses the entire scene hierarchy, including the add-on. Any add-on mesh that lacks `preserveMaterial = true` directly on the mesh object itself is classified as generic framing and forcibly reassigned the host frame material (`options.aluminumFinish`). If that mesh then fails the strict `isAddonFrame` filter in the subsequent loop, it remains permanently stained with the host frame's color. |
| Missing Add-on Config in Full Rebuild | `ProductModelWorkspace.tsx` lines 2023-2051 | **Omission of `addonConfig` in `loadModel()` Options:** When `loadModel()` is called from the workspace `useEffect`, the passed presentation options object includes `addonAluminumFinish`, but omits `addonConfig` entirely (`finishColor` and `zOffsetMm` are undefined). As a result, procedural add-on builders fall back to the default dark bronze color (`#221d1a`), ignoring the user's active add-on finish selection whenever a full parametric model rebuild takes place. |
| Glass Color Synchronization Gap | `ProductModelWorkspace.tsx` lines 1718-1724 | **Unsynchronized Glass Color State:** `handleGlassColorChange()` calls `setGlassColor(colorKey)` and triggers `applyWorkspacePresentation({ glassColor: colorKey })`, but does not synchronize with `selectedMaterials` or clear `hasExplicitOverrides`. If `hasExplicitOverrides` is active, the subsequent `loadModel()` completion executes `updateCustomMaterials()`, overriding the glass mesh with the previously assigned raw material PBR attributes. |
| Partial PBR Updates in Presentation | `modelRenderer.ts` lines 343-346 | **Stale Surface Optics on Add-on Recoloring:** `updatePresentation()` calls only `child.material.color.set(finishColor)`. It does not update physical roughness, metalness, clearcoat, or clearcoat roughness. Switching between Anodized (Analok), Powder Coated (White), and Metallic (Silver) finishes leaves the material with incorrect reflective properties, causing visible wash-out or lighting distortions. |

## 3. Technical Contract and Architectural Design

### 3.1 Unified Build Key Harmonization Contract
To eliminate race conditions between fast-path presentation blits and reactive model rebuilds, a single canonical build key generator function must be defined and shared across both `applyWorkspacePresentation` and the reactive `useEffect`.

```typescript
export interface WorkspaceBuildKeyParams {
  productId: string;
  widthCm: string | number;
  heightCm: string | number;
  panelCount: number;
  includeSill: boolean;
  selectedAddon: string;
  selectedAddonProductId: string | null;
  addonMountingSide: "front" | "back";
  addonAlumFinish: string;
  alumFinish: string;
  glassAppearance: string;
  glassColor: string;
  glassThicknessMm: number;
  includeHatch: boolean;
  screenMeshDensity: string;
  accessoriesKey: string;
  removableStatesKey: string;
}

export function computeWorkspaceBuildKey(params: WorkspaceBuildKeyParams): string {
  return [
    params.productId,
    params.widthCm,
    params.heightCm,
    params.panelCount,
    params.includeSill ? "sill:1" : "sill:0",
    params.selectedAddon,
    params.selectedAddonProductId ?? "none",
    params.addonMountingSide,
    params.addonAlumFinish,
    params.alumFinish,
    params.glassAppearance,
    params.glassColor,
    params.glassThicknessMm,
    params.includeHatch ? "hatch:1" : "hatch:0",
    params.screenMeshDensity,
    params.accessoriesKey,
    params.removableStatesKey,
  ].join("|");
}
```

1. When `applyWorkspacePresentation(overrides)` is invoked:
   - Compute `currentOptions` including all active parameters and overrides.
   - Execute `mvpRendererRef.current.updatePresentation(currentOptions)`.
   - Perform the immediate 2D canvas blit.
   - Generate `canonicalKey = computeWorkspaceBuildKey(...)` using the updated parameters.
   - Assign `skipPreparedBuildRef.current = canonicalKey`.
2. When the reactive `useEffect` runs:
   - Generate `currentKey = computeWorkspaceBuildKey(...)` using current component state.
   - If `skipPreparedBuildRef.current === currentKey`, consume the reference (`skipPreparedBuildRef.current = null`) and exit early without executing `loadModel()`.
   - This ensures that color and finish updates execute purely in memory in sub-16ms without triggering redundant asynchronous network fetches or scene graph reconstructions.

### 3.2 Dual State Reconciliation: Presentation Finishes vs Raw Material Overrides
The workspace must cleanly reconcile global finish selections with component-level raw material overrides:

1. **Explicit Override Reset on Global Finish Selection:**
   - When the user selects a base aluminum finish via `handleBaseFinishSelect(finishId)`:
     - Set `alumFinish` to `normalizeAluminumFinish(finishId)`.
     - Check whether `materialCustomizationGroups` has a matching raw material option in the "Framing" category.
     - If a matching raw material exists in the catalog: update `selectedMaterials` for all framing components with the new raw material ID.
     - If no matching raw material exists in the catalog (e.g. specialized R.R.D. color finishes `al_1001` through `al_1020`): remove framing component keys from `selectedMaterials` so they fall back to the global presentation finish, or reset `hasExplicitOverrides` to `false` for framing components.
     - Reset `hasExplicitOverrides` to `false` when the user explicitly chooses a global base finish, ensuring that subsequent background rebuilds honor the newly selected finish rather than reverting to stale part selections.
2. **Glass Color and Appearance Reconciliation:**
   - When `handleGlassColorChange(colorKey)` is called:
     - Set `glassColor` to `colorKey`.
     - If `materialCustomizationGroups` contains a matching glass raw material for that color: update `selectedMaterials` for glazing components.
     - If no direct raw material match exists: purge explicit glazing overrides from `selectedMaterials` and set `hasExplicitOverrides` to `false` for glazing so the visualizer uses the chosen glass presentation color.
     - Apply presentation materials immediately via `applyWorkspacePresentation({ glassColor: colorKey })`.

### 3.3 Scene Hierarchy Traversal and Add-on Frame Recognition Contract
In `modelRenderer.ts`, the logic that identifies add-on frame meshes must walk up the Three.js scene graph hierarchy to inherit parent container metadata, guaranteeing that uploaded add-on components, middle grille tiles, and wicket hatches are recognized.

```typescript
export function isAddonFrameMesh(mesh: THREE.Mesh): boolean {
  // 1. Direct name prefix check (procedural screens and grilles)
  if (
    mesh.name.startsWith("Screen_Frame_") ||
    mesh.name.startsWith("Grill_Frame_") ||
    mesh.name.startsWith("Grill_Bar_") ||
    mesh.name.startsWith("Screen_Access_Hatch_")
  ) {
    return true;
  }

  // 2. Mesh-level userData check
  if (
    mesh.userData?.isAddon === true &&
    (mesh.userData?.presentationCategory === "Framing" ||
     mesh.userData?.componentType === "Frame" ||
     mesh.userData?.addonType === "grill")
  ) {
    return true;
  }

  // 3. Hierarchy walk: check parent groups and wrappers
  let curr: THREE.Object3D | null = mesh.parent;
  while (curr && curr !== curr.parent) {
    if (
      curr.userData?.isAddon === true ||
      curr.userData?.isUploadedAddon === true ||
      curr.userData?.addonType !== undefined ||
      (typeof curr.name === "string" && (
        curr.name.startsWith("Addon_") ||
        curr.name.startsWith("Screen_") ||
        curr.name.startsWith("Grill_")
      ))
    ) {
      // Must be framing, not wire mesh or glass infill
      const category = curr.userData?.presentationCategory ?? mesh.userData?.presentationCategory;
      const isWire = mesh.userData?.isScreenMesh || curr.userData?.isScreenMesh;
      if (!isWire && (category === "Framing" || category === undefined)) {
        return true;
      }
    }
    curr = curr.parent;
  }

  return false;
}
```

1. In `modelRenderer.updatePresentation()`:
   - Replace the fragile leaf-only check with `isAddonFrameMesh(child)`.
   - Resolve the target finish options from `findFinishOption(presentation.addonAluminumFinish)`.
   - Update both `child.material.color` and physical surface attributes (`metalness`, `roughness`, `clearcoat`, `clearcoatRoughness`) on the matching mesh.
2. In `materialClassifier.applyPresentationMaterials()`:
   - Before classifying a mesh as generic host framing, verify `!isAddonObject(object)`.
   - Meshes belonging to an add-on assembly must never be touched or overwritten by the host product's palette applicator.

### 3.4 Deep Add-on Mesh Tagging in Geometry Builders
In `parametricProductBuilder.ts` and `addonGeometryBuilder.ts`:
1. **Uploaded Add-on Clones:** When cloning components from cache in `buildAddonAttachment()`, traverse the cloned hierarchy and explicitly set `child.userData.isAddon = true`, `child.userData.presentationCategory = comp.presentationCategory`, and `child.userData.preserveMaterial = true` directly on every `THREE.Mesh`.
2. **Middle Grille Bar Repetition:** In `buildGrillAssembly()`, ensure that repeated tile clones in `tileClone.traverse()` set `child.userData.isAddon = true` directly on the mesh in addition to `preserveMaterial = true`.
3. **Screen Access Hatch Instances:** In `buildAddonAttachment()`, ensure that hatch sub-frame meshes inside `finalMesh` receive `child.userData.isAddon = true` and `child.userData.presentationCategory = "Framing"`.
4. **Pass `addonConfig` in `loadModel()`:** In `ProductModelWorkspace.tsx`, ensure `loadModel()` receives the complete `addonConfig` object containing `{ finishColor: getFinishHexColor(addonAlumFinish), zOffsetMm: 18 }`.

## 7. Scope Boundary

1. **In Scope:**
   - Client visualization workspace (`ProductModelWorkspace.tsx`) color and material selection handlers.
   - Three.js presentation updater (`modelRenderer.ts`) and scene graph hierarchy traversal.
   - Material palette classifier (`materialClassifier.ts`) isolation between host and add-on meshes.
   - Parametric product builder (`parametricProductBuilder.ts`) and add-on geometry builder (`addonGeometryBuilder.ts`) mesh metadata tagging.
   - Cache invalidation key harmonization to eliminate unnecessary model re-creations.
2. **Out of Scope:**
   - Modifying database schema or creating new Supabase migrations (existing `raw_materials` and `product_components` schemas remain unchanged).
   - Altering the mathematical pricing formulas or scrap factors in `pricingEngine.ts`, `addonPricingEngine.ts`, or `grillePricingEngine.ts`.
   - Modifying FastAPI computer vision endpoints or fiducial paper detection algorithms.
   - Introducing new third-party styling frameworks or UI component libraries.
